## 1. 목록·숫자가 비어 보임

### 1-1. 에러를 빈 상태로 뭉갬 (가장 비쌌던 버그)

**증상**: "HOT SPOTS에 아무것도 안 뜬다." 백엔드를 curl로 부르면 5건이 정상 응답.

**원인**: `FutureBuilder`가 `snapshot.hasError`를 전혀 확인하지 않고 `final hotspots = snapshot.data ?? [];`만 씀. 네트워크 에러·타임아웃·스키마 불일치가 **전부 "지금 활동 중인 관광지가 없어요"라는 동일한 빈 상태 문구로 뭉개짐.**

**왜 비쌌나**: 백엔드가 정상이라 원인을 특정할 수 없었다. 콜드 캐시 재현 테스트까지 하고서야 프론트 문제로 좁혀졌다. 실제 원인은 코드 변경이 반영되지 않은 상태(재시작 누락)였을 가능성이 높다.

**재발 방지**: 모든 `FutureBuilder`에서 `waiting` / `hasError` / `isEmpty` / 정상 네 상태를 분기한다. 에러는 빨간 배너 + 원문 메시지, 빈 상태는 회색 안내 문구로 **시각적으로 구분**한다.

**검증**: 신규·수정된 `FutureBuilder`마다 `hasError` 분기 존재 확인.

### 1-2. 코드 변경이 반영되지 않음

**증상**: 고쳤는데 화면이 그대로.

**원인**: 백엔드 응답 스키마를 바꾼 뒤에는 프론트 hot reload만으로 부족하다. 완전 재시작이 필요하다.

**재발 방지**: 코드 버그로 단정하기 전에 양쪽 완전 재시작을 먼저 시도한다.

### 1-3. 탭을 살려두는 구조라 예전 숫자가 그대로 보임 (백엔드는 정상)

**증상**: "제보했는데 마이 화면 크레딧이 안 올라요." curl로 부르면 서버 값은 이미 올라가 있다.

**원인**: `home_screen.dart`가 `IndexedStack`이라 탭 위젯이 죽지 않는다. `initState`는 **앱 실행 중 한 번만** 돌므로, 다른 탭에서 서버 상태를 바꾸고 돌아와도 `FutureBuilder`가 예전 Future를 그대로 들고 있다.

**왜 놓치기 쉬운가**: 경계면(필드명·타입·경로)은 완벽하고, 백엔드도 정상이고, 화면 새로고침(앱 재시작)하면 맞는 값이 나온다. 그래서 "가끔 안 맞는다"로 보고되고 원인을 서버에서 찾게 된다.

**재발 방지**: **A 탭의 쓰기가 B 탭의 숫자를 바꾸면, B 탭은 재진입 시 재조회해야 한다.** `MapScreen`이 쓰는 `isActive` 규약을 그대로 따른다 — 부모가 `isActive: _currentIndex == <탭 index>`를 내려주고, 자식이 `didUpdateWidget`에서 비활성→활성 전환을 감지해 Future를 새로 만든다. 새 패턴을 만들지 않는다.

**검증**: 신규 화면이 서버 값을 읽는다면 ① 다른 탭의 쓰기가 이 값에 영향을 주는지 따지고 ② 준다면 재조회 경로(최초 진입 / 탭 재진입 / 하위 화면 복귀 / 명시적 새로고침)를 열거해 본다. `initState` 하나뿐이면 부족하다.

### 1-4. 성공 경로에서만 상태를 갱신해 실패 시 낡은 목록이 남음

**증상**: 이미 처리한 항목(답변한 질문, 삭제한 항목)이 배너·목록에 계속 보인다. 서버 데이터는 정상이고 에러도 안 보인다.

**원인**: 응답을 받아 `setState`로 목록을 갈아끼우는 코드가 **성공 분기 안에만** 있다. 실패·조기 return 경로에서는 이전 목록이 그대로 남는다.

```dart
if (!result.presenceRegistered) return;             // ← 여기서 나가면 목록이 안 바뀐다
setState(() => _pendingQuestions = result.pendingQuestions);
```

**왜 놓치기 쉬운가**: 같은 메서드가 "최초 조회"와 "행동 후 갱신(`onAnswered` 콜백)" 두 용도로 쓰일 때만 드러난다. 최초 조회에서는 이전 목록이 비어 있어 증상이 없다.

**재발 방지**: 조회 결과로 목록을 그리는 메서드는 **모든 종료 경로에서 목록을 확정**한다 — 실패면 빈 목록을 명시 대입한다(`_x = []`). 배너·목록이 사라지는 것은 다이얼로그가 아니므로 "무음 처리" 원칙과 충돌하지 않는다.

**검증**: 같은 응답을 소비하는 화면이 둘 이상이면 **실패 경로 처리를 나란히 놓고 대조**한다. 한쪽이 `cond ? list : []`이고 다른 쪽이 `if (!cond) return;`이면 둘 중 하나는 낡은 상태를 남긴다.

### 1-5. 중복 요청을 "건너뛰기"로 막아서 실패가 성공으로 둔갑

**증상**: 사용자가 당겨서 새로고침을 했는데 화면이 **빈 목록**을 그린다. 에러 표시는 없다. 서버는 정상이거나, 정상이 아닌데도 그 사실이 화면에 안 나온다.

**원인**: 주기 폴링과 사용자 새로고침이 **같은 조회 함수**를 부르는데, 중복 방지를 이렇게 구현했다.

```dart
if (_isPolling) return;          // ← 이미 폴링 중이면 그냥 나간다
```

새로고침을 부른 쪽 입장에서 이 함수는 **아무 일도 안 하고 즉시 성공으로 끝난다.** 그 사이 돌던 폴링이 실패해도 새로고침을 부른 화면은 그걸 모르고, "받은 게 없다 = 빈 목록"으로 그린다. 1-1과 같은 계열인데, 이번에는 에러를 삼킨 곳이 `FutureBuilder`가 아니라 **중복 방지 코드**다.

**재발 방지**: **진행 중인 요청의 `Future`를 보관해 두고 그대로 돌려준다.** 부른 쪽은 그 요청의 성공/실패를 똑같이 받는다.

```dart
Future<T>? _inFlight;
Future<T> refresh() => _inFlight ??= _doFetch().whenComplete(() => _inFlight = null);
```

**검증**: 배경 주기 작업과 사용자 시작 작업이 같은 조회를 공유하면, **사용자 쪽 경로가 실패를 받을 수 있는지** 확인한다. `return;`으로 빠져나가는 분기가 있으면 그 자리에서 실패가 사라진다.

## 2. 값이 null로 표시됨

### 2-1. 필드명 불일치

**증상**: 핫스팟 랭킹이 **"null명 | null건"**으로 출력.

**원인**: 서버와 앱의 필드 이름이 다름. Dart는 `json['키']`를 동적으로 읽으므로 컴파일러가 못 잡는다.

**재발 방지**: 응답은 **snake_case**로 고정. `contract_diff.py`로 대조 + curl 실제 응답 키 확인. `function.md` 5장의 "camelCase 통일"은 폐기된 문장이다 — 코드 전체가 snake_case로 구현돼 있다.

### 2-2. Optional 필드를 non-null 캐스팅

**증상**: 특정 항목에서만 캐스트 예외.

**원인**: `basis=REPORT`일 때만 채워지는 `report_count` 같은 조건부 필드를 Dart가 `as int`로 받음.

**재발 방지**: Pydantic `Optional` ↔ Dart `as X?` 를 짝맞춘다. `contract_diff.py`의 `NULLABLE` 코드.

### 2-3. 필수 필드를 기본값으로 삼킴

**증상**: 아무 일도 안 일어난 것처럼 보이는데 값만 비어 있음.

**원인**: 서버 필수 필드를 Dart가 `json['x'] ?? ''`로 받아 실패를 숨김.

**재발 방지**: 필수 필드에 `??`를 쓰지 않는다. 없으면 예외가 나서 드러나는 편이 낫다.

### 2-4. 목록이 이미 받은 값을 상세 화면에 안 넘겨 상세만 폴백을 그림

**증상**: 목록 카드에는 썸네일이 잘 보이는데, 그 항목을 탭해 들어간 상세페이지 헤더만 회색 placeholder다. 통신도 파싱도 정상이라 에러가 한 건도 안 보인다.

**원인**: 목록 응답에 `spot_image_url`이 왔고 모델도 그 값을 들고 있는데, 상세 화면으로 넘기는 생성자 호출(`Spot(contentId:, title:, address:)`)에서 그 필드만 빠졌다. 상세 화면 헤더는 넘겨받은 객체 하나만 보고 그리므로(서버 재조회분은 헤더에 안 쓰임) 값이 없는 것처럼 동작한다.

**왜 놓치기 쉬운가**: 옵셔널 named 파라미터라 안 넘겨도 컴파일이 통과한다. 비슷한 다른 진입 경로(HOT SPOTS)를 복사해 왔는데 **그쪽은 애초에 그 필드가 응답에 없어서** 안 넘기는 것이 맞았다 — 복사 원본이 정상이라 차이를 못 본다.

**재발 방지**: 목록 → 상세 이동을 붙일 때, **목록 모델이 들고 있는 필드와 상세 화면 생성자가 받는 필드를 한 줄씩 대조**한다. 목록에 있는데 안 넘긴 필드는 전부 "왜 안 넘기는지" 답할 수 있어야 한다. 답이 없으면 넘긴다 — 이미 손에 쥔 데이터를 버리고 폴백을 그리는 것은 손해뿐이다. 진입 경로를 복사해 올 때는 원본의 응답 필드 목록이 이쪽과 같은지 먼저 확인한다.

**검증**: 신규 `onTap → push(DetailScreen(...))` 마다 목록 엔트리 모델의 필드 수 ≥ 전달 인자 수 차이를 열거하고 각각의 사유를 확인.

### 2-5. NOT NULL 컬럼을 nullable로 바꿨는데 `Map<String, dynamic>`의 슬롯만 안 고쳐짐

**증상**: 화면 하나가 **build 중 TypeError로 통째로 죽는다**(회색/빨간 에러 화면). 또는 문자열에 `"null"`이 그대로 찍힌다. 특정 사용자·특정 행에서만 재현된다.

**원인**: 서버 컬럼이 `NOT NULL` → `nullable`로 바뀌면 Dart 모델의 `as String`은 `as String?`으로 고쳐야 하는데, **모델 필드만 고치고 `Map<String, dynamic>`으로 받는 자리를 빠뜨린다.** `Map<String, dynamic>`의 `[]`는 `dynamic`을 돌려주므로 `as String` 캐스트도, 문자열 보간(`'${m['nickname']}'`)도 **컴파일러와 `dart analyze`가 전부 침묵한다.** 실제 사례 — `AuthUser.nickname`은 `String?`로 정확히 고쳤는데, `response_model` 없이 dict를 내는 `/api/dev/test-users`를 소비하는 드롭다운(`u['nickname'] as String`)과 스낵바 보간이 남아 있었다. 게다가 그 두 곳은 **각자 따로 캐스팅**하고 있어서 둘 다 틀렸다.

**왜 놓치기 쉬운가**: nullable 전환 후 `grep nickname`을 돌리면 모델 필드가 잔뜩 나와서 "다 봤다"가 된다. `dynamic` 슬롯은 그 목록 안에서 다른 것들과 똑같이 생겼고, 컴파일 오류도 analyze 경고도 없다. 그리고 **null인 행을 만들어야만** 재현된다 — 그 행은 보통 QA 절차서에만 있다.

**재발 방지**:
- nullable 전환 작업에서는 **그 필드 이름을 전수 grep한 뒤, 히트를 "타입이 붙은 자리"와 "`dynamic` 자리"로 나눠 적는다.** `dynamic` 자리(`Map<String,dynamic>`의 `[]`, 문자열 보간, `List<dynamic>` 원소)는 컴파일러가 안 잡으므로 **손으로 세는 것 말고 방법이 없다.**
- **같은 필드를 두 곳 이상에서 캐스팅하고 있으면 헬퍼 하나로 모은다.** 캐스팅 지점이 하나면 다음에 호출부가 늘어도 틀릴 자리가 없다. 폴백 문자열에는 **구분 정보(id 등)를 같이 넣는다** — 미설정 행이 둘이면 라벨이 똑같아져 목록에서 구별되지 않는다.
- **null을 내는 행을 걸러내는 것으로 때우지 않는다.** 그 행이 곧 "미설정 상태"를 재현하는 QA 진입점인 경우가 많다 — 걸러내면 검증 수단을 스스로 없앤다.
- `orElse: () => {'id': x}` 같은 **기본값 Map에 키가 아예 없는 경우**도 같은 경로다(missing key → `null`). 헬퍼가 null과 missing을 같이 받는지 확인한다.

**검증**: nullable로 바꾼 필드마다 ① 실제로 `null`인 행을 만들고(`UPDATE … SET x=NULL`) ② 그 값을 소비하는 화면을 전부 열어 본다. `dart analyze`가 조용한 것은 근거가 아니다.

## 3. 시각이 어긋남

**증상**: "3분 전"이어야 할 제보가 9시간 전으로 표시.

**원인**: 서버는 `datetime.utcnow()`(naive UTC)를 보내는데 Dart가 `Z` 없이 `DateTime.parse`하면 로컬 시각으로 해석한다. KST는 UTC+9.

**재발 방지**: `HotspotEntry._parseUtc` 패턴을 모든 datetime 필드에 적용. `contract_diff.py`의 `UTC` 코드.

관련: "하루 단위 리셋"의 날짜 경계도 KST 기준이다. `_kst_today_start_utc()` / `_today_cutoff_utc()`를 쓴다.

## 4. 요청이 404

**원인**: 새 라우터를 `app/api/router.py`에 `include_router`로 등록하지 않음. 라우터 파일은 멀쩡히 존재한다.

**재발 방지**: 라우터 작성 = 파일 생성 + `router.py` 등록. 둘 다 해야 끝이다. 전체 경로는 `/api` + prefix + 라우터 경로.

## 5. 설정값이 의도와 다르게 동작

### 5-1. 중복 정의

**증상**: 의도한 반경 5000m가 아니라 2000m로 동작.

**원인**: `NearbyRequest` 설정이 파일에 두 번 정의돼 뒤의 것이 이김.

**재발 방지**: 스키마 클래스명 중복 검색. 같은 이름이 두 번 나오면 뒤가 이긴다.

### 5-2. 앱·서버 상수 불일치

**증상**: 앱과 서버가 다른 기준으로 같은 화면을 그림.

**원인**: `config.py`와 `constants.dart`에 같은 개념의 값이 따로 있고 한쪽만 바뀜.

**재발 방지**: 짝이 되는 값은 양쪽 주석에 대응 관계를 명시 (`LIVE_WINDOW_HOURS` ↔ `liveWindowHours`). **실제 판정을 서버가 하는 값은 앱에 두지 않는다.**

**주의**: `constants.dart::gpsVerificationRadius = 500`은 서버의 100+50=150과 다르지만, GPS 판정은 서버가 하므로 이 값은 쓰이지 않는 죽은 상수다. **불일치로 보고하지 말고 미사용·삭제 권고로 보고하라.** 실제로 쓰이는 값인지 먼저 추적하는 것이 판정의 첫 단계다.

### 5-3. 전역 식별 상태를 특정 화면에서만 복원 — 그 화면을 열기 전 배경 작업은 기본값으로 나간다

**증상**: 새로고침 직후 잠깐 **다른 사용자의 데이터**(배지 숫자, 알림, Credit 통계)가 보인다. MyPage를 한 번 열었다 나오면 정상이 된다.

**원인**: "누구로서 요청하는가"를 정하는 값(`ApiService.testUserId`, 앞으로는 로그인 토큰)을 `SharedPreferences`에서 복원하는 코드가 **그 값을 설정하는 화면의 `initState`에만** 있다. 그런데 배경 작업(폴링, 앱 루트의 최초 조회)은 그보다 훨씬 먼저 시작한다.

**왜 놓치기 쉬운가**: 개발 중에는 보통 그 화면을 먼저 열어보게 되어 창이 안 보인다. 웹은 새로고침이 잦아 시연 중에만 드러난다.

### 5-4. 주기·상한 같은 성능 상수의 "근거 주석"이 실제 코드 경로와 다르다

**증상**: 지금은 아무 증상이 없다. 다음 사람이 그 주석을 믿고 값을 더 밀어붙일 때 외부 API 429나 부하로 터진다.

**원인**: 폴링 주기를 60초 → 7초로 줄이면서 앱 상수 옆에 *"이 엔드포인트는 TourAPI를 부르지 않는 경량 엔드포인트라 부담 없다"*고 적었는데, 그 엔드포인트는 실제로는 매 호출 `resolve_spot_names()` → TourAPI를 부른다. 무해하게 만들고 있던 것은 "부르지 않아서"가 아니라 **600초 TTL 캐시** 때문이었고, 주석 어디에도 그 말이 없었다.

**재발 방지**: 주기·상한·타임아웃 값 옆에 근거를 적을 때는 **① 그 값을 떠받치는 안전장치의 이름을 명시하고(캐시·in-flight 가드·rate limit) ② "그 장치를 걷어내려면 이 값부터 다시 보라"는 문장을 같이 남긴다.** "부르지 않는다"류의 단정은 호출 경로를 한 단계씩 따라가 확인한 뒤에만 쓴다. 서로 관계가 생긴 두 상수(예: 폴링 주기 7초 ↔ Dio `receiveTimeout` 8초)는 **양쪽 상수 모두에** 그 관계를 적는다 — 한쪽에만 적으면 다른 쪽을 고치는 사람이 못 본다.

**검증**: 성능 근거를 주장하는 주석을 만나면 그 문장을 **grep으로 검증**하라(정말 그 호출이 없는지). 사실이 아니면 런타임 증상이 없어도 결함으로 보고한다.

**재발 방지**: **요청의 주체를 정하는 전역 상태는 `main()`에서 `runApp` 전에 복원한다.** 화면은 그 값을 바꾸기만 하고, 복원 책임을 갖지 않는다. 복원 키는 상수로 공유한다(`main.dart`의 `_testUserPrefsKey` ↔ `profile_screen.dart`의 `_prefsKey`).

**검증**: 앱 시작 직후 서버를 부르는 코드(폴링·루트 `FutureBuilder`)를 열거하고, 그 시점에 식별 상태가 이미 복원돼 있는지 호출 순서로 확인한다.

### 5-5. "이 요청은 누구인가"를 정하는 값이 둘 이상이 되면 — 소비자를 전수 열거해 우선순위를 통일한다

**증상**: 세 가지가 따로따로 신고된다. ⓐ 계정 A로 쓰다 B로 로그인하면 **B가 원래 갖고 있던 상태를 "방금 바뀐 것"으로 축하**하거나 반대로 진짜 변화가 조용히 넘어간다. ⓑ 로그아웃했는데 **배경 작업(폴링·WS)이 계속 돈다.** ⓒ 화면에는 "로그인하세요"인데 **버튼 게이트는 통과**하고 모든 요청이 401로 떨어진다.

**원인**: 신원 체계가 하나(예: 개발용 `X-Test-User-Id`)일 때 쓴 코드가 여기저기 남아 있는데, **두 번째 체계(실제 로그인 토큰)를 도입하면서 그 소비자들을 갱신하지 않았다.** "누구인가"를 읽는 코드는 인증 파일에만 있지 않다 — 실제 사례에서 흩어져 있던 곳:

| 소비자 | 하던 일 | 갱신 안 하면 |
|---|---|---|
| `badge_tracker.dart`의 `SharedPreferences` 키 | 사용자별 기준값 분리 | 로그인 사용자 전원이 `…:default` 한 칸을 공유 |
| `app.dart`의 신원 비교 | 폴링·WS 시작/정지 판정 | 로그아웃해도 안 멈춤 |
| `main.dart`의 복원 | 전역 식별 상태 설정 | 게이트 전체가 무력화 |
| 게이트 위젯의 로그인 판정 | 비로그인 UX | 옛 체계 값만으로 통과 |

**특히 위험한 비대칭**: 개발 전용 값에 `kDebugMode` 같은 가드가 **쓰는 쪽(UI)에만 있고 읽는 쪽(복원)에 없으면**, 릴리스 빌드에서 그 값이 되살아난다. 로컬 `localhost:8080`은 `flutter run`과 `flutter build web` 서빙이 **같은 origin**이라 localStorage가 실제로 겹친다.

**재발 방지**:
- **새 신원 체계를 도입할 때는 옛 체계의 값 이름을 저장소 전수 `grep`해 소비자를 하나도 빠짐없이 열거한다.** 그 목록의 모든 지점이 **같은 우선순위 한 순서**(①실제 로그인 ②개발용 헤더 ③비로그인)를 쓰게 만든다. 서버(`deps.py`)와 앱이 같은 순서여야 한다 — 다르면 "화면엔 내 닉네임, 저장은 남의 이름"이 된다.
- **무효한 ①이 ②로 폴스루하지 않게 한다.** 만료된 토큰이 조용히 개발용 헤더로 대체되면 증상이 더 혼란스럽다.
- **개발 전용 우회 값은 ⓐ 읽는 쪽·쓰는 쪽 가드를 대칭으로 두고 ⓑ 반드시 해제 경로를 만든다.** 해제 경로가 없으면 그 값을 한 번 쓴 브라우저에서는 **비로그인 UX를 두 번 다시 관찰할 수 없어 QA 자체가 막힌다.**

**검증**: 옛 신원 값 이름을 전수 grep해 나온 지점마다 "①을 먼저 보는가"를 한 줄씩 확인한다. 그리고 **해제 → 비로그인 상태 관찰 → 다시 설정**의 왕복이 UI만으로 가능한지 실제로 해 본다.

## 6. 권한 제약이 새어나감

### 6-1. 조건문으로 숨긴 제약

**원인**: "전체 LIVE Q&A에서는 누구도 답변 불가"를 `if`로 버튼을 숨기면 조건이 하나 바뀔 때 새어나온다.

**재발 방지**: 답변 버튼이 **코드 구조상 존재할 수 없는** 별도 위젯으로 분리한다 (`GlobalQaList` vs `QaSection`).

### 6-2. 클라이언트 인증 상태를 신뢰

**원인**: 앱이 "GPS 인증됨" 상태를 들고 있다고 서버가 그대로 믿음.

**재발 방지**: 권한이 걸린 쓰기는 **매 요청마다 서버가 좌표를 재계산**한다. 현장 인증은 영구적이지 않고 일정 시간만 유효하다 (앱이 3분마다 조용히 재인증).

### 6-3. 새 게이트를 도입할 때는 게이트 지점이 아니라 **보호 대상 API에서 역추적**한다

**증상**: 대부분의 버튼은 로그인 유도 시트가 잘 뜨는데, **한 군데만** 서버의 빨간 에러 문구(`"로그인이 필요합니다"`)가 그대로 노출된다. 보안 구멍은 아니지만(서버가 401로 막는다) 사용자에게는 **고장으로 보인다.**

**원인**: 게이트를 붙일 지점 목록을 **화면 쪽에서 위에서부터 훑어** 만들었다. 눈에 띄는 버튼(FAB, 작성 모달 진입점)은 다 잡히는데, **"부수적으로 쓰기 API를 부르는" UI**가 빠진다. 실제 사례 — LIVE 탭의 "GPS 연동" 토글. 스위치 하나지만 켜는 순간 `POST /reports/verify-location` + `/reports/me` + `/questions/me/answers` 세 개가 나간다. 같은 파일의 제보 FAB에는 게이트가 있는데 이 토글에만 없었다.

**재발 방지**: **보호 대상 API에서 위젯으로 올라가는 방향으로 센다.** ① 이번에 401이 되는 엔드포인트를 전부 나열하고 ② 각각을 부르는 `ApiService` 메서드를 grep하고 ③ 그 메서드를 부르는 위젯·화면을 전부 찾아 ④ 진입점마다 게이트가 있는지 확인한다. 게이트가 없는 진입점은 **"왜 없어도 되는지"를 답할 수 있어야 한다**(예: 그 위젯의 데이터가 로그인 필수 응답에서만 생겨 비로그인에게는 구조적으로 도달 불가).

**두 가지 부수 규칙**:
- **게이트는 권한 팝업(GPS·카메라·알림)보다 먼저 둔다.** 순서가 반대면 어차피 못 쓸 사용자에게 위치 권한부터 요구한다.
- **토글·스위치는 켜는 방향만 막는다.** 끄는 동작까지 막으면 로그인이 풀린 뒤 토글을 되돌릴 수 없다.

**검증**: `ensureLoggedIn` 류 호출 수와 위 ④에서 센 진입점 수를 **숫자로 대조**한다. 화면 목록을 훑어 "다 있어 보인다"로 끝내지 않는다. 그리고 이 게이트가 **보안 경계가 아님**을 잊지 않는다 — 실제로 막는 것은 서버 401뿐이고, 게이트는 에러 대신 안내를 보여 주는 UX 장치다. 둘 다 필요하다.

|---|---|---|
| CORS가 적용 안 됨 | `allow_credentials=True` + `allow_origins=["*"]`는 브라우저가 거부하는 조합 | `allow_credentials=False`. 토큰은 쿠키가 아니라 `Authorization` 헤더로 전달하므로 불필요 |

| 누구나 다른 사용자 행세 | `TEST_MODE=true`가 배포에 남음 | 배포 시 `TEST_MODE`, `DEMO_BYPASS_GPS` 모두 `False` |
| 폴백이 정상 경로가 되어 기능이 조용히 죽음 | 외부 모델·API의 실제 응답 시간이 우리 타임아웃 예산보다 길어서 매번 타임아웃 → 폴백. 응답은 계속 200이라 **에러가 한 건도 안 보인다** | 외부 모델·엔드포인트를 이름이나 최신성으로 고르지 말고 **같은 조건에서 4회 이상 재서 중앙값과 "예산 안에 들어온 비율"로 고른다**. 고른 근거(실측 수치)를 설정 상수 주석에 남기고, 모델명은 `.env`로 덮어쓸 수 있게 둔다 |
| 보안 검증이 **꺼진 채로** 정상 동작 (경고 로그만 남음) | 새 설정값(`JWT_SECRET`·`KAKAO_APP_ID` 등)을 `.env.example`에만 추가하고 실제 `.env`는 안 채움. `.env`는 gitignore 대상이라 **builder 에이전트가 채울 수 없고**, "예시 파일 수정"과 "실제 값 채우기"는 다른 사람이 하는 다른 행위다. 키가 없으면 기동을 막는 대신 경고만 남기고 검증을 건너뛰도록 설계한 경우(개발 편의) 특히 조용히 남는다 | 새 설정값을 추가하면 ⓐ `.env.example` ⓑ **로컬 `.env`** ⓒ **배포 환경변수(Railway)** 세 곳을 체크리스트로 적고 각각 확인한다. 서버를 실제로 띄워 **경고 로그가 사라졌는지**를 검증 조건으로 쓴다("추가했다"가 아니라 "경고가 없다"). 같이 딸려오는 것: 더 이상 읽지 않는 죽은 키(`KAKAO_API_KEY` 류)는 같은 작업에서 `.env`에서도 지운다 — 남기면 "어느 키인지 모를 값"이 다시 쌓인다 |
| 새 SDK를 넣었더니 import·호출 시점에 터짐 | ① 패키지가 `requirements.txt`에만 있고 venv에 미설치 ② SDK의 async 클라이언트가 프로젝트에 고정된 다른 의존성의 상위 버전 심볼을 참조 | 착수 전 `venv/Scripts/python.exe -c "import <pkg>"`로 실제 import를 확인한다. async 경로가 의존성과 안 맞으면 SDK 버전을 올리기 전에 **동기 클라이언트를 `asyncio.to_thread`로 감싸는 우회**를 먼저 검토한다(공유 의존성을 올리면 TourAPI·날씨까지 영향) |

## 8. Mock을 실데이터로 바꿀 때

### 8-1. 배지는 진짜가 됐는데 옆 문구는 그대로 하드코딩

**증상**: 화면 일부(배지 하나)만 mock에서 실제 API 값으로 교체했더니, 바로 옆에 있던 다른 하드코딩 문구가 새 실측값과 정면으로 모순되는 말을 하게 됨. (예: 날씨 배지 = "구름 조금", 바로 아래 요약 문구 = "☀️ 쾌적한 날씨" 고정)

**원인**: 작업 범위를 "배지 교체"로만 좁혀서 인접한 다른 하드코딩 텍스트를 안 건드림. 교체 전에는 둘 다 가짜라 안 어긋났는데, 하나만 진짜가 되면서 남은 가짜가 더 눈에 띄게 틀려짐.

**재발 방지**: 화면 일부를 실제 데이터로 바꿀 때는 **같은 카드/섹션 안에 남아있는 다른 하드코딩 텍스트가 새 실측값과 모순되지 않는지 같이 확인**한다. 고칠 필요가 있는데 이번 범위가 아니면, QA에서 관찰로만 남기고 FAIL로 올리지 않되 리더에게 "시연 노출 지점"으로 보고한다.

**검증**: 신규로 실데이터를 붙인 위젯의 형제 위젯(같은 부모 아래 다른 자식)에 조건 없이 항상 렌더링되는 문자열 리터럴이 있는지 확인.

### 8-2. 출처 라벨만 조건부로 만들고 섹션 제목은 그대로 둠

**증상**: 응답의 출처 필드(`source` 등)에 따라 "AI로 생성됨" 라벨은 정확히 숨겨지는데, 그 라벨이 붙어 있던 **섹션 제목·배지("AI 브리핑")는 조건 없이 항상 표시**된다. 폴백 문장(템플릿·안내문)이 여전히 "AI" 간판 아래 놓인다.

**원인**: 정직성 요구사항을 "라벨 하나를 조건부로 만든다"로 좁게 읽음. 같은 주장을 하는 UI 요소가 라벨 말고도(제목, 아이콘, 그라데이션 배지, 애니메이션 연출) 더 있다는 점을 안 셈.

**재발 방지**: 출처 기반 표시를 만들 때는 **그 섹션 안에서 "이건 AI/실시간이다"라고 주장하는 요소를 전부 열거한 뒤**, 어느 것을 조건부로 하고 어느 것을 남길지 명시적으로 결정한다. 남기기로 했다면 그 이유를 일지·QA 관찰에 적는다(암묵적으로 남기면 다음 사람이 버그로 오해한다).

**검증**: `source`가 폴백 값일 때의 위젯 트리를 그려 보고, 화면에 남는 문자열 중 실제 생성 방식과 어긋나는 단어가 있는지 확인.

## 9. 새로 추가한 메서드만 형제와 모양이 다름

**증상**: 에러 화면에 서버가 보낸 한국어 메시지 대신 **영문 기술 문자열**이 그대로 뜬다. (`DioException [bad response]: This exception was thrown because the response has a status code of 500 …`)

**원인**: `api_service.dart`의 기존 메서드들은 전부 이 모양이다.

```dart
} on DioException catch (e) {
  throw Exception(_extractErrorMessage(e));   // 서버 detail을 꺼낸다
}
```

그런데 이번에 추가한 조회 메서드 2개에만 그 `try/catch`가 없었다. Dio는 500을 받으면 상태 코드 검사 `if`에 닿기 전에 `DioException`을 던지므로, 화면까지 올라가는 것은 `Exception`이 아니라 `DioException`이다. 화면은 `'Exception: '` 접두사만 벗기는데 `DioException.toString()`은 그 접두사로 시작하지 않아 벗겨지지 않는다.

**왜 놓치기 쉬운가**: 정상 경로에서는 아무 증상이 없다. **서버가 "정직하게 500을 던지는" 바로 그 순간에만** 드러나는데, 그 상황을 만들려면 일부러 DB를 깨야 한다. 그리고 새 메서드 자체는 문법적으로 완전히 정상이다.

**재발 방지**: **`api_service.dart`에 메서드를 추가할 때는 같은 파일의 형제 메서드를 하나 열어 모양을 그대로 따른다** — `try/catch` 유무, 예외 타입, 반환 타입, 상태 코드 처리. "이 메서드만 다르게 할 이유"를 댈 수 없으면 다르게 만들지 않는다. 이 규칙은 에러 처리에만 적용되는 게 아니다(응답 래핑, 타임아웃, 로깅도 같다).

**검증**: 신규 API 메서드마다 같은 파일의 형제 메서드와 **줄 단위로 나란히 놓고 대조**한다. 특히 `on DioException catch`가 빠진 메서드가 있는지 `grep`으로 센다 — 메서드 수와 `catch` 수가 다르면 그 차이를 설명할 수 있어야 한다.

## 10. 응답 필드를 "삭제"할 때 한쪽만 지움

**증상**: 정책이 바뀌어 응답 필드 하나를 없앴는데, 앱이 그 키를 non-null로 읽고 있어 목록 화면이 통째로 에러가 된다. 또는 반대로 서버는 계속 보내는데 앱만 지워서 **죽은 필드가 조용히 남는다.**

**원인**: 필드 하나가 사는 곳이 최소 다섯 군데다 — 백엔드 Pydantic 스키마 / 라우터 생성자 인자 / `config.py` 설정값 / Dart 모델 필드 + `fromJson` / 그 값을 쓰는 서비스·화면. 지울 때는 추가할 때보다 **놓치기 쉽다**(추가는 안 하면 컴파일이 깨지지만, 삭제는 남겨둬도 안 깨진다).

**같이 딸려오는 것**: 필드가 사라지면 그 값을 전제로 그리던 UI도 사라져야 한다. 전역 TTL 값 하나로 푸터 한 줄("30분이 지나면 사라져요")을 그리고 있었다면, **항목마다 값이 달라지는 순간 그 전역 한 줄은 화면이 하는 거짓말이 된다** — 항목별 표시로 내려야 한다.

**재발 방지**: 필드 삭제는 **삭제 목록을 먼저 적고 시작한다** — 스키마·라우터·설정값·헬퍼 함수·모델 property·Dart 필드·getter·화면. 삭제 후 그 이름 전부를 저장소 전수 `grep`해서 **히트가 주석뿐인지** 확인한다. 실행되는 참조가 하나라도 남으면 실패다.

**의미만 바뀌는 경우가 더 위험하다**: 이름·타입·nullable이 그대로인데 **계산 기준만 바뀐 필드**(예: `expires_at`이 "알림 created_at + 30분" → "질문 created_at + 2시간")는 `contract_diff.py`도 curl 키 대조도 절대 못 잡는다. 이때는 ① 앱에 그 값을 **역산하는 코드가 있는지** grep하고(`add(Duration`, `.add(`, `Duration(hours:`) ② 서버 값과 역산 값이 **실제로 갈라지는 응답**을 하나 만들어 실측한다.

**검증**: `contract_diff.py`가 `[OK]`를 줘도 끝이 아니다. 삭제된 심볼 전수 grep + 의미가 바뀐 필드의 실측 응답 확보까지가 한 세트다.

### 10-1. 이름이 비슷한 이웃을 같이 지운다

**증상**: 지우기로 한 기능과 **다른 기능**의 엔드포인트·상수·모델이 함께 사라진다. 그 기능을 쓰는 화면이 404나 500을 받는데, 이번 작업의 변경 목록 어디에도 그 파일이 없어서 원인을 엉뚱한 데서 찾는다.

**원인**: URL 접두사나 이름 접두사가 같다는 이유로 한 세트로 취급했다. 실제 사례 — 지워야 할 것은 `/api/notifications/**push-settings**`(기능 8, 전역 알림 토글)인데 바로 옆에 `/api/notifications/**settings**`(기능 3, 관광지별 제보 유도 알림)가 있다. **한 단어 차이이고 기본값도 서로 반대다.** `grep "settings"`로 삭제 목록을 뽑으면 둘 다 걸린다.

**재발 방지**: **기능 경계는 경로가 아니라 "어느 기능이 쓰는가"로 긋는다.** 삭제 목록을 이름으로 뽑았으면, 각 항목마다 **소비자(호출하는 화면·서비스)를 한 번씩 열거**해서 이번 기능이 맞는지 확인한다. 소비자가 다른 기능이면 목록에서 뺀다.

**검증**: 삭제 대상과 **이름이 비슷한 생존 대상**을 짝으로 묶어 둘 다 curl로 실측한다 — 지운 쪽은 404, 남긴 쪽은 200에 **응답 본문까지** 정상인지. "지운 것이 지워졌다"만 확인하면 절반이다.

## 12. 기능·UI를 "제거"할 때

### 12-1. UI를 지우면 그 안에만 있던 **조작 경로**가 같이 사라진다

**증상**: 상태를 나타내는 표시(배지 숫자, 파란 점, 강조 테두리)가 **영영 안 꺼진다.** 데이터는 정상이고 에러도 없다.

**원인**: 화면 하나를 제거할 때 "무엇을 보여주고 있었나"만 세고 **"무엇을 할 수 있었나"를 안 셌다.** 실제 사례 — 내 Q&A의 "알림" 탭을 지웠는데, 그 탭에만 읽음 처리 경로 두 개(항목 탭 → 단건 읽음, "모두 읽음" 버튼 → 전체 읽음)가 있었다. 표시는 다른 화면으로 이식했지만 조작을 안 옮겨서, 배지와 강조가 데이터가 만료될 때까지 안 꺼지는 상태가 될 뻔했다.

**왜 놓치기 쉬운가**: 표시는 눈에 보이니까 "이걸 어디로 옮기지"를 반드시 묻게 된다. 조작은 사용자가 누르기 전까지 화면에 아무 흔적이 없어서 제거 목록에서 조용히 빠진다. 그리고 컴파일도 통과하고 analyze도 조용하다.

**재발 방지**: 화면·탭·섹션을 제거할 때 **그 안의 요소를 "표시"와 "조작"으로 나눠 표로 적고 시작한다.** 조작에는 각각 "이걸 없애면 어떤 상태가 못 바뀌게 되나"를 적는다. 답이 "영구히 못 바꾼다"면 반드시 다른 화면으로 이식한다.

**검증**: 제거 후, 그 기능이 만드는 **상태를 되돌리는 경로가 화면에 하나라도 남아 있는지** 확인한다(읽음 처리, 해제, 취소, 끄기, 삭제). 없으면 실패다. TTL·만료로 저절로 없어지는 것은 해결책이 아니다 — 그때까지 사용자에게는 고장으로 보인다.

### 12-2. "이제 안 일어난다"를 증명하려면 **일어날 조건을 만들어야** 한다

**증상**: 검증은 통과했다고 적혀 있는데 실제로는 아무것도 검증되지 않았다. 나중에 그 동작이 살아 있다는 것이 시연 중에 드러난다.

**원인 ⓐ — 음성 결과를 그냥 믿었다**: "질문을 올렸는데 알림이 0건이니 생성이 중단됐다"는 증명이 아니다. **원래도 현장에 사람이 없으면 0건**이다. 음성 결과는 "고쳐서 안 일어난 것"과 "조건이 안 맞아서 안 일어난 것"을 구분하지 못한다.

**원인 ⓑ — 두 필터가 같은 결과를 낸다**: 목록에서 `NEW_QUESTION`이 안 보이는 이유가 새로 넣은 **타입 필터** 때문인지, 원래 있던 **만료 필터**(연결 질문이 2시간을 넘김) 때문인지 구분되지 않는다. 과거 데이터가 대부분 만료돼 있으면 필터를 안 넣어도 같은 화면이 나온다.

**재발 방지**:
- ⓐ **"안 일어남"을 검증할 때는 그것이 일어날 조건을 먼저 만든다.** 이전 코드였다면 **반드시 N건 생겼을** 상태를 데이터로 조성하고(presence 갱신, 좌표 조작 등), 전/후 건수를 집계해 대조한다.
- ⓑ **두 필터가 겹치면 한쪽만 걸리는 데이터를 일부러 만든다.** 위 사례에서는 "연결 질문이 아직 살아 있는 `NEW_QUESTION` 행"을 임시 INSERT해서 만료로는 절대 빠질 수 없게 만든 뒤 조회했다. 검증이 끝나면 그 임시 행은 지운다.

**검증**: 제거·차단을 주장하는 QA 항목마다 **"이 검증이 통과할 다른 이유가 있는가"**를 한 번 묻는다. 답이 있으면 그 이유를 배제하는 데이터를 만들기 전까지 통과로 적지 않는다.

## 11. "새로 온 것"을 개수로 판정 / 리셋 함수가 두 상황을 같은 값으로 묶음

**증상**: 목록과 배지는 정상적으로 갱신되는데 **알림 배너·토스트·하이라이트만 안 뜬다.** 데이터는 분명히 도착했으므로 통신·스키마를 아무리 봐도 원인이 안 나온다.

### 11-1. 변화를 개수로 판정하면 동시 증감에 눈이 먼다

**원인**: "직전보다 개수가 늘었으면 새로 온 것"이라는 판정은 **대용물**이다. 같은 폴링 주기 안에서 1건이 빠지고(만료·삭제·읽음) 1건이 들어오면 개수가 그대로라 **아무 일도 없었던 것으로 판정된다.** 증상은 간헐적이고 재현이 어려워 디버깅 비용이 크다.

**재발 방지**: 묻고 싶은 것이 "무엇이 새로 왔는가"라면 **id 집합의 차집합**으로 직접 물어라 — `current.difference(previous)`. 개수 비교는 목록의 원소가 한 방향으로만 변할 때만 옳다. `> previousCount`, `!= lastLength`, `length` 비교로 변화를 감지하는 코드를 보면 **그 목록에서 원소가 빠질 수 있는지**부터 확인한다(TTL·만료·서버 필터가 있으면 빠진다).

### 11-2. 리셋 함수가 "앱 시작"과 "사용자 전환"을 같은 값으로 묶는다

**원인**: 기준선(baseline)을 `null`로 두면 "첫 관측은 알림을 띄우지 않고 기준선만 세운다"가 된다. 이건 **콜드 스타트에서는 옳다**(앱을 열자마자 묵은 알림이 튀어나오면 안 된다). 그런데 사용자 전환·로그아웃/로그인 리셋이 같은 함수를 재사용해 기준선을 `null`이나 "현재 값"으로 세우면, **전환 직후 이미 도착해 있던 것이 전부 "원래 있던 것"으로 취급돼 조용히 억제된다.**

**재발 방지**: 상태를 리셋하는 함수를 쓸 때 **"이 리셋 후 첫 관측은 사용자에게 새로운 것인가"**를 상황마다 따로 답한다.
- 앱 최초 시작 → 새롭지 않다(기준선 = `null`, 관측만)
- 사용자/계정 전환 → **새롭다**(기준선 = **빈 집합**, 현재 것 전부가 신규로 판정)

두 상황이 같은 값을 쓰고 있으면 한쪽은 반드시 틀렸다. 갈라 놓았으면 **왜 다른지를 그 자리 주석에 쓴다** — 안 쓰면 다음 사람이 "중복이네" 하며 다시 합친다.

**검증**: 배너·토스트류는 **상태를 리셋하는 모든 경로**를 하나씩 밟아 본다(콜드 스타트 / 새로고침 / 사용자 전환 / 앱 복귀). "목록은 갱신되는데 팝업만 안 뜬다"는 신고를 받으면 통신이 아니라 **이 판정 로직 한 곳**을 먼저 열어라.

## 13. 같은 검증 규칙을 서버와 앱 양쪽에 둘 때

**증상**: 사용자가 **정상적인 값**을 입력했는데 앱이 먼저 거부한다. 서버에는 요청이 **아예 나가지 않으므로** 서버 로그에 아무 흔적이 없고, curl로 같은 값을 보내면 200이 나온다. 그래서 "서버는 멀쩡한데 앱만 이상하다"로 신고되고 경계면(필드명·타입·경로)을 아무리 봐도 원인이 안 나온다.

**원인**: 입력 규칙을 앱에도 복제할 때 **판정 조건(정규식·길이)만 베끼고 그 앞의 정규화 단계를 빠뜨렸다.** 실제 사례 — 서버 `validate_nickname()`은 `strip` + **유니코드 NFC**로 자모를 합친 **뒤에** 검사하는데, 앱은 그 NFC 단계 없이 같은 정규식과 길이 제한만 복제했다. 결과적으로 NFD(자모 분해형) 한글 — macOS·iOS 계열의 입력·붙여넣기가 실제로 만드는 형태 — 이 앱에서만 "문자 집합 위반"으로 거부됐다(`밤톨이` = 코드포인트 3개 vs 8개).

**왜 위험한가**: 이 결함의 크기는 **그 입력 화면에서 빠져나갈 수 있는지**에 달려 있다. 닫을 수 있는 시트면 불편이지만, **닫을 수 없는 전면 모달**이면 사용자가 로그아웃 말고는 앱에서 나갈 길이 없는 **사고**가 된다. 강제 모달을 도입하는 순간 그 안의 모든 클라이언트 검증이 이 등급으로 올라간다.

**재발 방지**:
- 클라이언트 검증이 지켜야 할 불변식은 하나뿐이다: **"서버가 허용하는 값을 앱이 먼저 거부하지 않는다."** 반대 방향(앱이 통과시킨 것을 서버가 거부)은 왕복 한 번일 뿐 사고가 아니다. **앱 검증은 서버보다 항상 느슨하거나 같아야 한다.**
- 규칙을 복제할 때는 조건이 아니라 **판정 파이프라인 전체를 순서까지 복제한다** — 정규화 → 길이 → 문자 집합. 한 단계만 빠져도 판정이 갈린다. 에러 문구도 같은 문자열을 쓴다("확인할 땐 초록불, 제출하면 다른 문구"를 막는다).
- **규칙을 위젯 안에 두지 않는다.** 상수·정규식·문구를 위젯 안에 적으면 화면이 하나 늘 때 복제가 한 번 더 일어난다. 별도 파일(`lib/utils/<rule>_rules.dart`)로 빼고 위젯은 그 함수만 부른다.
- 판정이 갈릴 때 **조건을 넓혀서 맞추려 하지 마라.** 넓히면 "서버가 거부하는 값을 앱이 통과시키는" 반대 방향의 불일치가 새로 생긴다(위 사례에서 결합 자모 범위를 정규식에 더하면 합쳐지지 않는 낱자 하나까지 통과한다). **정규화를 맞추는 쪽이 입력 전체에 대해 일치한다.**

**검증**: **양쪽 구현을 같은 입력 코퍼스로 실제로 실행해 판정을 대조한다** — 한쪽 코드를 읽고 "같아 보인다"로 끝내지 않는다. 앱 쪽은 **실제 소스 파일을 import해서** 부른다(규칙을 복제한 검증 스크립트로 확인하면 "복제본은 맞는데 앱은 틀린" 원래의 실패 모드를 그대로 반복한다). 집계할 숫자는 두 개다: **서버 OK & 앱 거부 = 0**(앱 잠김 사고), 앱 OK & 서버 거부(헛왕복). 유한한 문자 범위라면 **전수 스윕**이 가능하다(한글 음절 11,172개 등).

**입력 코퍼스 주의**: NFD처럼 **에디터·git·포매터가 저장 중에 조용히 바꿔 버리는 값**은 소스에 직접 적지 말고 **코드포인트로 조립한다**(`String.fromCharCodes([0x1107, …])`). 그러지 않으면 테스트가 아무것도 검증하지 않게 되는데, 통과하므로 아무도 모른다.
