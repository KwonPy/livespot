# LiveSpot 작업일지

기능 개발 하나가 끝날 때마다 그 기능의 개발 과정과 학습 내용을 기록한다.

작업일지는 단순한 개발 기록이 아니라, **사용자가 1~2개월 뒤 프로젝트를 다시 보면서 무엇을 왜 만들었고 어떻게 동작하는지 복습할 수 있는 문서**를 만드는 것이 목적이다.

## 실행 조건

- 하나의 기능 개발이 완료된 경우
- 하나의 주요 기술 구현이 완료된 경우
- 하나의 문제/오류를 해결했고 기록할 가치가 있는 경우

사소한 코드 수정이나 오타 수정에는 작업일지를 만들지 않는다.

## 저장 위치

```text
docs/worklogs/
```

기능별로 Markdown 파일 하나. 번호로 개발 순서를 알 수 있게 한다.

```text
docs/worklogs/001-realtime-qna.md
docs/worklogs/002-live-page.md
docs/worklogs/003-hot-spots.md
```

**번호 정하는 법:** 쓰기 전에 `ls docs/worklogs/`로 기존 파일을 확인하고 가장 큰 번호 + 1을 쓴다. 번호를 추측하지 않는다. 파일명 뒷부분은 영문 kebab-case로, 기능을 알아볼 수 있게 짧게 쓴다.

---

## 작업일지 기본 형식

```markdown
# [기능명]

## 1. 한 줄 요약
이 기능이 무엇을 하는지 한 문장으로.

## 2. 왜 만들었는가
프로젝트 전체 흐름에서 이 기능이 왜 필요한지.

## 3. 구현한 것
실제로 무엇을 만들었는지.

## 4. 동작 흐름
데이터가 어디에서 들어와 어디로 가는지.

예:
사용자 GPS 좌표
→ Flutter ApiService
→ FastAPI 라우터 (반경 100m 검증)
→ SQLite 저장
→ 목록 응답
→ Dart fromJson
→ 화면

## 5. 주요 파일
관련 파일과 각 파일의 역할.

예:
- livespot_backend/app/routers/questions.py: 질문·답변 API
- livespot_backend/app/models/question.py: DB 테이블 정의
- livespot_app/lib/models/question.dart: 서버 JSON을 앱 객체로 변환
- livespot_app/lib/services/api_service.dart: 서버 호출

## 6. 핵심 코드 / 개념
기능을 이해하는 데 중요한 코드와 개념. 초보자가 이해할 수 있는 설명을 우선한다.

## 7. 사용한 기술
이번에 새로 사용한 기술, 라이브러리, 외부 API.

## 8. 문제와 해결
- 문제:
- 원인:
- 해결:
- 배운 점:

## 9. 의사결정
구현 과정에서 선택한 중요한 결정과 그 이유.

## 10. 배운 것
새롭게 이해한 개념.

## 11. 현재 한계
부족하거나 임시로 처리한 부분.

## 12. 다음 단계
이 기능 이후 자연스럽게 이어지는 작업.
```

이 12절 구조를 그대로 따른다. 절을 늘리거나 순서를 바꾸지 않는다. 해당 사항이 없는 절은 "없음"이라고 쓴다.

---

## 절별 보충 기준

### 9. 의사결정 — 이 절이 일지의 본체다

**사용자가 채팅으로 준 정책 원문이 있었다면 이 절에 인용 블록으로 원문 그대로 남긴다.** 요약하지 않는다.

```markdown
### 사용자가 준 정책 (원문)
> 질문은 관광지 상세페이지에서만 작성 가능 / 자유 텍스트 / TTL 2시간 ...

### 정책에 없어서 확정한 것
| 쟁점 | 결정 | 근거 |
|---|---|---|
| 무엇이 갈렸나 | 어느 쪽을 택했나 | **왜 다른 쪽을 버렸나** |
```

원문과 우리 판단을 반드시 분리한다. 섞어 쓰면 나중에 무엇이 사용자의 말이고 무엇이 우리 해석인지 구분되지 않고, 그때부터 근거로서의 가치가 사라진다. **원문은 사용자만 줄 수 있고 놓치면 복구할 방법이 없다** — 이번 작업에 정책 원문이 있었다면 기록을 빠뜨리지 마라.

"구현했다"는 결정이 아니다. 이 프로젝트에서 실제로 막힌 것은 코드가 아니라 판단이었다 — 설계서(`function.md`)와 사용자 정책이 어긋나거나, 명세에 설계 결정(만료 처리 방식, 정렬 기준, 후보 데이터 출처)이 빠져 있는 경우다. 그 갈림길과 선택 이유를 남긴다.

### 8. 문제와 해결

교훈을 여기에만 적어두면 다음에 아무도 안 읽는다. **일반화해서 해당 스킬이나 `.claude/skills/livespot-contract/references/bug-patterns.md`에 실제 규칙으로 넣고**, "배운 점"에는 어디에 넣었는지도 한 줄 적는다. 특정 파일에만 적용되는 교훈은 일반화가 덜 된 것이다.

### 11. 현재 한계 / 12. 다음 단계

의도적으로 미룬 것은 **나중에 어디에 연결해야 하는지**까지 쓴다. "Credit 지급(+50)은 이번 범위에서 제외 — 기능 4 구현 시 답변 저장 로직에 연결" 같은 기록이 없으면 미룬 것이 그대로 잊힌다.

QA에서 미해결로 남은 항목은 반드시 "현재 한계"에 쓴다. 통과하지 못한 것을 통과로 쓰지 않는다.

## 작성 원칙

### 1. 초보자 관점으로 작성(초등학생도 이해할 수 있을 정도의 수준)

사용자가 나중에 코드를 다시 볼 때 이해할 수 있게 쓴다. 전문 용어만 나열하지 않는다.

잘못된 설명:
> `fromJson`으로 응답을 deserialize해 모델 인스턴스로 매핑한다.

좋은 설명:
> 서버가 보낸 JSON 데이터를 앱이 다룰 수 있는 Dart 객체로 바꿔준다. (이 변환 함수를 `fromJson`이라고 부른다)

필요하면 쉬운 설명 아래에 정확한 기술 용어를 덧붙인다.

### 2. 코드보다 "왜"를 기록

코드를 그대로 복사하기보다 다음에 집중한다.

- 왜 이 기능이 필요한가?
- 왜 이 방법을 선택했는가?
- 어떤 데이터를 다루는가?
- 어떤 문제가 있었는가? 어떻게 해결했는가?

### 3. 실제 구현과 다르게 작성하지 않는다

작업일지는 프로젝트의 현재 상태를 기록한다. 구현하지 않은 기능을 구현한 것처럼 쓰지 않는다. 임의의 기술 선택이나 미래 계획을 실제 구현 내용처럼 쓰지 않는다.

- `_workspace/` 산출물과 실제 소스에서 확인되지 않는 내용을 지어내지 않는다.
- 날짜는 실제 작업일. 추정하지 말고 확인한다.
- 이 저장소는 git 저장소가 아니라 커밋 이력을 근거로 쓸 수 없다.

### 4. 완료 시점의 상태를 기록

기능이 완료된 시점을 기준으로 쓴다. 나중에 그 기능이 변경되면 새 일지를 만들지 말고, 해당 파일 맨 끝에 변경 내용을 덧붙인다.

```markdown
---

## 변경 이력

### {YYYY-MM-DD} — {무엇이 바뀌었나}
- 바뀐 것 / 왜 바꿨나
```

본문 12절은 완료 시점 기록이므로 덮어쓰지 않는다. 단, 본문이 지금 코드와 정면으로 다르면(예: 폐기된 필드) 해당 줄에 "→ {날짜} 변경, 아래 변경 이력 참조"만 덧붙인다.

## 자료 출처

`livespot-feature` 하네스 실행 직후라면 `_workspace/`에 재료가 다 있다.

| 파일 | 어느 절로 |
|---|---|
| `_workspace/01_spec.md` 2절(확정 정책) · 3절(충돌과 판정) · 4절(미결정) | 2. 왜 만들었는가 / 9. 의사결정 |
| `_workspace/02_backend_contract.md`, `03_flutter_wiring.md` | 3. 구현한 것 / 4. 동작 흐름 / 5. 주요 파일 / 7. 사용한 기술 |
| `_workspace/04_qa_report.md` | 8. 문제와 해결 / 11. 현재 한계 |

`_workspace/`가 없으면 실제 소스와 대화 맥락에서 재구성한다.

## 완료 후 체크

- 이 기능의 목적을 설명할 수 있는가?
- 데이터 흐름을 설명할 수 있는가?
- 주요 파일의 역할을 설명할 수 있는가?
- 새롭게 배운 개념을 설명할 수 있는가?
- 발생했던 주요 문제와 해결 방법이 기록되어 있는가?
- 사용자가 준 정책 원문이 있었다면 9절에 원문 그대로 남았는가?
- 다음 작업이 무엇인지 알 수 있는가?

## 중요한 원칙

작업일지는 **개발자용 공식 문서처럼 어렵게 작성하지 않는다.**

사용자가 1~2개월 후 다시 읽었을 때 "아, 내가 이때 이런 이유로 이렇게 구현했구나."라고 기억을 되살릴 수 있는 수준으로 쓴다.

작업일지를 쓰기 위해 기능 개발 방식을 바꾸거나, 불필요하게 긴 내용을 추가하지 않는다.
