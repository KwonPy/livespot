# Credit 보상 · 뱃지 (기능 4 · 11)

> 소급 기록 — 2026-09-08 작성. `function.md` 표에는 아직 "⬜ 미구현"으로 남아 있지만, 코드는 이미 완성돼 있다. 이 일지가 실제 구현 상태를 기록하고 표를 대신한다.

## 1. 한 줄 요약

사용자가 현장 제보를 쓰거나 질문에 답하면 Credit이라는 점수가 쌓이고(제보 +10, 답변 +5), 누적 점수에 따라 새싹🌱 → Spot 탐방객📍 → Spot 탐험가🧭 → 베테랑🏆 → 마스터👑 뱃지가 자동으로 매겨진다.

## 2. 왜 만들었는가

LiveSpot은 사용자가 직접 현장 정보(혼잡도, 대기시간, 주차 상황)를 올려야 굴러가는 서비스다. 아무 보상 없이 "제보해 주세요"만으로는 계속 쓸 이유가 약하다. 그렇다고 복잡한 리워드·포인트샵을 만들면 그 자체가 큰 프로젝트가 된다.

그래서 **"서비스에 정보를 주거나 다른 사람을 돕는 행동에만 점수를 준다"**는 원칙 하나로 단순화했다(질문 작성은 정보를 요청하는 행동이라 0점 — 아래 9절 정책 원문 참고). 점수는 현금이나 상품으로 바꿀 수 없고, 오직 뱃지라는 "타이틀"로만 돌아온다. 리워드 시스템의 복잡함(포인트 가치, 교환 기준, 부정 이용 방지, 소멸 정책)을 전부 걷어내고 게이미피케이션만 남긴 것이 이 기능의 핵심이다.

## 3. 구현한 것

- **`credit_ledger` 테이블** — 잔액 숫자 하나가 아니라 "언제, 왜, 얼마" 적립됐는지 한 줄씩 쌓는 통장식 원장
- **적립 판정 서비스**(`services/credit.py`) — 제보/답변 저장과 **같은 트랜잭션**에서 적립 자격을 판정하고 원장 행을 만드는 로직
- **뱃지 등급 계산**(`resolve_badge`) — 별도 테이블 없이, 누적 점수로부터 그때그때 계산
- **조회 전용 API 3개**(`GET /api/credits/me`, `/me/ledger`, `/me/activity`)
- **앱 화면 2곳** — 마이 화면의 스탯 카드(제보/답변/Credit/뱃지), Credit 내역 화면(통장 내역)

## 4. 동작 흐름

**적립되는 흐름 (제보 예시)**

```
사용자가 현장 제보 작성
→ POST /api/reports (GPS 반경 검증 먼저)
→ credit_service.prepare_report_award() 호출
   - GPS 인증 안 됐으면 → None (적립 안 함)
   - 이미 이 제보로 적립했으면 → None (원장 UNIQUE 제약)
   - 오늘 이 장소에서 이미 3건 적립했으면 → None
   - 위 전부 통과 → CreditLedger 행 객체 생성 (아직 DB에 안 씀)
→ Report 행 생성 → db.add(report), db.add(ledger)  ← 같은 트랜잭션
→ db.commit()  ← 제보와 적립이 한 번에 저장되거나, 둘 다 안 됨
```

**조회되는 흐름 (마이 화면)**

```
마이 화면 진입
→ GET /api/credits/me           → 잔액, 누적, 현재 뱃지
→ GET /api/credits/me/activity  → 내가 쓴 제보/답변/질문 건수
→ 화면 스탯 카드 4칸
→ "Credit 내역" 탭
→ GET /api/credits/me/ledger    → 최신순 원장 전체
→ 통장 UI (+10p 파란 글씨, 회수는 -5p 빨간 글씨)
```

## 6. 핵심 코드 / 개념

**① 잔액(balance)과 누적(total_earned)은 다른 값이다.** 지금은 크레딧을 쓸 곳이 없어서 둘이 항상 같지만, 나중에 크레딧 사용처가 생기면 잔액은 줄어도 누적은 줄지 않는다. **뱃지 등급은 반드시 누적 기준**이다 — 써서 등급이 깎이면 사용자 입장에서 "내가 기여한 사실"이 취소되는 셈이라 부당하다. 그래서 서버는 두 값을 원장에서 각각 따로 더해 보낸다(`get_totals`).

**② 뱃지 등급표는 DB에 저장하지 않는다.** `BADGE_TIERS`라는 상수 목록(0/50/100/200/500점 구간)만 있고, 조회할 때마다 누적 점수를 이 표에 대조해서 즉석으로 계산한다(`resolve_badge`). 등급 컷을 나중에 조정해도 전체 사용자 행을 고칠 필요가 없다.

**③ 적립 자격 판정과 실제 저장(commit)을 분리했다.** `prepare_award()`는 "적립해도 되는지" 확인만 하고 원장 행 **객체**를 돌려줄 뿐, DB에 쓰지는 않는다. 호출한 쪽(`reports.py`, `questions.py`)이 제보/답변 저장과 **같은 `db.commit()`** 안에 이 객체를 같이 넣는다. 왜 이렇게 나눴는지: 만약 적립 판정 따로 commit, 제보 저장 따로 commit 이면 "제보는 저장됐는데 크레딧은 안 들어왔다"(또는 반대) 같은 상황이 실제로 생길 수 있다. 하나의 트랜잭션 안에 있으면 이런 반쪽짜리 상태가 원천적으로 불가능하다.

**④ 이중 지급은 DB 제약 하나로 막는다.** `credit_ledger`에 `UNIQUE(user_id, source_type, source_id)`를 걸어뒀다. 제보는 `source_id`가 매번 새로 생기는 `report.id`라 자연히 1회다. 답변은 조금 다른데, **한 질문에 답변을 여러 개 다는 것 자체는 허용**이지만 적립은 질문당 1번만 줘야 한다. 그래서 답변 적립의 `source_id`는 `answer.id`가 아니라 **`question.id`**로 잡았다 — 같은 질문에 두 번째 답변이 달리면 이 UNIQUE 제약이 코드 조건문 없이 그냥 막아준다.

## 7. 사용한 기술

새 외부 기술은 없다. 기존 패턴을 그대로 재사용했다:
- SQLAlchemy `UniqueConstraint` — 애플리케이션 로직이 아니라 DB 제약으로 부정 이용 방지
- `report_window.today_cutoff_utc()`(KST 자정 계산, [002](002-report-gps-verification.md)에서 만든 함수) 재사용 — "하루 3건" 상한의 하루 경계를 다른 기능(혼잡도, LIVE)과 동일하게 맞추기 위함

## 8. 문제와 해결

이번 소급 기록 시점에는 새로 겪은 버그는 없지만, 코드 주석에 남아있는 **원래 구현 당시 실제로 조심했던 함정** 두 가지를 옮겨 적는다.

- **문제:** 적립 자격 판정 함수(`prepare_award`)는 내부에서 SELECT를 한다. 이걸 `db.add(new_report)` **이후에** 부르면, SQLAlchemy의 autoflush가 그 시점에 끼어들어 아직 커밋 안 된 제보 행을 먼저 DB에 흘려보낸다. 그러면 "중복 제출 시 기존 제보를 그대로 돌려준다"는 관례(`client_request_id` 중복을 `try/except IntegrityError`로 잡는 코드)가 **try 블록 밖에서 예외를 터뜨려** 깨진다.
- **해결:** 적립 판정을 반드시 `db.add(new_report)` **이전에** 호출한다. `report_id`를 미리(`uuid.uuid4()`) 발급해서 원장의 `source_id`로 쓰기 때문에 순서를 바꿀 수 있었다.
- **배운 점:** SQLAlchemy 세션에 SELECT를 넣는 헬퍼 함수는, 호출 순서에 따라 의도치 않은 autoflush를 유발할 수 있다는 일반 규칙. → 새로운 항목으로 일반화하기엔 이번 프로젝트에서 아직 재발한 적이 없어 이 일지에만 남겨두고, 다음에 같은 패턴(판정 함수 + 조건부 저장)이 또 나오면 `bug-patterns.md`에 정식으로 옮긴다.

- **문제:** 마이 화면은 `HomeScreen`의 `IndexedStack`이 탭을 안 죽이는 구조라, 다른 탭에서 제보해서 서버 크레딧이 올라도 마이 탭으로 돌아오면 예전 숫자가 그대로 보였다.
- **해결:** `ProfileScreen`이 `isActive` 플래그를 받아 `didUpdateWidget`에서 비활성→활성 전환을 감지하면 크레딧·활동 Future를 다시 만든다.
- **배운 점:** 이건 이미 일반화된 패턴이라 [[bug-patterns]] 1-3("탭을 살려두는 구조라 예전 숫자가 그대로 보임")에 이미 기록돼 있다 — 사실 그 기록의 실제 사례가 바로 이 화면이다.

## 9. 의사결정

### 사용자가 준 정책 (원문, `function.md` 기능 4·11)

> 핵심 원칙: "서비스에 정보를 제공하거나 다른 사용자에게 도움을 주는 행동에 보상한다." 질문 작성은 정보를 요청하는 행동이라 보상 대상이 아니다 — 크레딧을 주면 보상을 노린 의미 없는 질문이 반복될 수 있다. 답변은 실제로 다음 방문자를 돕는 행동이므로 보상 명분이 있다.
>
> - `credit_ledger` 테이블 — 잔액 숫자 하나가 아니라 통장 거래내역처럼 적립·차감을 쌓는다.
> - `users.credit_balance`는 빠른 조회용 캐시. 원장 합계가 진실.
> - 이중 지급 방지 2중 장치: `client_request_id`(기능 2) + "이 건에 대한 적립은 1회만" DB 제약.
> - 뱃지 등급은 잔액이 아니라 누적 총액 기준.
> - 복잡한 평판·사용자 평가 시스템은 만들지 않는다. 대신 최소한의 제한만 둔다 — 같은 장소 하루 3건까지만 적립 (초과해도 제보 자체는 저장). 행동별 일일 지급 상한의 세부 숫자는 구현 단계에서 확정.
> - 크레딧은 리워드나 현금성 포인트로 교환하지 않는다.
>
> (기능 11) 크레딧을 직접 리워드나 현금성 포인트로 교환하지 않는다. 사용자 활동 → Credit → 누적 Credit → Badge로 이어지는 게이미피케이션만 가져간다. 포인트 가치·교환 기준·부정 이용·운영 정책·제휴처·소멸 정책까지 딸려오는 리워드 시스템은 공모전 MVP 범위 밖으로 명확히 제외한다.
>
> | 누적 크레딧 | 뱃지 |
> |---:|---|
> | 0~49 | 🌱 새싹 |
> | 50~99 | 📍 Spot 탐방객 |
> | 100~199 | 🧭 Spot 탐험가 |
> | 200~499 | 🏆 베테랑 |
> | 500+ | 👑 마스터 |

### 정책에 없어서 확정한 것

| 쟁점 | 결정 | 근거 |
|---|---|---|

| 조회 API에 적립을 유발하는 POST를 별도로 열까 | **열지 않는다.** `api/credits.py`는 조회 전용 | 적립 엔드포인트가 따로 있으면 근거 없이 크레딧을 발급하는 경로가 생긴다. 적립은 반드시 제보/답변 저장 트랜잭션 안에서만 |
| `balance`(잔액)를 화면에 낼까, `total_earned`(누적)만 낼까 | **둘 다 응답에 포함** | 지금은 소비처가 없어 값이 같지만, 나중에 소비 기능이 생겨도 앱 코드를 고치지 않도록 키를 미리 분리 |
| 뱃지 등급 컷 상수를 앱에도 둘까 | **서버만 갖는다.** 앱은 서버가 준 emoji/label/진행률을 그대로 그림 | 서버에서 등급 컷을 조정해도 앱이 옛 기준으로 그리는 어긋남을 원천 차단 |
| 사용자·원장이 아예 없을 때 응답 | **404가 아니라 200 + 0 + 최하위 뱃지** | 아직 아무 활동이 없는 것은 에러가 아니라 정상적인 빈 상태. 여기서 404를 내면 마이 화면 전체가 못 그려진다 |

## 10. 배운 것

- **파생값은 저장하지 않는 편이 안전할 때가 있다.** 뱃지 등급은 원장 합계에서 항상 다시 계산할 수 있는 값이라, 컬럼으로 박아두면 "등급 컷을 바꿨는데 기존 사용자 행이 안 갱신됨" 같은 어긋남이 생긴다. 계산 비용이 작다면(단순 합계 + 표 대조) 저장하지 않고 매번 계산하는 쪽이 정합성 버그를 원천 차단한다.
- **판정(자격이 있는가)과 저장(commit)을 분리하면 여러 곳에서 트리거되는 부수 효과(적립)를 한 트랜잭션에 안전하게 묶을 수 있다.** 제보 저장, 답변 저장처럼 트리거가 여러 파일에 흩어져 있어도, "판정만 하고 객체를 돌려주는" 공용 함수 하나면 각 호출부가 자기 트랜잭션에 알아서 끼워 넣을 수 있다.
- **DB 제약(UNIQUE)은 코드로 짠 조건문보다 믿음직한 최종 방어선이다.** 애플리케이션 로직이 실수로 조건 체크를 건너뛰어도 DB가 거절한다.

## 11. 현재 한계

- 크레딧 소비처가 전혀 없다 — `balance`와 `total_earned`가 지금은 항상 같은 값이다.
- 로그인(기능 1)이 아직 실제로 붙지 않아, 모든 크레딧은 `test_user` 또는 `TEST_MODE`의 `seed_user_*`에 쌓인다. 마이 화면의 "테스트유저 전환" 드롭다운으로 여러 사용자 분리를 시연만 하는 상태다.
- 뱃지는 5단계 고정 표이고, 등급이 오른 순간을 알려주는 알림(예: "새 뱃지 획득!")은 없다 — 조용히 다음 조회 때부터 바뀐 뱃지로 보일 뿐이다.
- 회수(음수 원장 행)를 만드는 관리 기능이나 자동 트리거는 아직 없다. 스키마와 화면(원장 목록의 빨간 -Np 표시)만 준비돼 있다.

## 12. 다음 단계

- 로그인(기능 1)이 붙으면 `deps.get_current_user_id()`만 실제 인증으로 바뀌고 이 기능은 코드 변경 없이 그대로 동작한다(설계상 의도된 지점).
- 크레딧 소비처가 생기면 `balance`가 `total_earned`보다 작아지는 첫 순간이 온다 — 그때 화면 문구("잔액"과 "누적"을 같이 보여주는 두 줄 UI)가 실제로 의미를 갖기 시작한다.
- 뱃지 승급 시점을 감지해 알림(기능 8, 푸시)으로 알려주는 것은 이번 범위 밖으로 남겨뒀다.
