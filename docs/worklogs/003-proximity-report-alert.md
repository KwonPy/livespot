# 관광지별 자동 제보 유도 알림 (기능 3⑤)

> 소급 기록 — 2026-09-01 작성. DB 마이그레이션 생성일 기준 실제 구현은 2026-08-21.

## 1. 한 줄 요약

관심 있는 관광지에 종 아이콘으로 알림을 켜두면, 앱을 켜고 그 근처 50m 안에 들어갔을 때 "지금 제보하시겠어요?" 다이얼로그가 뜬다.

## 2. 왜 만들었는가

제보 기능([002](002-report-gps-verification.md))은 만들었지만, **사용자가 스스로 앱을 열고 상세페이지까지 들어가야만** 제보할 수 있었다. 현장에 있는 사람이 "아 지금 제보해야지"라고 떠올릴 이유가 없다.

원래 기획은 "관광지 근처에 들어오면 자동으로 Live 참여"였는데, 그건 백그라운드 위치 추적(기능 6, `presence` 테이블)이 있어야 한다. 그게 없는 상태에서 할 수 있는 가장 작은 버전으로 만든 것이 이 기능이다.

## 3. 구현한 것

- `spot_notification_settings` 테이블 — 사용자별·관광지별 알림 on/off
- 알림 설정 조회·변경 API
- 앱: 상세페이지 종 아이콘 토글
- 앱: 홈 화면이 떠 있는 동안 60초마다 위치를 확인해 조건에 맞으면 다이얼로그

## 4. 동작 흐름

```
[설정] 상세페이지 🔔 아이콘 탭
→ POST /api/notifications/settings {content_id, push_enabled: true}
→ spot_notification_settings 저장

[감지] 홈 화면, 60초마다 (+ 앱이 다시 화면에 돌아올 때마다)
→ 현재 위치
→ POST /api/spots/nearby (반경 3km) : 주변 관광지 목록
→ GET /api/notifications/settings?enabled_only=true : 알림 켠 목록
→ 둘을 대조 → 알림 켜져 있고 50m 이내인 곳
→ 기기에 저장된 마지막 알림 시각 확인 (2시간 쿨다운)
→ 통과하면 "📍 지금 이곳에 계신가요?" 다이얼로그
→ "지금 제보하기" → 제보 폼(기능 2)
```

## 6. 핵심 코드 / 개념

**`upsert`란** — "있으면 수정, 없으면 새로 만들기"를 한 번에 처리하는 것. 알림 토글은 켰다 껐다를 반복하므로 매번 새 행을 만들면 안 된다. `(user_id, spot_content_id)` 조합에 유니크 제약을 걸어 한 사용자·한 관광지당 한 행만 존재하도록 했다.

**쿨다운은 왜 서버가 아니라 기기에 저장하나** (`shared_preferences`)

```dart
// 마지막 알림 시각을 기기에 저장
await prefs.setInt('proximity_alert_last_$contentId', 지금);
```

알림을 보여준 사실은 "이 기기에서 일어난 일"이지 계정의 상태가 아니다. 서버에 저장하면 다른 기기에서도 알림이 막히는데, 그건 원하는 동작이 아니다. 또 서버 왕복 없이 즉시 판정할 수 있다.

**겹칠 때 하나만 고르기** — 관광지가 밀집한 곳에서는 50m 안에 여러 곳이 동시에 들어온다. 다 띄우면 알림 폭탄이 되므로 **가장 가까운 한 곳만** 고른다.

**사용자가 무시해도 쿨다운은 갱신한다** — 다이얼로그를 띄운 순간 쿨다운을 시작한다. 안 그러면 같은 자리에 서 있는 동안 60초마다 계속 뜬다.

## 7. 사용한 기술

| 기술 | 용도 |
|---|---|
| `UniqueConstraint` (SQLAlchemy) | 사용자·관광지 조합 중복 방지 |
| `shared_preferences` | 기기 로컬 저장 (쿨다운 시각) |
| `WidgetsBindingObserver` | 앱이 다시 화면에 돌아온 시점 감지 |

## 8. 문제와 해결

- **문제:** 이걸 "푸시 알림"이라고 부를 수 있는가?
- **원인:** 진짜 푸시는 앱이 꺼져 있어도 온다. 이건 앱이 켜져 있어야만 동작한다.
- **해결:** 이름과 문서에서 **"foreground 전용"**임을 명시하고, OS Geofencing/백그라운드 추적이 아니라는 걸 코드 주석에도 남겼다.
- **배운 점:** 기능 이름이 실제보다 크면 나중에 자신도 속는다. 설계 원칙 4("정직하게 만든다")는 화면 문구뿐 아니라 **코드와 문서의 이름**에도 적용된다.

## 9. 의사결정

| 쟁점 | 결정 | 근거 |
|---|---|---|
| 백그라운드 위치 추적을 쓸까 | **쓰지 않는다.** foreground 전용 | 웹은 탭을 닫으면 끝이다. OS Geofencing은 모바일 앱 전환이 전제. 지금 할 수 있는 범위에서 정직하게 만든다 |
| 알림 반경 | **50m** (제보 인증의 150m보다 훨씬 좁게) | 알림은 "확실히 그 자리에 있을 때"만 떠야 한다. 애매하게 뜨면 짜증만 난다 |
| 쿨다운 저장 위치 | **기기 로컬** (`shared_preferences`) | 기기별 사건이고, 서버 왕복이 필요 없다 |
| 자동 알림과 능동적 현장 인증의 관계 | **완전히 독립.** 서로의 상태를 보지 않는다 | 알림이 꺼져 있어도 "현장 제보" 버튼은 항상 쓸 수 있어야 한다. 자동 알림 쪽은 이미 50m 안이라는 전제라 서버 인증을 다시 부르지 않고 바로 폼을 연다 |
| 위치 좌표를 서버에 저장할까 | **저장하지 않는다** | 저장하면 사용자의 이동 경로가 복원된다. 거리 판정은 기기에서 하고 좌표는 버린다 |

## 10. 배운 것

- 웹앱과 네이티브 앱의 가장 큰 차이는 **백그라운드 동작**이다. 웹에서 "알아서 감지되는" 기능은 대부분 만들 수 없거나 크게 제한된다.
- 알림 기능은 "언제 보낼까"보다 **"언제 보내지 않을까"**(쿨다운, 하나만, 좁은 반경)를 정하는 게 설계의 대부분이다.

## 11. 현재 한계

- **앱을 닫으면 즉시 멈춘다.** 브라우저 탭을 닫으면 아무 알림도 오지 않는다.
- 홈 화면이 떠 있을 때만 동작한다. 다른 탭(지도/라이브/마이)에서는 타이머가 돌지 않는다.
- 60초마다 위치 + 주변 관광지 조회 2개 API를 호출한다. 사용자가 많아지면 부담이 된다.
- 진짜 푸시(기능 8)는 미구현. `device_tokens`·`push_jobs` 테이블 없음.
