# 북마크 기능 + 상세페이지 날씨 배지 축소·우측 이동

작업일: 2026-09-08

## 1. 한 줄 요약

관광지 상세페이지의 날씨 배지를 작게 줄여 헤더 우측 상단으로 옮기고, 마음에 든 관광지를 저장해 두었다가 마이페이지 목록에서 다시 찾아 들어갈 수 있는 **북마크 기능**을 서버 DB부터 화면까지 새로 만들었다.

---

## 2. 왜 만들었는가

두 가지 서로 다른 일을 한 번에 했다. 서로 의존이 없어서 같이 진행했지만, 둘 다 상세페이지 헤더(`_buildSliverAppBar()`)를 건드린다는 공통점이 있었다.

**(A) 날씨 배지** — [008](008-weather-open-meteo.md)에서 날씨를 붙일 때 배지를 "관광지명 바로 뒤"에 놓았다. 실제로 써 보니 제목 옆에 딱 붙어 있어서 시선을 뺏고, 크기도 필요 이상으로 컸다. 날씨는 이 화면의 주인공이 아니라 부수 정보다. 사용자가 직접 "크기를 줄이고 오른쪽 끝으로 보내달라"고 요청했다.

**(B) 북마크** — `function.md`에서 마이페이지(기능 12)에 "북마크" 메뉴가 있다고 적어두긴 했는데, 실제로는 **껍데기만 있고 아무 동작도 없었다.**

- 마이페이지의 북마크 메뉴는 `onTap` 자체가 없어서 눌러도 리플(누른 표시)조차 안 났다.
- 상세페이지 우상단의 북마크 아이콘은 `onPressed: () {}` — 빈 함수라 눌리기는 하는데 아무 일도 안 일어났다. 이쪽이 더 나빴다. 죽었다는 사실이 사용자 눈에 안 보이기 때문이다.

즉 "여행 중 마음에 든 곳을 담아뒀다가 나중에 다시 본다"는, 여행 앱에서 가장 기본적인 흐름이 통째로 비어 있었다. 이번에 그 빈칸을 채웠다.

## 3. 구현한 것

### (A) 날씨 배지 (프론트만)

- `WeatherBadge` 위젯에 **`compact` 플래그**를 새로 만들었다. 켜면 아이콘 10 / 글자 10 / 여백 6·2 / 모서리 6으로 작아진다. (기존값은 12 / 11 / 8·4 / 8)
- 상세페이지 헤더에서만 `compact: true`를 넘긴다. 지도 화면의 브리핑 카드는 같은 위젯을 쓰지만 플래그를 안 넘기므로 **크기가 그대로**다.
- 배지를 관광지명 옆에서 떼어내, 헤더 이미지 위 **액션 아이콘 줄(뒤로가기·알림·북마크) 바로 아래 우측**에 고정 배치했다.

### (B) 북마크 (백엔드 + 프론트 전부)

백엔드:

- 새 테이블 `bookmarks` + 마이그레이션 1건
- API 3개
  - `POST /api/bookmarks` — 추가
  - `DELETE /api/bookmarks/{content_id}` — 해제
  - `GET /api/bookmarks` — 내 북마크 목록
- `spot_lookup.py`에 목록 카드용 조회 함수 `resolve_spot_cards()` 추가 (이름뿐 아니라 주소·대표이미지까지 가져온다)

프론트:

- 상세페이지 북마크 버튼이 **실제로 동작**한다. 화면에 들어가면 현재 상태를 조회해서 채워진 아이콘/빈 아이콘으로 보여주고, 누르면 토글된다.
- 마이페이지 "북마크" 메뉴 → 새 화면 `BookmarksScreen` 연결
- 북마크 목록 카드를 탭하면 그 관광지 상세페이지로 바로 이동한다.

북마크의 성격 (다른 기능과 다른 점):

| | 북마크 |
|---|---|
| Credit 지급 | **없음** — 남을 돕는 행동이 아니라 개인 편의다 |
| GPS 현장 인증 | **요구 안 함** — "가고 싶다"는 표시라 현장에 없는 사람이 쓴다 |
| 만료(TTL) | **없음** — 제보·질문과 달리 시간이 지나도 유효하다 |

## 4. 동작 흐름

**북마크를 누를 때**

```
상세페이지 북마크 아이콘 탭
→ 화면이 먼저 아이콘을 바꿔 놓는다 (낙관적 반영)
→ ApiService.addBookmark(contentId)
→ POST /api/bookmarks  {"content_id": "126508"}
→ 라우터가 이미 있는지 확인 → 없으면 bookmarks 테이블에 한 줄 INSERT
   (동시에 두 번 들어와도 DB의 UNIQUE 제약이 막는다)
→ 200 {"content_id":"126508","bookmarked":true}
→ 앱은 200이면 그대로 두고, 예외가 나면 아이콘을 되돌리고 SnackBar
```

**마이페이지에서 목록을 볼 때**

```
마이페이지 "북마크" 메뉴 탭
→ BookmarksScreen 진입 (들어올 때마다 새로 조회, 캐시 안 함)
→ GET /api/bookmarks
→ 내 북마크를 최신순(created_at DESC)으로 꺼냄
→ content_id들을 모아 TourAPI에서 이름·주소·대표이미지를 한 번에 조회
   (resolve_spot_cards, 10분 캐시 재사용)
→ [{content_id, spot_name, spot_address, spot_image_url, created_at}, ...]
→ Dart BookmarkEntry.fromJson
→ 썸네일 + 이름 + 주소 + "N일 전" 카드 목록
→ 카드 탭 → SpotDetailScreen(Spot(contentId, title, address, imageUrl))
```

**상세페이지에 들어갔을 때 북마크 상태를 아는 방법**

단건 조회 API(`GET /api/bookmarks/{id}` 같은 것)를 **만들지 않았다.** 대신 목록을 통째로 받아서 내 content_id가 그 안에 있는지 확인한다.

```
initState → GET /api/bookmarks → 목록에 내 contentId가 있나?
  있다 → _bookmarked = true  (채워진 아이콘)
  없다 → _bookmarked = false (빈 아이콘)
  아직 응답 전 → _bookmarked = null → 버튼 비활성(onPressed: null)
```

## 6. 핵심 코드 / 개념

### `bookmarks` 테이블

```
id              String(36) PK   기본값 uuid4
user_id         String(36)      users.id 참조, index
spot_content_id String(20)      TourAPI 관광지 번호(문자열), index
created_at      DateTime        index, 기본값 utcnow
UNIQUE(user_id, spot_content_id)  이름: uq_bookmark_user_spot
```

관광지 정보(이름·주소·사진)를 **여기 저장하지 않는다.** 번호만 들고 있다가 목록을 보여줄 때 TourAPI에서 그때그때 가져온다. 관광지 정보는 우리 것이 아니라서 복사해 두면 원본이 바뀌었을 때 낡은 값이 남는다. (프로젝트 설계 원칙 2)

`UNIQUE(user_id, spot_content_id)` — "한 사람이 같은 관광지를 두 번 북마크할 수 없다"는 규칙을 **DB가 직접 강제**한다. 같은 규칙을 라우터의 `if`문으로도 한 번 더 확인하긴 하지만, 그건 편의고 최종 방어선은 DB다. 두 요청이 거의 동시에 들어오면 `if`문은 둘 다 통과할 수 있는데 DB는 안 뚫린다.

### 멱등(idempotent) — 몇 번 눌러도 결과가 같다

이번 API의 가장 중요한 성질이다. "멱등"이란 **같은 요청을 여러 번 보내도 결과가 처음 한 번 보낸 것과 똑같다**는 뜻이다.

- 이미 북마크된 걸 또 POST → 409(충돌) 아니고 **200**
- 북마크 안 한 걸 DELETE → 404(없음) 아니고 **200**

왜 이렇게 했나: 상세페이지 버튼이 "낙관적 토글"이다. 즉 서버 응답을 기다리지 않고 아이콘부터 바꾼다. 사용자가 빠르게 두 번 누르거나 네트워크가 느려 재시도가 일어나는 일이 일상적으로 생기는데, 거기에 대고 서버가 409/404를 뱉으면 앱은 그걸 실패로 보고 **아이콘을 되돌리고 빨간 SnackBar를 띄운다.** 실제로는 아무 문제도 없었는데 화면만 고장난 것처럼 보인다. 그래서 "결과 상태가 원하는 대로면 성공"으로 정했다.

```python
# app/api/bookmarks.py — 존재 확인 + IntegrityError 이중 방어
if existing.scalar_one_or_none() is None:
    db.add(Bookmark(user_id=user_id, spot_content_id=payload.content_id))
    try:
        await db.commit()
    except IntegrityError:      # 확인과 INSERT 사이에 다른 요청이 끼어든 경우
        await db.rollback()
return BookmarkToggleResponse(content_id=payload.content_id, bookmarked=True)
```

### 낙관적 반영과 롤백

```
1. 화면 상태를 먼저 바꾼다      (사용자는 즉시 반응을 본다)
2. 서버에 요청을 보낸다
3. 실패하면 원래대로 되돌리고 SnackBar로 알린다
```

이 패턴은 새로 만든 게 아니라 알림 토글(`_togglePushSetting`)이 이미 쓰던 것을 복제했다. 앱 안에서 같은 성격의 동작은 같은 방식으로 움직여야 한다.

### `compact` 플래그 — 기본값을 안 건드리는 것이 핵심

```dart
const WeatherBadge({super.key, required this.weather, this.compact = false});
...
size: compact ? 10 : 12,
```

`WeatherBadge`는 상세페이지 말고 지도 화면 브리핑 카드도 쓴다. 위젯 안의 숫자를 그냥 줄이면 **아무도 요청하지 않은 지도 화면까지 같이 작아진다.** 그래서 기본값을 현행 그대로 두고, 상세페이지에서만 `compact: true`를 넘긴다. `briefing_card.dart`는 한 글자도 안 고쳤는데도 동작이 보존된다.

### 서버 시각에 Z 붙이기

서버는 `datetime.utcnow()`가 만든 `"2026-09-08T09:39:39.961484"`를 보낸다. 타임존 표시가 없다(naive UTC). Dart가 이걸 그냥 `DateTime.parse`하면 **한국 시간으로 착각해서 9시간이 어긋난다.** 그래서 파싱 전에 끝에 `Z`를 붙인다. 이건 이 프로젝트에서 이미 여러 번 밟은 지뢰라 `_parseUtc` 함수를 그대로 복사해 왔다.

## 7. 사용한 기술

새로 도입한 라이브러리는 **없다.** 전부 이미 쓰던 것들이다.

- SQLAlchemy 비동기 모델 + `UniqueConstraint`
- Alembic 마이그레이션 (`down_revision`으로 이전 리비전에 이어 붙이기)
- FastAPI `Depends(get_current_user_id)` — 로그인 대신 쓰는 기존 사용자 식별 체계
- TourAPI 상세 조회 + 10분 캐시 (`spot_lookup.py`가 이미 갖고 있던 것을 함수만 하나 더 만들어 재사용)
- Flutter `FutureBuilder` 4분기 / `RefreshIndicator` / `Positioned`(Stack 안 절대 위치 배치)

이번에 새로 배운 것은 라이브러리가 아니라 **"멱등하게 설계한다"는 API 설계 습관**이다(6절·10절 참조).

## 8. 문제와 해결

### 문제 1 — 북마크 목록에서 상세로 들어가면 사진이 사라졌다 (QA O-1)

- **문제**: 목록 카드에는 관광지 썸네일이 잘 보이는데, 그 카드를 탭해서 들어간 상세페이지 헤더는 회색 그라데이션(사진 없을 때 쓰는 대체 배경)으로 떴다. 통신도 파싱도 전부 정상이라 에러가 한 건도 안 났다.
- **원인**: 목록 응답에 `spot_image_url`이 분명히 왔고 `BookmarkEntry`도 그 값을 들고 있는데, 상세 화면으로 넘길 때 그 필드만 빠져 있었다.

  ```dart
  spot: Spot(
    contentId: b.contentId,
    title: b.spotName ?? '관광지 정보 없음 (ID ${b.contentId})',
    address: b.spotAddress,     // ← imageUrl이 없다
  ),
  ```

  상세페이지 헤더는 넘겨받은 `widget.spot.imageUrl` **하나만** 보고 그린다. 서버에서 다시 받아오는 상세 정보(`_spotDetail`)는 헤더 이미지에 안 쓰인다. 그래서 값이 아예 없는 것처럼 동작했다.
- **왜 놓쳤나**: `imageUrl`이 옵셔널 인자라 안 넘겨도 컴파일이 통과한다. 게다가 이 코드는 이미 검증된 HOT SPOTS 진입 경로(`live_screen.dart`)를 복사해 온 것인데, **그쪽은 애초에 응답에 이미지 필드가 없어서** 안 넘기는 게 맞았다. 원본이 정상이라 차이가 눈에 안 띄었다.
- **해결**: `imageUrl: b.spotImageUrl,` 한 줄 추가. `Spot` 생성자에 이미 옵셔널 `imageUrl`이 있어서 다른 변경은 없었다. (QA 2회차에서 리더가 직접 반영, `dart analyze` → No issues found)
- **배운 점**: 목록 → 상세 이동을 붙일 때는 **목록 모델이 들고 있는 필드와 상세 화면 생성자가 받는 필드를 한 줄씩 대조**하고, 안 넘기는 필드마다 "왜 안 넘기는지" 답할 수 있어야 한다. 답이 없으면 그냥 넘긴다 — 이미 손에 쥔 데이터를 버리고 대체 화면을 그리는 건 손해뿐이다. 이 규칙을 `bug-patterns.md` **2-4**로 등록했다.

### 문제 2 — 공유 위젯을 줄이면 요청 안 한 화면까지 같이 줄어든다

- **문제**: "상세페이지 날씨 배지를 줄여달라"는 지시를 그대로 따라 `WeatherBadge` 안의 치수를 줄이면, 같은 위젯을 쓰는 지도 화면 브리핑 카드의 배지까지 조용히 작아진다.
- **원인**: 위젯을 한 화면 전용으로 착각. 실제로는 두 곳에서 공유한다.
- **해결**: 명세 단계(P-A3)에서 미리 잡아, 위젯 내부 상수 대신 `compact` 옵셔널 플래그로 분기하고 **기본값을 현행 그대로** 뒀다. QA에서 `briefing_card.dart`에 `compact`라는 문자열 자체가 없음을 확인해 무영향을 증명했다.
- **배운 점**: 한 화면만 지목한 UI 변경 지시가 와도 **그 위젯을 누가 또 쓰는지 먼저 grep**한다. 바꾸지 말아야 할 것은 기본값이다. 이 규칙을 `livespot-flutter` 스킬의 **"공유 위젯의 모양을 한 화면만 바꿔달라고 하면"** 절로 넣었다.

### 문제 3 — `MyReportEntry`를 복사하면 키 이름이 어긋난다 (사전 차단)

- **문제 가능성**: 북마크 목록 스키마는 `MyReportEntry`를 본떠 만들었는데, 관광지 번호 키 이름이 다르다. `MyReportEntry`는 `spot_content_id`, `BookmarkEntry`는 **`content_id`**다. 복사해 오면 Dart가 `json['spot_content_id']`를 읽어 null이 나고, 그건 이 프로젝트에서 이미 겪은 "null명 | null건" 버그와 같은 유형이다.
- **원인**: 북마크는 관광지 그 자체가 주인공이라 `content_id`가 본체 필드다. 반면 제보 목록은 "제보"가 본체이고 관광지가 딸린 정보라 `spot_` 접두사가 붙는다. 즉 접두사는 **조인해서 붙인 부가 정보**에만 쓴다.
- **해결**: 백엔드가 계약서에 "첫 키는 `content_id`이지 `spot_content_id`가 아니다"라고 경고를 명시했고, QA가 서버 실측 키와 Dart `fromJson`을 문자 단위로 대조해 5/5 일치를 확인했다. 실제 버그로는 발생하지 않았다.
- **배운 점**: 선례 파일을 복사할 때 **키 이름까지 같다고 가정하지 않는다.** 라우터에서도 DB 컬럼명(`spot_content_id`)과 응답 키(`content_id`)를 `content_id=b.spot_content_id`로 명시적으로 갈라 놨다 — 이름이 다르다는 사실이 코드에 드러나 있어야 다음 사람이 안 헷갈린다. (기존 `bug-patterns.md` 2-1이 이미 커버하는 유형이라 새 규칙은 추가하지 않았다)

## 10. 배운 것

**멱등(idempotent)이라는 API 설계 개념.** "같은 요청을 몇 번 보내도 결과가 한 번 보낸 것과 같다"는 성질이다. 이게 왜 중요한지 이번에 몸으로 알았다 — 앱이 "낙관적 반영"(서버 응답 전에 화면부터 바꾸기)을 하는 순간, 중복 요청은 예외 상황이 아니라 **일상**이 된다. 그때 서버가 409/404 같은 에러를 정직하게 뱉으면 앱은 정상 상황을 실패로 처리한다. "요청이 중복인가"가 아니라 **"원하는 최종 상태가 됐는가"**를 성공 기준으로 잡는 것이 옳다.

**"조건문은 편의, 최종 방어선은 DB 제약."** 중복 북마크를 라우터의 `if`문으로 막았지만, 거의 동시에 두 요청이 들어오면 둘 다 `if`를 통과할 수 있다(확인과 INSERT 사이에 틈이 있다). `UNIQUE` 제약은 그 틈에서도 안 뚫린다. 그래서 `if` + `IntegrityError` 이중으로 짰다.

**공유 위젯을 바꿀 때 바꾸지 말아야 할 것은 "기본값"이다.** 새 옵션을 추가하되 기본값을 현행 그대로 두면, 다른 호출부는 파일을 한 글자도 안 고쳐도 동작이 보존된다. "안 건드린 곳이 안 바뀐다"를 코드 구조로 보장하는 방법이다.

**선례를 복사할 때 위험한 건 구조가 아니라 이름이다.** `MyReportEntry`의 구조는 그대로 베끼는 게 맞았지만 키 이름(`spot_content_id` vs `content_id`)은 달라야 했다. 접두사 `spot_`은 "조인해서 붙인 부가 정보"라는 뜻이고, 북마크에서는 관광지 번호가 부가 정보가 아니라 본체다. 이름 규칙에도 의미가 있다.

## 11. 현재 한계

**QA 결과: 8개 항목 전부 PASS, FAIL 0건, 미해결 0건.** 1회차에서 나온 수정 권고 1건(O-1, 8절 문제 1)은 2회차에서 반영 완료했다.

아래는 결함이 아니라, 알고 있으면서 남겨둔 것들이다.

- **실제 화면을 눈으로 보지 않았다 (U-2, 미검증).** 검증은 코드 경로와 curl 실측까지고, `flutter run`으로 화면을 띄워 확인하지는 않았다(검증 규약). 특히 다음 3가지는 좌표 계산상 문제없다고 판단했을 뿐 스크린샷 증거가 없다 — ① 헤더가 접혔을 때 날씨 배지가 액션 아이콘과 실제로 안 겹치는지 ② 글자 크기 10으로 줄인 배지가 읽히는지 ③ 북마크 목록 카드가 좁은 폭에서 넘치지 않는지. **사용자 구동 확인 항목이다.**

- **`X-Test-User-Id`에 DB에 없는 아무 문자열을 넣으면 헤더가 무시된다 (U-1).** 이건 북마크가 만든 결함이 **아니다.** `app/api/deps.py`가 원래 그렇게 동작한다 — 해당 사용자가 DB에 없으면 기본 테스트 사용자로 폴백한다. 실제 사용자 격리(서로 다른 실제 사용자끼리 목록이 갈리는지)는 실측으로 확인했다. 다만 계약서의 격리 실측표만 보면 "아무 헤더나 넣으면 갈라진다"고 오해할 수 있어 기록해 둔다.

- **북마크를 목록에서 해제할 수 없다.** 한계라기보다 사용자가 명시적으로 택한 정책이다(9절 Q2 = A). 해제하려면 그 관광지 상세페이지에 들어가서 버튼을 다시 눌러야 한다. 북마크가 20~30개 쌓이면 정리가 번거로울 수 있다.

- **마이페이지에 북마크 개수가 안 보인다.** 이것도 사용자 선택이다(Q3 = A). 나중에 원하면 `GET /api/credits/me/activity` 응답에 `bookmark_count` 필드 하나를 얹는 것이 가장 싸다 — 엔드포인트를 새로 만들 필요가 없고 마이페이지의 네트워크 요청도 안 늘어난다.

- **북마크 폴더·태그·메모·정렬 옵션·개수 상한 없음.** 이번 범위 밖.

- **로그인 연동 없음.** 프로젝트 전체 규약대로 사용자는 `deps.get_current_user_id()`가 준다.

### 낡아진 문서 (리더가 `function.md`를 직접 갱신할 예정)

이번 작업으로 `function.md`의 아래 서술이 사실과 달라졌다. **이 일지에서 `function.md`를 직접 고치지는 않았다.**

1. **24행 "알림 설정·위치 권한·계정(로그아웃)·북마크는 아직 죽은 메뉴"** — 북마크는 이제 죽은 메뉴가 아니다. 마이페이지 메뉴와 상세페이지 버튼 둘 다 실제로 동작한다. 이 목록에서 "북마크"를 빼야 한다.
2. **기능 12 "MyPage 목록 항목을 탭해도 관광지 상세페이지로 이동하지 않는다"** — 이 정책이 **북마크 목록에 한해 뒤집혔다.** 내 제보·내 Q&A에는 그대로 유효하다. 세 화면을 하나로 묶어 서술한 문장을 갈라야 한다.
