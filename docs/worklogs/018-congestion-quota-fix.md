# 집중률 API 쿼터 소진 버그 수정

## 1. 한 줄 요약

지도·상세페이지의 방문 집중률 데이터가 시간대·날짜별로 뜨다 안 뜨다 하던 문제를 고쳤다. 원인은 캐시가 3곳에 따로 쪼개져 있던 것과, API 실패를 "데이터 없음"으로 착각해 하루 종일 캐싱하던 버그였다.

## 2. 왜 만들었는가

사용자가 "어제는 뜨던 집중률이 오늘 안 뜨고, 아침엔 뜨던 게 저녁엔 안 뜬다"는 증상을 제보해서 원인을 조사했다. [004-congestion-prediction.md](004-congestion-prediction.md)에서 만든 `CongestionService`는 "시군구 단위로 하루 몇 번만 호출하면 개발계정 일일 쿼터(1000회)를 아낄 수 있다"는 전제로 설계됐는데, 실제로는 이 전제가 두 가지 이유로 깨져 있었다.

## 3. 구현한 것

- `CongestionService`를 진짜 싱글턴으로 변경 — 모듈 전역 인스턴스 하나만 두고 `spots.py`/`live.py`/`crowdedness.py`가 전부 이걸 가져다 쓰게 함
- API 호출 실패와 "정상 응답인데 데이터 0건"을 구분하는 `CongestionFetchError` 예외 도입, 실패는 120초만 캐싱(자정까지 굳히지 않음)
- `/live/hotspots`의 집중률 fallback 후보 지역을 서울+경기 → **서울만**으로 축소

## 4. 동작 흐름

```
지도/상세페이지가 집중률 요청
→ CongestionService.get_sigungu_rates(시군구)
→ 캐시에 있으면 그대로 반환 (이제 인스턴스가 하나라 어디서 먼저 캐싱했든 공유됨)
→ 없으면 TatsCnctrRateService 호출
   → 성공(0건 포함) → 당일 자정까지 캐싱
   → 실패 → CongestionFetchError → 120초만 캐싱 (다음 요청에서 재시도 가능)
```

## 5. 주요 파일

- `livespot_backend/app/services/congestion.py` — `CongestionFetchError` 추가, 모듈 전역 `congestion_service` 싱글턴 추가
- `livespot_backend/app/api/spots.py`, `livespot_backend/app/api/live.py`, `livespot_backend/app/services/crowdedness.py` — 각자 만들던 `CongestionService()`를 싱글턴 import로 교체
- `livespot_backend/app/api/live.py::get_hotspots` — 집중률 fallback 후보군에서 경기도 제거

## 6. 핵심 코드 / 개념

**캐시는 인스턴스 소유다.** `CongestionService()`를 새로 만들면 그 안의 `TTLCache`도 새로 생긴다. 세 파일이 각자 `CongestionService()`를 호출하고 있었기 때문에, 같은 시군구 데이터를 요청 경로(지도/상세/레거시 브리핑)에 따라 최대 3번 따로 캐싱하고 있었다 — 설계할 때 기대한 "시군구당 하루 1회"가 실제로는 "시군구당 하루 최대 3회"였던 것이다. 해결은 인스턴스를 하나만 만들고 다 같이 쓰는 것(싱글턴).

**실패와 "데이터 없음"은 다르다.** 기존 코드는 API 호출이 실패해도(타임아웃, 쿼터 초과 등) 빈 딕셔너리 `{}`를 반환했고, 호출부는 이걸 "이 지역엔 원래 데이터가 없다"로 오해해서 자정까지 캐싱했다. 그래서 하루 중 쿼터가 소진된 시점 이후 처음 조회되는 시군구는 그날 하루 종일 "정보 없음"으로 고정됐다. 이제는 실패 시 `CongestionFetchError` 예외를 던져서 호출부가 구분하고, 실패는 120초만 캐싱해 다음 요청에서 다시 시도할 수 있게 했다.

## 7. 사용한 기술

새로운 외부 기술은 없음. Python 예외 처리(`try/except`)와 모듈 전역 변수로 싱글턴을 구현했다.

## 8. 문제와 해결

- **문제:** 집중률 데이터가 "어제는 됐는데 오늘 안 됨", "아침엔 됐는데 저녁엔 안 됨"처럼 들쭉날쭉하게 안 보임
- **원인:** ① `CongestionService` 인스턴스가 3개라 캐시가 공유되지 않아 실제 호출량이 설계 예상의 최대 3배였음 ② API 실패를 "그 지역엔 데이터가 없다"로 착각해 자정까지 캐싱하는 버그가 있어서, 쿼터가 소진된 이후 조회되는 시군구는 그날 내내 빈 값으로 고정됨
- **해결:** 싱글턴화 + 실패/정상 구분 캐싱
- **배운 점:** "외부 서비스 클래스를 여러 파일에서 각자 인스턴스화하면 그 안의 캐시도 갈라진다"는 패턴은 이 프로젝트에 있는 다른 캐시 기반 서비스(`WeatherService`, `PhotoGalleryService` 등)에도 해당될 수 있는 일반 패턴이다. 별도 기록은 하지 않았고, 향후 비슷한 증상이 나오면 이 일지를 참고할 것.

## 9. 의사결정

### 사용자가 준 정책 (원문)

> hot spot에 집중률 데이터 기반으로는 서울지역만 한정하자. 경기도까지 모두 호출하려니까 api 호출이 많은거아니야? 그 부분 확인해주고, 서울의 '관광지'만 집중률 기반으로 보여주는 방안 + 제보는 서울/경기 모두 가능 이렇게 하는 방안도 검토해줘

### 정책에 없어서 확정한 것

| 쟁점 | 결정 | 근거 |
|---|---|---|
| 제보(REPORT) 기반 핫스팟도 서울로 제한할까 | **아니오, 그대로 전국·전 타입 유지** | 제보는 실측 데이터라 집중률처럼 "상대 비율 왜곡"이 없고, 애초에 지역·타입 제한이 없었다. 사용자가 말한 "제보는 서울/경기 모두"는 사실 기존 동작(전국)의 부분집합이라, 별도 구현 없이 이미 요구를 충족하고 있었다 |
| 집중률 fallback을 서울만으로 줄이면서 API 호출도 같이 줄었는지 확인 | 시군구 수 기준 서울 25개, 서울+경기 약 70개로 확인 — 약 1/3로 축소 | 사용자가 "경기도까지 호출하려니 API 호출이 많은거 아니야?"라고 직접 지적한 가설을 코드(`region_codes.py`)로 검증 |

## 10. 배운 것

- data.go.kr류 공공 API는 "에러 없이 조용히 빈 응답"을 주는 경우가 있는데, 이걸 호출부가 "성공, 데이터 없음"과 구분하지 않고 캐싱하면 일시적 장애나 쿼터 초과가 하루 전체를 망가뜨릴 수 있다.
- Python에서 서비스 클래스를 여러 라우터 파일에서 각자 `Service()`로 인스턴스화하면, 그 안에 캐시나 상태를 들고 있을 경우 서로 다른 캐시를 갖게 된다는 점을 놓치기 쉽다.

## 11. 현재 한계

- 실패 원인(타임아웃 vs 쿼터 초과)을 구분하지 않는다. 쿼터가 실제로 소진된 상태라면 120초마다 재시도해도 자정까지는 계속 실패한다 — 다만 이전처럼 하루 종일 "확정된 빈 데이터"로 잘못 캐싱되지는 않는다.
- `_fetch` 실패 시 원본 응답 본문을 로그로 남기지 않아서, 실패가 진짜 쿼터 초과인지 다른 오류인지는 로그만으로 바로 확인할 수 없다.

## 12. 다음 단계

- 실패 원인 중 "쿼터 초과"를 명시적으로 감지해서 그 경우엔 자정까지, 그 외 일시적 오류는 짧게 캐싱하도록 나누는 개선이 남아있다(이번 범위에서는 제외).
