# 현장 제보 저장 + GPS 100m 인증 (기능 2·3)

> 소급 기록 — 2026-09-01 작성. DB 마이그레이션 생성일 기준 실제 구현은 2026-08-18.

## 1. 한 줄 요약

관광지 반경 150m 안에 있는 사람만 혼잡도·대기시간·주차 상황을 올릴 수 있고, 그 제보가 DB에 실제로 저장된다.

## 2. 왜 만들었는가

LiveSpot이 다른 여행앱과 다른 단 하나의 지점이 **"현장에 있는 사람만 쓸 수 있다"**는 것이다. 이게 없으면 그냥 후기 앱이다.

그런데 이걸 만들기 전까지 앱은 제보 폼만 있고 저장되는 곳이 없었다(서버 메모리 리스트에 담겨서 서버를 껐다 켜면 사라졌다). 이 기능이 붙는 시점이 "LiveSpot이 실제로 동작하기 시작하는" 지점이다.

## 3. 구현한 것

- `users`, `reports` 테이블과 첫 Alembic 마이그레이션
- 제보 등록·조회 API
- GPS 거리 판정 — **서버가 매번 직접 계산**한다
- 별도의 "현장 인증" 전용 API — 제보 폼을 열기 전에 먼저 확인하는 용도
- 중복 제출 방지
- 앱: 제보 모달, GPS 인증 배지, 상세페이지 제보 목록

## 4. 동작 흐름

```
[인증] 상세페이지 "현장 제보" 버튼
→ 브라우저 위치 권한 → 현재 좌표
→ POST /api/reports/verify-location {content_id, lat, lng}
→ 서버가 TourAPI로 그 관광지 좌표를 받아옴
→ Haversine 공식으로 거리 계산 → 150m 이내면 verified
→ 성공하면 제보 폼이 열림

[저장] 제보 폼 제출
→ POST /api/reports {혼잡도, 대기, 주차, 코멘트, lat, lng, client_request_id}
→ 서버가 거리를 **다시** 계산 (앱이 보낸 "인증됨" 상태를 믿지 않는다)
→ reports 테이블 저장
→ 상세페이지 목록에 즉시 반영
```

## 6. 핵심 코드 / 개념

**Haversine 공식** (`geo.py`) — 지구가 둥글기 때문에 두 위경도 사이의 실제 거리는 평면 좌표처럼 빼기로 구할 수 없다. 구면 위의 거리를 구하는 표준 공식이 Haversine이고, 그대로 옮겨 썼다.

**판정 기준은 상수 두 개의 합**

```python
GPS_VERIFICATION_RADIUS_M = 100   # 정책상 반경
GPS_ERROR_MARGIN_M = 50           # GPS 측정 오차 허용치
threshold = 100 + 50              # = 실제 판정은 150m
```

**중복 제출 방지 2단**

앱이 제보 폼을 열 때 고유번호(`client_request_id`)를 하나 만들어 함께 보낸다. 서버는:
1. 저장 전에 같은 번호가 이미 있는지 확인 → 있으면 기존 결과를 그대로 돌려준다
2. 그래도 동시에 두 번 들어오면 DB의 유니크 제약이 막는다 → `IntegrityError`를 잡아서 기존 결과를 돌려준다

두 번 누른 사용자에게 에러를 보여주는 게 아니라, **조용히 같은 결과를 돌려주는 것**이 핵심이다.

**작성자 자리표시자** (`deps.py`) — 실제 로그인이 아직 없어서 모든 쓰기 작업의 작성자는 고정된 `test_user`다. 나중에 진짜 로그인이 붙으면 이 함수 하나만 바꾸면 된다.

## 8. 문제와 해결

- **문제:** 노트북으로 시연하면 제보가 아예 안 된다.
- **원인:** 노트북은 GPS 칩이 없어 WiFi나 IP로 위치를 추정한다. 오차가 100m~50km라 150m 판정을 통과할 수 없다.
- **해결:** `DEMO_BYPASS_GPS` 설정을 만들었다. 켜면 거리를 초과해도 거부하지 않고 `gps_verified=false`로 저장한다. 배포 시에는 반드시 꺼야 한다.
- **배운 점:** 위치 기반 기능은 **접속 기기에 따라 아예 동작하지 않을 수 있다.** 시연 환경을 미리 정하고(휴대폰 브라우저) 그게 안 될 때의 우회로를 설계 단계에서 준비해야 한다.

- **문제:** 오차 허용치를 처음엔 100m로 뒀는데, 실제 기기로 테스트하니 멀리 있어도 인증됐다.
- **원인:** 100m + 100m = 200m는 도심에서 지나치게 넓다.
- **해결:** 50m로 좁혔다(총 150m).
- **배운 점:** GPS 임계값은 책상에서 정할 수 없다. 실기기 테스트 후 조정해야 한다.

## 9. 의사결정

| 쟁점 | 결정 | 근거 |
|---|---|---|
| 앱이 보낸 "인증 완료" 상태를 믿을까 | **믿지 않는다.** 저장할 때 서버가 좌표를 다시 계산 | 클라이언트 상태는 조작할 수 있다. 인증과 저장이 별개 요청이라 그 사이에 자리를 떠날 수도 있다 |
| 인증 API와 저장 API의 판정 기준 | **동일한 상수를 공유** | 기준이 다르면 "인증은 성공했는데 제출은 거부되는" 모순이 생긴다 |
| 인증 요청에 `content_id`를 넣을까, GPS로 추정할까 | **반드시 넣는다** | GPS만으로 관광지를 추정하면 주변 여러 곳 중 아무거나 골라잡게 된다. 사용자가 상세페이지에서 고른 곳만 인증한다 |
| 기능별 GPS 적용 범위 | 제보·답변은 **거부**, 리뷰는 허용(표시만), 질문은 **제한 없음** | 질문자는 원래 멀리 있는 사람이다. 질문에 위치 제한을 걸면 서비스가 성립하지 않는다 |
| 관광지 참조 | TourAPI `content_id` 문자열 저장 (로컬 FK 아님) | [001](001-tourapi-spots.md)의 "로컬 캐싱 안 함" 원칙 |
| 사진 업로드 | **이번 범위 제외.** `photo_url` 컬럼·필드만 마련 | 업로드 파이프라인(파일 선택 UI + 저장소 + 엔드포인트)은 별도 작업량. 컬럼만 미리 둬서 나중에 스키마 변경이 없게 함 |
| Credit 지급(+30) | **이번 범위 제외** | `credit_ledger` 테이블이 아직 없다. 기능 4 구현 시 이 저장 로직에 트랜잭션으로 묶어야 한다 |

## 10. 배운 것

- **트랜잭션 경계**: 제보 저장과 Credit 적립은 나중에 반드시 한 트랜잭션으로 묶여야 한다. 따로 두면 "제보는 됐는데 포인트는 안 들어옴" 상태가 생긴다.
- **멱등성(idempotency)**: 같은 요청을 두 번 보내도 결과가 한 번 보낸 것과 같아야 한다는 개념. `client_request_id`가 그 장치다.
- 위치 조작은 서버가 원리적으로 완전히 막을 수 없다. 이건 보안 장치가 아니라 "선의의 사용자가 실수로 원격 제보하는 걸 막는 장치"로 이해하는 게 정확하다.

## 11. 현재 한계

- **사진 업로드 없음.** `photo_url`은 항상 `null`이다.
- **Credit 지급 없음.** 마이페이지 잔액은 항상 0.
- **작성자가 한 명뿐.** 실제 로그인이 붙기 전까지 모든 제보는 `test_user`가 쓴 것으로 저장된다.
- 제보 삭제·수정 기능이 없다.
- 하루 제보 횟수 제한, 순간이동 감지 같은 어뷰징 방지 장치는 설계만 있고 미구현.
