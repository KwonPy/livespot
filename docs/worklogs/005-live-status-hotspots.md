# LIVE 상태창 + 핫스팟 랭킹 (기능 5)

> 소급 기록 — 2026-09-01 작성.

## 1. 한 줄 요약

쌓인 제보를 실시간으로 집계해서, 관광지 상세의 🔴 LIVE 패널과 라이브 탭의 🔥 핫스팟 TOP 5를 **진짜 숫자로** 채운다.

## 2. 왜 만들었는가

제보를 저장하는 것([002](002-report-gps-verification.md))까지 됐지만, 저장된 제보가 **아무 데도 반영되지 않았다.** LIVE 숫자는 코드에 박아둔 고정값이었고, 핫스팟 랭킹은 가짜 데이터인 데다 필드명이 안 맞아 화면에 `null명 | null건`으로 나오고 있었다.

**"현장에서 올린 제보가 저장되고, LIVE 상태창이 진짜 숫자를 보여준다"** — 이 지점이 제품의 가치를 증명하는 순간이다.

## 3. 구현한 것

- `GET /api/live/status/{content_id}` — 상세페이지 LIVE 패널용
- `GET /api/live/hotspots` — 핫스팟 랭킹. 제보가 없으면 집중률 예측으로 채운다
- 앱: 상세 LIVE 패널, 라이브 탭 랭킹, 지도 마커, 탐색 탭 "인기 급상승"을 전부 실데이터로 교체

## 4. 동작 흐름

```
[LIVE 상태]  GET /api/live/status/{content_id}
→ reports 테이블을 시간창 두 개로 조회
   ① 최근 2시간  → is_live, 제보 건수  (활동성 판정)
   ② 오늘(KST)   → 현재 혼잡도/대기/주차 (정보 신선도)
→ 매번 계산해서 응답 (미리 계산해둔 값 아님)

[핫스팟]  GET /api/live/hotspots?limit=5
→ 1순위: 최근 2시간 제보가 있는 관광지 전부
          정렬 = 혼잡도 ↓ → 최신성 ↓ → 건수 ↓
→ 자리가 남으면
   2순위: 서울 전체 관광지의 집중률 예측 ↓  ([004] 참조)
→ 두 소스를 섞지 않고 순서대로 이어 붙임 (basis 필드로 구분)
```

## 6. 핵심 코드 / 개념

**시간창을 두 개 쓴다** — 이게 이 기능의 핵심 아이디어다.

| 무엇 | 기준 | 왜 |
|---|---|---|
| "지금 LIVE인가", 제보 건수 | **최근 2시간** | 활동성 판정. 오래된 제보로 부풀리지 않는다 |
| 현재 혼잡도/대기/주차 | **오늘(KST 자정 기준)** | 정보 신선도. 어제 값을 오늘 것처럼 보여주면 안 된다 |

당일 제보가 하나도 없으면 혼잡도 3개 필드는 전부 `null`로 내려간다. 앱은 그때 "오늘 제보 없음"이라고 표시한다.

**KST 자정을 계산하는 법** — `created_at`은 UTC로 저장되는데 "오늘"은 한국 시간 기준이어야 한다.

```python
now_kst = datetime.utcnow() + timedelta(hours=9)      # UTC → KST
start_of_today_kst = datetime(연, 월, 일)              # KST 자정
return start_of_today_kst - timedelta(hours=9)        # 다시 UTC로 (비교용)
```

**정렬 3중 기준을 한 줄로**

```python
key=lambda c: (혼잡도점수, 최신시각, 제보건수), reverse=True
```

파이썬은 튜플을 앞에서부터 순서대로 비교하므로, `reverse=True` 하나로 세 기준이 모두 내림차순이 된다.

## 7. 사용한 기술

| 기술 | 용도 |
|---|---|
| SQLAlchemy `func.count`, `order_by().limit(1)` | 건수 집계, 최신 1건 조회 |
| `asyncio.gather` | 상위 N개 관광지의 제목·주소를 TourAPI에서 병렬 조회 |
| Pydantic `Literal` | `basis` 필드를 `REPORT`/`CONGESTION` 두 값으로 고정 |

## 8. 문제와 해결

- **문제:** 핫스팟 랭킹이 화면에 `null명 | null건`으로 나왔다.
- **원인:** 서버 응답의 필드 이름과 앱이 읽는 JSON 키가 달랐다.
- **해결:** 응답 필드를 `snake_case`로 통일하고, Dart의 `fromJson`에서 `json['snake_case']` → `camelCase 필드`로 매핑하는 규칙을 고정했다.
- **배운 점:** 이 프로젝트에서 **가장 자주 반복된 버그 유형이 백엔드↔프론트 필드명 불일치**다. 화면이 비어 보이거나 값이 null이면 앱 코드보다 경계면을 먼저 의심해야 한다.
  → 이 교훈은 하네스에 반영되어 있다: `livespot-contract` 스킬(경계면 대조)과 `contract_diff.py`(Pydantic↔Dart 키 자동 대조), `bug-patterns.md`.

- **문제:** 데모 하루 이틀 뒤에 다시 켜면 핫스팟이 전부 비었다.
- **원인:** 시드 스크립트가 넣는 제보의 `created_at`이 실행 시점 기준 상대값이라, 시간이 지나면 2시간 창 밖으로 밀려난다.
- **해결:** 시드 스크립트가 이미 있는 제보를 건너뛰지 않고 **시각을 지금 기준으로 다시 맞추도록** 바꿨다. 데모 직전에 한 번 더 실행하면 된다.
- **배운 점:** "최근 N시간" 기준으로 동작하는 기능은 시드 데이터도 시간을 갱신할 수 있어야 한다.

## 9. 의사결정

| 쟁점 | 결정 | 근거 |
|---|---|---|
| 미리 계산(rollup)해둘까, 매번 계산할까 | **매번 실시간 계산** | 서울 20~30곳 규모에서는 체감 지연이 없다. 미리 계산하면 방금 올린 제보가 바로 안 보인다. 지금 만들면 이른 최적화다 |
| "현장 인원 N명"·"질문 N개"를 보여줄까 | **보여주지 않는다** | `presence`(기능 6)와 `questions`(당시 기능 7 미구현)가 없는데 숫자를 만들면 다시 가짜다. 설계 원칙 4 |
| 활동 통합 테이블(`activities`) | **보류** | 질문·답변이 없으니 "최근 활동" = "최근 제보"다. 상세화면은 이미 불러온 제보 목록 상위 3건을 재사용한다 |
| 제보가 부족할 때 핫스팟을 어떻게 채울까 | **집중률 예측으로 2순위 채움.** 단, 정렬은 섞지 않는다 | 제보가 적은 초기에 랭킹이 텅 비면 화면이 죽는다. 다만 [004](004-congestion-prediction.md)의 "합치지 않는다" 원칙을 지켜, 제보 기반을 전부 먼저 나열하고 남는 자리만 예측으로 채운다. `basis` 필드로 출처를 구분해 앱이 문구를 다르게 쓴다 |
| 혼잡도/대기/주차의 시간 기준 | **당일(KST)**, 활동성 판정과 다른 창 | 신선도가 중요한 정보라 며칠 지난 값이 남아 있으면 오히려 해가 된다 |

## 10. 배운 것

- **하나의 화면에 성격이 다른 두 시간창이 공존할 수 있다.** "활동 중인가"와 "지금 상태가 뭔가"는 다른 질문이라 다른 기준이 맞다.
- 시간대(timezone)를 다루는 코드는 저장은 UTC, 판정은 서비스 기준 시간대(KST)로 명확히 나눠야 한다. 이 KST 자정 계산 로직은 나중에 Q&A의 "하루 단위 리셋"에서 그대로 재사용됐다([006](006-realtime-qna.md)).
- 랭킹에 서로 다른 소스를 섞어야 할 때, **값을 섞는 것**과 **순서를 이어 붙이는 것**은 전혀 다르다. 후자는 원칙을 깨지 않는다.

## 11. 현재 한계

- 관광지 수가 늘어나면 핫스팟 계산이 무거워진다(관광지마다 쿼리 2회 + TourAPI 호출).
- `spot_live_rollup`(60초 사전계산), `activities`(활동 통합) 테이블은 만들지 않았다.
- "현장 사용자 수"(기능 6)는 여전히 없다.
- 시드 데이터에 의존한 데모다. 실사용 제보가 쌓인 상태로 검증한 적은 없다.
