# 알림 정책 축소 — 토글 제거 · 답변 알림만 · Live 배너 제거

> 작업일: 2026-09-13
> 관련 기능: `function.md` 기능 8(푸시 알림) 주 · 기능 12(MyPage) · 기능 6(Q&A) 부
> **선행 일지: [014](014-question-answer-notification.md) — 이번 작업은 014에서 확정했던 정책 3건을 뒤집는다.**

## 1. 한 줄 요약

어제(2026-09-12) 만든 알림 기능이 "너무 많이 알린다"는 판단에 따라, **전역 ON/OFF 토글을 통째로 없애고(테이블까지 드롭), 인앱 알림을 "내 질문에 답변이 달렸을 때" 1종만 남기고, Live 화면의 답변 대기 질문 배너를 제거**했다.

> ⚠️ **같은 날 정정됨 — 아래 3절 "흐름 A"는 더 이상 사실이 아니다.** QA 통과 후 사용자가 앱을 확인하며 정정했다: "알림 목록 *페이지*를 없애라"는 뜻이었지 "새 질문 도착 시 뜨는 실시간 모달까지 없애라"는 뜻이 아니었다. `NEW_QUESTION` 알림 생성과 목록 포함(`active_join`의 타입 필터)을 **같은 날 다시 원상복구**했다. 최종 상태는 **9-6절**을 볼 것 — 이 요약과 3~4절은 정정 *전* 상태를 설명하므로 역사적 기록으로만 읽는다.

## 2. 왜 만들었는가

### 하루 만에 방향이 반대로 꺾인 작업이다

014(기능 8 푸시 알림)는 2026-09-12에 끝났다. 그 일지의 철학은 명확했다 — 사용자가 직접 이렇게 말했다.

> "난 사용자를 귀찮게해야 참여율이 올라간다고 보기때문에 최대한 노출을 시켜줘야한다고 생각해" (014 9-8절 변경 C 원문)

그래서 014는 **"앞으로 알림을 줄이자는 제안이 나오면 그건 사용자 정책을 거스르는 것"**이라고 문서에 못 박아 뒀다. 그런데 하루 뒤, **사용자 본인이 정반대 방향(축소)을 요청했다.**

명세 판정관(`spec-arbiter`)의 판정은 이랬다 — **"사용자 본인이 줄이라고 했으므로 이번 요청이 이긴다"**(우선순위 1: 사용자 최신 정책 > 과거 일지 > 설계서). 014의 못박기는 "우리가 임의로 줄이지 말라"는 뜻이지, 사용자가 직접 줄이는 것을 막는 문장이 아니다.

### 실제로 무엇이 과했나

사용자가 직접 쓰지 않은 이유까지 포함해 정리하면 세 가지다.

| 과했던 것 | 왜 과했나 |
|---|---|
| 알림 ON/OFF 토글 | "설정을 줄이자"는 요청. 토글이 있으면 사용자가 관리할 스위치가 하나 더 생긴다 |
| 질문 알림(`NEW_QUESTION`) | 내가 답변할 의무가 없는 남의 질문까지 알림이 온다. 목록·배지가 남의 질문으로 채워진다 |
| Live 화면 상단 배너 | **바로 아래 "현장 Q&A" 목록에 같은 질문이 또 보인다.** 사용자 원문: "어차피 현장 Q&A 목록에 뜨니까" |

### 이 요청이 "신규 기능"이 아닌 이유

이번 작업에 **새로 만든 화면·API·응답 필드가 하나도 없다.** 전부 제거·필터·화면 재구성이다. 그래서 "무엇을 만들까"가 아니라 **"어디까지 지울까"**가 이번 작업의 전부였다(→ 9절).

## 3. 구현한 것

### 백엔드 (FastAPI)

- **`NEW_QUESTION` 알림 생성 중단** — `create_question`에서 `prepare_new_question(...)` 호출과 그에 딸린 `flush`/`build`/`add_all`/`deliver`를 전부 제거. 질문을 올려도 알림 행이 한 건도 안 생긴다.
- **목록·배지·읽음 처리에 종류 필터** — `active_join()` 헬퍼 **한 곳**에 `Notification.type == 'NEW_ANSWER'` 조건 추가. 이 헬퍼를 `list_active`·`count_unread`·`list_unread_for_update` 세 곳이 공유하므로 세 곳이 자동으로 같은 판정을 쓴다.
- **전역 스위치 관련 코드 전면 삭제** — `_disabled_user_ids()`(OFF 사용자 SELECT) · `get_push_enabled` · `set_push_enabled` · `prepare_new_question` 제거. `select_recipients()`에 남은 필터는 **"본인 제외" 하나뿐**이 됐다.
- **엔드포인트 2개 제거** — `GET /api/notifications/push-settings`, `POST /api/notifications/push-settings` → 이제 **404**.
- **스키마 2개 제거** — `PushSettingsResponse`, `PushSettingsUpdate`.
- **모델 파일 삭제** — `app/db/models/user_notification_setting.py` + `__init__.py`의 import.
- **신규 마이그레이션 `b7f3c1e9a204`** — `user_notification_settings` 테이블 드롭.

### 프론트 (Flutter 웹)

- **알림 설정 토글 카드 제거** — `_buildPushSettingsCard` · `_pushSettingsErrorBanner` · `_onTogglePush` + 상태 3종.
- **내 Q&A를 3탭 → 2탭으로** — "알림" 탭 전체(`_buildNotificationsTab` 외 8개 메서드)를 삭제하고 "내가 쓴 질문 / 내가 단 답변"만 남겼다.
- **안 읽음 4겹 표시를 질문 카드로 이식** — 알림 탭이 없어지면서 갈 곳을 잃은 표시(파란 점 8×8 · 테두리 강조 · 본문 볼드 · "새 답변" 칩)를 "내가 쓴 질문" 탭의 각 질문 카드에 옮겼다.
- **읽음 처리 경로 2개도 질문 탭으로 이동** — 질문 카드를 펼치면 그 질문의 답변 알림만 읽음, 상단 줄의 "모두 읽음" 버튼은 전체 읽음.
- **`initialTabIndex: 2` 참조 전부 재배선** — 재접속 요약 다이얼로그의 "확인하러 가기"가 `const MyQnaScreen()`(탭 0)으로. `initialIndex`에 `clamp(0, _tabCount - 1)` 방어도 넣었다.
- **Live 화면에서 배너 제거** — `PendingQuestionsBanner` 렌더와 `_pendingQuestions` 필드 + 대입 6곳, 그리고 미사용이 된 import 2개를 전부 삭제.
- **모달 문구 단순화** — `_NotificationDialog`의 `NEW_QUESTION` 분기 제거(제목이 `'내 질문에 답변이 달렸어요'`로 고정). 재접속 요약 문구도 `'새로운 질문·답변 알림이 N건'` → `'내 질문에 달린 새 답변이 N건'`.

## 4. 동작 흐름

### 흐름 A — 질문이 올라왔을 때 (**한 번 끊었다가 같은 날 되살린** 경로 — 9-6절 참고)

```
사용자가 질문 등록
→ POST /api/questions
→ [014 원본] 현장 사용자 목록 조회 → NEW_QUESTION 알림 N건 INSERT → WS 신호
→ [이 절 작성 시점] 질문만 저장하고 끝. 알림 0건. (QA가 "현장 4명 있어도 0건"을 실측 확인)
→ [당일 정정 이후 = 현재 상태] 014 원본과 동일하게 복원. 현장 사용자 전원(본인 제외)에게
  NEW_QUESTION 알림 INSERT + WS 신호. 목록/배지에도 다시 잡힌다.
```

**바뀌지 않은 것**: "알림" 탭/목록 *페이지*는 여전히 없다(2탭 그대로). 복원된 것은 실시간 모달과, 그 모달이 딛고 서 있는 목록 조회 데이터일 뿐 — 그 목록을 사용자에게 펼쳐 보여주는 화면은 만들지 않았다. "목록 페이지 없음"과 "목록 조회에 포함됨"이 다른 층위라는 것이 이 정정의 핵심 교훈이다(→ 9-6절).

### 흐름 B — 내 질문에 답변이 달렸을 때 (**유일하게 살아남은** 경로)

```
다른 사용자가 답변 등록
→ POST /api/questions/{id}/answers
→ 질문 주인 1명에게 NEW_ANSWER 알림 1건 INSERT (같은 트랜잭션)
→ WebSocket으로 "뭔가 왔다" 신호만 전송 (내용은 안 보냄)
→ 앱이 GET /api/notifications 재조회
   └ 서버: active_join()이 type='NEW_ANSWER' + 질문이 아직 2시간 안 인 것만 통과
→ NotificationService(앱의 단일 상태 출처)가 items / unreadCount 갱신
   ├→ 모달 다이얼로그 "내 질문에 답변이 달렸어요"
   ├→ MyPage "내 Q&A" 메뉴 우측 미읽음 배지
   └→ 내 Q&A → "내가 쓴 질문" 탭: 그 질문 카드에 파란 점·테두리·볼드·"새 답변" 칩
→ 카드를 펼쳐 답변을 보면 POST /api/notifications/{id}/read → 표시가 꺼진다
```

### 흐름 C — Live 화면의 답변 대기 질문 (**배너만** 사라짐)

```
GPS 인증 (POST /api/reports/verify-location)
→ 응답에 pending_questions 배열이 여전히 온다 (필드 유지)
→ [이전] Live 화면 상단 배너 + 아래 현장 Q&A 목록 = 같은 질문이 두 번
→ [지금] Live 화면은 이 필드를 아예 안 읽는다. 헤더 → QaSection 순서만 그린다
→ 상세페이지는 그대로 배너를 그린다 (이 필드의 소비자로 살아 있다)
```

**정보가 사라지지 않는 근거**: 배너의 원본은 `fetch_spot_questions(pending_only=True, active_only=True, limit=N)`이고, `QaSection(activeOnly: true)`는 **같은 함수**를 `active_only=True`(limit 없음)로 부른다. 즉 **배너에 뜨던 질문 집합 ⊂ 현장 Q&A 목록 집합**이다. 사용자의 전제("어차피 현장 Q&A 목록에 뜨니까")가 코드로 증명된다.

## 6. 핵심 코드 / 개념

### 6-1. "필터를 딱 한 곳에만 넣는다"가 이번 작업의 중심이었다

알림 목록에는 세 가지 질문이 걸린다.

1. **목록에 뭘 보여줄까?** (`list_active`)
2. **배지 숫자는 몇일까?** (`count_unread`)
3. **"모두 읽음"이 뭘 읽을까?** (`list_unread_for_update`)

이 셋이 **같은 답**을 내야 한다. 안 그러면 "배지에는 3건인데 목록은 비어 있다" 같은, 사용자가 절대 이해 못 할 상태가 생긴다. 014가 이걸 대비해 판정 로직을 `active_join()`이라는 헬퍼 하나로 모아 뒀고, 이번에 그 덕을 봤다.

```python
def active_join(stmt):
    # 필터는 반드시 여기 한 곳에만 넣는다.
    # 목록·미읽음 수·읽음 처리 세 곳이 이 함수를 공유한다.
    return stmt.join(Question, Question.id == Notification.question_id).where(
        Notification.type == TYPE_NEW_ANSWER,          # ← 이번에 추가한 한 줄
        Question.created_at >= question_validity_cutoff_utc(),
    )
```

**`POST /notifications/read-all`은 코드를 한 줄도 안 고쳤는데 자동으로 새 정책을 따랐다.** 이것이 필터를 헬퍼에 넣은 이유의 실물 증거다.

한 가지 더 — 이 JOIN은 **INNER JOIN**이다. `Notification.question_id`가 없으면 애초에 목록에 못 실린다. 덕분에 프론트가 걱정하던 "`question_id`가 `null`이면 질문 카드 강조가 조용히 다 꺼진다"는 시나리오가 **구조적으로 불가능**하다(QA가 확인).

### 6-2. 화면에서 표시를 없앨 때는 "그 상태를 끄는 방법"도 같이 옮겨야 한다

알림 탭을 지우면서 딸려 사라질 뻔한 것이 있었다. **읽음 처리 경로 두 개**다.

- 알림 항목을 탭 → 그 알림 읽음
- "모두 읽음" 버튼 → 전부 읽음

이걸 그냥 지웠으면 어떻게 됐을까? **읽음으로 만들 방법이 화면에서 사라진다.** 그러면 MyPage 배지와 질문 카드의 파란 점이 **질문이 2시간 뒤 만료될 때까지 영영 안 꺼진다.** 사용자는 "알림이 고장났다"고 느낀다.

그래서 두 경로를 질문 탭으로 옮겼다.

- **카드를 펼치면** = 답변을 실제로 봤다 → 그 질문의 답변 알림만 읽음 (`_onExpandQuestion`)
- **상단 줄의 "모두 읽음"** → 전부 읽음

"화면을 연 것"이 아니라 **"카드를 펼친 것"**을 읽음으로 본다. 목록을 연 것과 내용을 읽은 것은 다르다는 014의 원칙 그대로다.

### 6-3. 앱은 "읽었는지"를 **계산하지 않는다**

질문 카드에 강조를 그릴지 말지는 앱이 정하지 않는다. 서버가 준 값을 그대로 읽고 **짝만 맞춘다**.

```dart
_notificationService.items
    .where((n) => n.isNewAnswer && !n.isRead && n.questionId == questionId)
```

- `!n.isRead` — 서버가 보낸 `is_read` 그대로. 앱이 "이건 읽은 걸로 치자"를 안 한다.
- `n.questionId == questionId` — 서버의 `question_id`와 내 질문 목록의 `id` 대조.

그리고 목록의 출처는 `NotificationService` **하나**다. 이 화면이 따로 `GET /notifications`를 들고 있지 않으므로 MyPage 배지(`unread_count`)와 갈라질 수가 없다. 014 6-5절의 "상태는 한 곳에서만 관리(single source of truth)"를 그대로 지켰다.

> 초보자용 보충: "계산하지 않는다"는 말이 헷갈릴 수 있는데, 앱이 하는 일은 **필터링(짝 찾기)**이고 하지 않는 일은 **판정(무엇이 읽힌 것인가를 정하는 것)**이다. 판정은 서버만 한다.

### 6-4. 마이그레이션을 "되돌리기"가 아니라 "위에 쌓기"로 한 이유

`user_notification_settings` 테이블을 만든 마이그레이션은 `1d90a3fa7298`인데, 이 리비전은 **테이블 3개(`notifications` · `push_subscriptions` · `user_notification_settings`)를 한 번에** 만든다.

그래서 `alembic downgrade`로 되돌리면 **알림 기능 전체가 날아간다.** 절대 쓰면 안 되는 길이다.

대신 새 리비전 `b7f3c1e9a204`를 그 위에 쌓았다.

- `upgrade()`: 인덱스 드롭 → `drop_table('user_notification_settings')` **하나만**
- `downgrade()`: 그 테이블만 원래 모양대로 재생성 (행 데이터는 복구 안 됨)

실제로 왕복(`upgrade` → `downgrade -1` → `upgrade`)을 돌려서 **`notifications` 100행과 `push_subscriptions`가 전부 무사한 것**을 확인했다.

> **드롭 직전 그 테이블에 7행이 실제로 있었다.** 014 QA가 남긴 테스트 데이터다. 만약 "UI만 지우고 테이블은 남기는" 선택을 했다면, 그 7행 중 OFF로 저장된 사용자는 **알림을 영영 못 받고 되돌릴 화면도 없는** 상태가 됐을 것이다(→ 9절 N3).

### 6-5. `border: null` 대신 투명 테두리를 쓰는 이유

작은 것이지만 기억할 만하다. 질문 카드에 강조 테두리를 켰다 껐다 하는데, 안 읽은 카드만 테두리를 주고 읽은 카드는 `border: null`로 두면 **강조가 꺼질 때 카드가 1px 움찔한다**(테두리 두께만큼 크기가 변하니까).

그래서 읽은 카드에도 **같은 두께의 `Colors.transparent` 테두리**를 둔다. 레이아웃 크기가 변하지 않는다.

## 7. 사용한 기술

**새로 도입한 기술·라이브러리·외부 API는 없다.** 이번 작업은 전부 기존 스택 안의 제거·필터·화면 재구성이다.

다만 이번에 처음 제대로 쓴 것이 하나 있다.

- **Alembic의 "리비전 쌓기"** — 기존 리비전을 수정하거나 `downgrade`로 되돌리는 대신, `down_revision`으로 체인을 이어 새 리비전을 얹는 방식. 이미 적용된 마이그레이션은 **절대 고치지 않는다**가 원칙이다(다른 환경에는 이미 적용돼 있으므로).
- **`alembic check`** — 모델 metadata와 실제 DB 스키마가 일치하는지 확인하는 명령. 모델 파일을 지운 뒤 `No new upgrade operations detected.`가 나온 것이, autogenerate가 그 테이블을 되살리려 하지 않음을 뜻한다.

## 8. 문제와 해결

QA는 **1회차에 통과**했고 수정 요청 0건이었다. 아래는 그 과정에서 미리 막았거나 확인한 지점이다.

### 문제 1 — 이름이 비슷한 두 엔드포인트를 같이 지울 뻔했다

- **문제**: 지워야 할 것은 `/api/notifications/**push-settings**`(기능 8, 전역 토글)인데, 바로 옆에 `/api/notifications/**settings**`(기능 3, 관광지별 제보 유도 알림)가 있다. 이름이 한 단어 차이다.
- **원인**: 기능이 다른데 경로 접두사가 같다. `grep`으로 "settings"를 지우면 둘 다 걸린다.
- **해결**: 명세 단계에서 이 지점을 미리 위험으로 표기했고, QA가 **양쪽을 각각 실측**했다.
  ```
  GET  /api/notifications/push-settings     -> 404   (의도된 제거)
  POST /api/notifications/push-settings     -> 404   (의도된 제거)
  GET  /api/notifications/settings          -> 200
  GET  /api/notifications/settings/128988   -> 200   {"content_id":"128988","push_enabled":false}
  POST /api/notifications/settings          -> 200   실제 토글까지 동작
  ```
  (검증 중 바꾼 값은 원래 값 `false`로 되돌려 놨다.)
- **배운 점**: **기능 경계는 URL 경로가 아니라 "어느 기능이 쓰는가"로 긋는다.** 접두사가 같다는 이유로 한 세트로 취급하면 안 된다. → 이 교훈은 `bug-patterns.md` 10절(응답 필드를 "삭제"할 때 한쪽만 지움)에 **"이름이 비슷한 이웃"** 항목으로 추가했다.

### 문제 2 — "지웠다"를 증명하려면 **그게 생겨야 할 조건**을 만들어야 한다

- **문제**: "`NEW_QUESTION` 알림이 더는 안 생긴다"를 어떻게 증명하나? 그냥 질문을 하나 올려보고 알림이 안 생겼다고 말하는 것은 증명이 아니다 — **원래도 현장에 사람이 없으면 알림은 0건**이다.
- **원인**: 음성 결과(아무 일도 안 일어남)는 "고쳐서 안 일어난 것"과 "원래 조건이 안 맞아서 안 일어난 것"을 구분하지 못한다.
- **해결**: QA가 대상 관광지(`128988`)의 `presences` 행 `last_seen`을 현재 시각으로 갱신해 **"현장 사용자 4명"** 상태를 일부러 만들었다. 이전 코드였다면 여기서 알림이 **반드시 4건** 생겼을 조건이다.
  ```
  onsite presences (2h window) for 128988 = 4
  BEFORE notif counts: {'NEW_ANSWER': 11, 'NEW_QUESTION': 89}
  POST /questions -> 200
  AFTER  notif counts: {'NEW_ANSWER': 11, 'NEW_QUESTION': 89}
    NEW_QUESTION 증가: 0
  ```
- **배운 점**: **"안 일어나는 것"을 검증할 때는 그것이 일어날 조건을 먼저 만든다.** → `bug-patterns.md` **신규 12-2절**에 "'이제 안 일어난다'를 증명하려면 일어날 조건을 만들어야 한다"로 넣었다.

### 문제 3 — 타입 필터가 "진짜 동작한 것"인지 "만료 덕분"인지 구분해야 했다

- **문제**: 과거 `NEW_QUESTION` 89행은 **대부분 연결 질문이 2시간을 넘겨** 어차피 목록에서 빠진다. 목록에 안 보이는 것만으로는 타입 필터가 동작했다고 말할 수 없다.
- **원인**: 두 개의 필터(`type` + `만료`)가 같은 결과를 낸다. 효과가 겹쳐 있으면 원인을 특정할 수 없다.
- **해결**: **연결 질문이 아직 살아 있는(2시간 안) `NEW_QUESTION` 행**을 임시로 INSERT해서 격리 검증했다. "만료로는 절대 안 빠지는" 행을 만든 것이다.
  ```
  DB에 미읽음 NEW_QUESTION: 72건 (그중 유효 질문에 연결된 것 포함)
  GET /api/notifications -> types present: ['NEW_ANSWER']   ← 누출 0
  unread_count: 1   item_count: 2
  read-all 후: NEW_QUESTION 미읽음 72 (그대로) / NEW_ANSWER 미읽음 0
  ```
  목록·배지·읽음 처리 셋 다 같은 판정을 쓴다는 것이 실측으로 확인됐다.
- **배운 점**: **두 필터가 같은 결과를 내는 상황에서는 한쪽만 걸리는 데이터를 일부러 만들어야 검증이 성립한다.** → `bug-patterns.md` **신규 12-2절**에 원인 ⓑ로 함께 넣었다.

### 문제 4 — 화면을 지우면 그 화면이 갖고 있던 "동작"도 같이 사라진다 (사전 차단)

6-2절에 쓴 그대로다. 알림 탭을 지우면서 읽음 처리 경로 2개가 같이 사라질 뻔했고, 그랬다면 배지가 영원히 안 꺼졌을 것이다.

- **배운 점**: **UI를 제거할 때는 "그 UI 안에만 있던 동작"을 목록으로 먼저 뽑는다.** 표시(보여주기)와 조작(끄기·바꾸기)은 보통 같은 화면에 있어서, 표시를 지우려다 조작까지 같이 지운다. → `bug-patterns.md` **신규 12-1절** "UI를 지우면 그 안에만 있던 조작 경로가 같이 사라진다"로 추가했다.

### 문제 5 — 죽은 코드를 안 지우면 `analyze` 기준선이 깨진다 (사전 차단)

Live 화면에서 배너를 떼면 `_pendingQuestions` 필드와 대입 6곳, 그리고 `models/question.dart` import가 전부 **아무도 안 쓰는 코드**가 된다. 남겨두면 `unused_import`·`unused_field` 지적이 새로 생겨 이 프로젝트의 기준선(69건)을 넘긴다.

명세 단계에서 대입 6곳의 위치를 전부 열거해 두고 시작했고, 결과는 **69 → 69 (신규 지적 0건)**이었다.

## 9. 의사결정

### 9-1. 사용자가 준 정책 (원문) — 1차 요청

> 저번에 설정한 알림설정 있잖아. 그냥 토글 페이지 없애고, 그냥 디폴트로 다이얼로그 알림은 가도록 하자. 그리고 인앱 알림은 내 질문에 답변이 달렸을때만 내 Q&A페이지에서 확인할 수 있도록 처리하자. 또한 현재는 질문이 도착하면 live page에서 현장 Q&A랑 따로 배너까지 상단에 뜨는데, 배너 뜨는것도 제거하자. 어차피 현장 Q&A 목록에 뜨니까. 여기까지 작업해줘

### 9-2. 사용자가 준 정책 (원문) — 확인 질문에 대한 확답

`spec-arbiter`가 원문만으로는 갈리지 않는 미결정 5건을 뽑았고, 리더가 그중 **되돌리기 비용이 큰 4건**을 물었다. 아래는 사용자 답변 **원문 그대로**다.

| 리더의 질문 | 사용자 답변 (원문) |
|---|---|
| 알림 설정(`user_notification_settings`) 테이블을 DB에서 완전히 드롭할까요, 아니면 코드에서만 안 쓰이게 분리(테이블·마이그레이션은 유지)할까요? | > **테이블까지 드롭** |
| "디폴트로 다이얼로그 알림은 가도록"에서 말하는 '다이얼로그 알림'은 어떤 걸 가리키나요? | > **기존 인앱 모달 (Recommended)** |
| `NEW_QUESTION`(새 질문 도착) 알림을 이번 정책 변경에서 어떻게 처리할까요? | > **아니 애초에 내 알림목록을 없애라니까? 그리고 인앱알림은 내 질문에 답변 달린 경우에만 작동하도록!** |
| 인앱 알림이 사실상 NEW_ANSWER 1종만 남게 되는데, 내 Q&A 페이지의 '알림' 탭 구조(3탭: 질문/답변/알림)를 그대로 둘까요? | > **알림 탭 자체를 없애라고** |

> 위 네 칸은 사용자가 채팅으로 준 문장 그대로다. 아래 9-3절부터가 우리(에이전트)의 판단이다. 섞어 읽지 말 것.

### 9-3. 이번 요청이 014의 무엇을 뒤집었나

**이것이 이번 작업에서 가장 중요한 기록이다.** 014를 읽은 사람이 사라진 토글을 "버그"로 오인해 되살리는 것을 막기 위해서다.

| 이번 결정 | 무효가 된 014 결정 | 왜 뒤집혔나 |
|---|---|---|
| 알림 토글 제거, 항상 켜짐 | **014 9-2절 Q3=B** ("기본 ON + MyPage에서 전역 OFF 가능") · **9-6절 P19**(전역 스위치 OFF 제외 필터) | 사용자가 "토글 페이지 없애고 그냥 디폴트로"라고 명시 |
| 인앱 알림을 `NEW_ANSWER` 1종으로 | **014 9-6절 P27** ("질문 알림·답변 알림 **둘 다** 존치") · **9-8절 변경 C의 최대 노출 철학** | 사용자가 "내 질문에 답변이 달렸을때만"이라고 명시 |
| Live 배너 제거 | **014 9-4절 마지막 표** ("기능 6 배너를 대체하지 않고 병행") | 사용자 근거: "어차피 현장 Q&A 목록에 뜨니까" — 그리고 그 전제가 코드로 맞다(4절 흐름 C) |

**014는 "앞으로 알림을 줄이자는 제안이 나오면 그건 사용자 정책을 거스르는 것"이라고 적어 뒀다.** 그 문장은 여전히 유효하다 — **우리가 임의로 줄이지 말라**는 뜻이다. 이번에 줄인 것은 사용자 본인이고, 그래서 이번 요청이 이긴다(우선순위: 사용자 최신 정책 > 과거 일지 > `function.md`).

### 9-4. 원문만으로 갈리지 않아 사용자에게 물은 것 — 무엇을 버렸나

위 9-2절이 **답**이고, 아래는 **그 답이 무엇을 버린 것인가**의 기록이다.

| 쟁점 | 결정 | 버린 쪽과 그 이유 |
|---|---|---|
| **"다이얼로그 알림"이 뭔가** | **기존 인앱 모달**(`notification_banner.dart`의 `AlertDialog`) | 버린 쪽: **브라우저 알림(웹 푸시) 신규 구현.** ⓐ 어제 같은 사용자가 **같은 단어를 이 모달에** 썼다(014 9-8절 변경 B: "다이얼로그 형태로") ⓑ 웹 푸시는 Service Worker + VAPID 키 + `pywebpush` + 권한 요청 플로우 신규 구현이라 **작업량이 자릿수로 다르다** ⓒ 무엇보다 **웹 푸시는 브라우저 권한 팝업을 띄운다** — "토글 없애고 디폴트로"(설정을 줄이자)라는 이번 요청의 취지와 정면으로 모순된다. 새 설정을 하나 만드는 셈이다. ⚠️ 리더가 정리한 요구사항에는 "브라우저 다이얼로그(웹 푸시)"라고 적혀 있었는데, **코드에 그런 기능이 존재하지 않는다.** 그대로 넘겼으면 없는 기능을 새로 만들 뻔했다 |

| **알림 탭을 남기나** | **탭 자체 삭제 (3탭 → 2탭)** | 버린 쪽 ①: **3탭 유지**(권장안, 변경 최소). 버린 쪽 ②: **알림 탭 유지 + 질문 목록에도 표시 추가** — 같은 사실을 두 곳에 그리게 되고 **읽음 상태의 두 번째 사본**이 생긴다(014 6-5절이 피한 것). 사용자가 "알림 탭 자체를 없애라고"로 명시 |
| **`NEW_ANSWER` 만료 기준** | **유지 (질문 등록 + 2시간)** — 묻지 않고 가정 | 버린 쪽: 답변 알림만 자기 수명(알림 `created_at` + 2시간) 또는 만료 없음. 둘 다 **"가리키는 질문이 이미 사라진 알림"**을 만든다 → 탭하면 질문 상세가 없어 관광지 상세로 폴백하는 증상이 상시화된다. 그리고 이번 요청은 알림을 **줄이자는** 방향인데 수명 연장은 반대 방향이다. ⚠️ **사용자에게 묻지 않은 유일한 항목이다** → 11절 |

### 9-6. 같은 날 정정 — Q1=B를 다시 뒤집었다 (`NEW_QUESTION` 알림 복원)

QA(4절)까지 통과한 뒤, 사용자가 실제 화면을 확인하며 정정했다. 정정 원문 그대로:

> "내 말은 질문이 새로 달렸을때도 위와 같이 모달 다이얼로그는 표시해줘야지.. 아예 알림을 없애버리라는 뜻이 아니야. 따로 알림 페이지를 만들어서 사용자에게 목록을 표시하지말라는 뜻이지. 질문 받았을때도 사용자가 지금과 같이 모달 다이얼로그는 받게끔 다시 수정해줘"
>
> (뒤이어) "그리고 웹을 나갔다가 다시 들어오는 사용자 대상으로한 알림도 정상적으로 작동하는지 확인해줘. 질문알림이든 답변 알림이든"

**무엇을 오해했나**: 리더가 Q1(4절)을 "인앱 알림은 답변만 남기고 질문 알림은 **생성 자체를 중단**한다"로 확정했는데, 사용자의 원래 의도는 "**목록 페이지**를 없애라"였다. 이 프로젝트의 알림 아키텍처는 실시간 모달·미읽음 배지·목록이 전부 `GET /api/notifications` 응답 하나에서 갈라진다(`notification_service.dart::_applyList`가 새로 나타난 id를 모달로, `unread_count`를 배지로 씀) — "생성 중단"이라는 한 가지 조치가 그 셋을 한꺼번에 지워버렸다.

**최종 상태(이 일지가 기록하는 마지막 상태)**:
- `NEW_QUESTION` 알림 생성 복원 — `create_question`이 다시 `prepare_new_question()`을 부른다. 대상 판정은 014 원본 그대로 `get_onsite_user_ids()` 재사용, 본문은 014 P28의 고정 문구 "새로운 질문이 도착했습니다"(발췌 없음).
- `active_join()`의 `type == 'NEW_ANSWER'` 필터 제거 — `NEW_QUESTION`·`NEW_ANSWER` 둘 다 다시 목록/미읽음 수/읽음 처리 대상이다. **필터를 다시 걸 곳도 이 함수 한 곳뿐이라는 게 이번 정정에서도 그대로 이득이 됐다.**
- `notification_banner.dart`의 모달이 다시 타입 분기(`NEW_QUESTION` → "새로운 질문이 도착했어요", `NEW_ANSWER` → "내 질문에 답변이 달렸어요")로 문구를 나눈다. 재접속 요약도 "새로운 질문·답변 알림이 N건"으로 되돌아갔다.
- **되돌리지 않은 것**: 알림 탭(2탭 그대로), 알림 설정 토글, `user_notification_settings` 테이블 드롭. `NEW_QUESTION` 수신자는 애초에 그 질문을 올린 사람이 아니라서 "내가 쓴 질문" 탭에는 나타나지 않는다 — 목록 *페이지*가 없다는 원래 결정과 이번 복원이 충돌하지 않는 이유다.

**핵심 교훈**: "목록 페이지가 없다"와 "목록 조회(active_join)에 포함된다"는 다른 층위다. 전자는 화면 층위 결정(내 Q&A에 알림 탭이 있는가), 후자는 데이터 층위(그 데이터를 다이얼로그·배지가 내부적으로 쓰는가)다. 이번 실수는 이 둘을 같은 스위치로 착각한 것이었다.

**QA(3차, 리더가 직접 수행)**: opus 서브에이전트가 세션 한도(rate limit)로 두 차례 중단돼, 코드 변경은 완료된 상태에서 리더가 직접 curl로 재검증했다.
- 경복궁(126508)에 온사이트 3명(`seed_user_01/02/03`) 상태를 만들고 기본 테스트유저로 질문 등록 → 온사이트 3명 전원에게 `NEW_QUESTION` 알림 생성 확인, **질문자 본인은 자기 질문 알림을 받지 않음**(P7 본인 제외 실측)
- `unread_count`가 `NEW_QUESTION`+`NEW_ANSWER` 합산으로 나오는 것을 실측(예: 3건 = NEW_QUESTION 2 + NEW_ANSWER 1)
- `read-all`이 두 타입 모두에 `read_at`을 찍는 것 확인(`updated_count: 3` → 이후 `unread_count: 0`)
- `push-settings` 여전히 404, `pending_questions` 필드 여전히 응답에 포함 — 이번 정정이 015의 다른 결정(토글 제거·배너 제거)을 건드리지 않았음을 재확인
- `dart analyze` 69건 그대로(신규 0건)
- **미검증**: 재접속 요약 다이얼로그·실시간 모달의 실제 화면 렌더링(브라우저 조작 필요) — 코드 검토로는 `notification_service.dart`가 타입 중립적으로 짜여 있어(어디에도 `type` 분기가 없음) 정상 동작할 것으로 판단되지만, 사용자가 앱에서 직접 확인해야 한다.

## 10. 배운 것

1. **"필터는 한 곳에만"의 값어치는 정책이 바뀔 때 드러난다.** 014가 `active_join()` 헬퍼 하나에 판정을 모아 둔 덕에, 이번에 **한 줄 추가로 목록·배지·읽음 처리 세 곳이 동시에** 새 정책을 따랐다. `read-all`은 코드를 한 줄도 안 고쳤는데 맞게 동작했다.

2. **UI를 지우는 것은 표시를 지우는 것이 아니라 "그 화면이 갖고 있던 능력"을 지우는 것이다.** 알림 탭에는 표시만 있는 게 아니라 **읽음 처리라는 조작**이 함께 있었다. 표시만 생각하고 지웠으면 배지가 영원히 안 꺼졌을 것이다.

3. **"안 일어난다"를 증명하려면 그것이 일어날 조건을 만들어야 한다.** 현장 사용자 0명인 상태에서 질문을 올려 알림이 0건인 것은 아무것도 증명하지 않는다. 일부러 4명 상태를 만들어야 한다.

4. **필터 두 개가 같은 결과를 내면 둘 다 검증되지 않은 것이다.** `type` 필터와 만료 필터가 같은 행을 걸러내면, 한쪽만 걸리는 데이터를 일부러 만들어야 한다.

5. **이미 적용된 마이그레이션은 고치지 않고 위에 쌓는다.** 그리고 **`downgrade`를 쓰기 전에 그 리비전이 무엇까지 되돌리는지 읽는다** — `1d90a3fa7298`은 테이블 3개를 한 번에 만들었으므로 되돌리면 알림 기능 전체가 날아갔을 것이다.

6. **같은 사용자가 어제 쓴 단어가 오늘 같은 뜻일 가능성이 가장 높다.** "다이얼로그 알림"을 웹 푸시로 읽었으면 0.3일짜리 작업이 며칠짜리 신규 기능이 됐다. 판정의 근거는 일반적인 용어 뜻이 아니라 **이 프로젝트의 기록**이다.

7. **되돌리기 비용이 비싼 결정만 물어야 한다.** 5건 중 4건을 물었고 1건(`NEW_ANSWER` 만료)은 "유지"로 가정했다 — 유지는 코드 0줄이라 나중에 언제든 바꿀 수 있기 때문이다. 반대로 "테이블 드롭"은 물어야 했다. 지운 행은 복구가 안 된다.

8. **사용자가 어제 한 말을 뒤집는 것도 사용자의 권한이다.** 014가 정책을 못 박아 둔 것은 **우리가 임의로 바꾸지 말라**는 뜻이지, 사용자를 묶는 문장이 아니다. 다만 뒤집힌 사실을 **양쪽 일지에 모두** 적어 둬야 다음 사람이 헷갈리지 않는다.

### 정책적으로 그대로 두기로 한 것

| # | 항목 | 내용 |

| 4 | **과거 `NEW_QUESTION` 89행이 DB에 남아 있다** | DELETE 하지 않았다(014 기록 보존 원칙). 타입 필터로 목록·배지 어디에도 안 나오고, 연결 질문이 2시간 뒤 만료되면 완전히 무의미해진다. **조치 불요** |
| 5 | **`TYPE_NEW_QUESTION` 상수의 소비자가 0명이다** | `app/db/models/notification.py:11`. 이 상수를 참조하는 실행 코드가 없고, 옆 주석("최근 30분 안에 GPS 인증한 관광지에 새 질문이 올라옴")은 **폐기된 동작을 서술**하고 있어 다음 사람이 "이 알림은 아직 살아 있구나"로 오독할 수 있다. **지금 지우면 안 된다** — `schemas.py`의 `NotificationType` Literal과 함께 과거 행 파싱을 떠받치고 있다. → **89행이 자연 소멸한 뒤 `Literal`과 같이 정리할 것** |
| 6 | **`get_onsite_user_ids()`가 다시 호출자 0명이 됐다** | `prepare_new_question` 제거의 직접 결과다. 014 9-2절 Q1이 피하려 했던 바로 그 상태로 돌아갔다. `count_onsite_users()`는 화면에서 계속 쓰이므로 `presence.py` 자체는 죽지 않았다. **새 알림 종류가 생기면 재사용 대상** |
| 7 | **질문 인지 경로가 "현장 Q&A 목록" 하나로 줄었다** | 질문 알림도 없고 Live 배너도 없으므로, 현장 사용자는 **Live 화면을 직접 열어 목록을 봐야만** 새 질문을 안다. **이것은 사용자가 알고 선택한 대가다**(9-4절). 질문자가 답변을 받을 확률이 떨어지면 이 결정부터 다시 볼 것 |
| 8 | **`NEW_ANSWER` 만료 기준을 사용자에게 묻지 않았다** | 답변 알림의 수명은 여전히 **연결된 질문의 등록 시각 + 2시간**이다. 질문 1시간 50분 뒤에 답변이 달리면 그 알림은 **10분만** 보인다. 알림이 2종일 때는 일부 사례였지만, **1종만 남은 지금 이것이 곧 기능 전체의 한계**다. 유지가 코드 0줄이라 되돌리기 싸다는 이유로 가정하고 넘어갔다. → **사용자가 "답변 왔다는 건 오래 보여야 한다"고 생각하면 즉시 불만이 된다. 제대로 고치려면 `GET /questions/{id}`부터 필요하다**(12절) |
| 9 | **`unread_count`(무제한) vs `items`(50건 상한)의 이론적 분기** | 미읽은 답변 알림이 51건을 넘으면 상단 줄 "새 답변이 N건"과 실제 강조된 카드 수가 갈릴 수 있다. **2시간 안에 한 사람이 51건의 답변을 받아야 해서 도달 불가에 가깝다.** 기록만 남긴다 |
| 10 | **로컬 `livespot.db`에 QA 테스트 데이터가 계속 쌓이고 있다** | 이번 QA가 질문 1건 · 답변 1건 · 알림 1건을 추가했고, `128988`의 presence 3행 `last_seen`을 현재 시각으로 갱신했다(014 QA 데이터 위에). **"알림이 이상하다"를 발견하면 이것부터 의심할 것** |
