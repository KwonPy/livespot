## 1. 한 줄 요약

관광지에 **질문이 올라오면 그 자리에 있는 사람들에게**, **내 질문에 답변이 달리면 나에게** 알림을 보내는 기능. 서버가 알림 기록을 남기고, 앱이 **WebSocket으로 "새 알림 있음" 신호를 받아 즉시** 가져와서 **모달 다이얼로그**와 MyPage "내 Q&A → 알림" 탭에 보여준다. 알림은 **연결된 질문이 살아 있는 동안(질문 등록 후 2시간)** 보인다.

> 위 문장은 **2026-09-12 3차 변경 이후의 상태**다. 값과 방식이 세 번 바뀌었다.
> - 최초(2026-09-10 1차): **60초 폴링** + 알림 **자체 30분 만료** + 자동 닫힘 배너
> - 2026-09-10 2차: **7초 폴링** + **질문 기준 2시간 만료**
> - 2026-09-12 3차: **WebSocket 신호 + 7초 폴링 폴백** + **모달 다이얼로그**(자동 닫힘 없음) + **재접속 시 "새 알림 N건" 요약 다이얼로그**
>
> 전부 아래 변경 이력에 남아 있다.

## 2. 왜 만들었는가

### 기능 6(Q&A)이 반쪽이었던 이유

관광지 상세페이지에서 질문을 올릴 수 있게 만들었지만(기능 6), 두 가지가 비어 있었다.

1. **질문을 올려도 현장에 있는 사람이 그 사실을 모른다.** 답변을 받으려면 누군가 우연히 그 관광지 페이지를 열어봐야 했다.
2. **답변이 달려도 질문한 사람이 모른다.** 질문자가 직접 화면을 다시 열어 확인해야 했다.

기능 6에서는 이걸 "답변 대기 질문 배너"(GPS 인증할 때 답변 안 된 질문을 같이 내려주는 것)로 임시 보완했는데, 그건 사용자가 그 화면에 들어와야만 보이는 수동적인 경로였다.

### 이번 기능이 그 자리에 들어간다

`function.md` 7장 구현 순서의 **7단계 "푸시"**가 이번 작업이다. 그리고 [013 일지](013-onsite-user-count.md) 12절이 이미 이렇게 못 박아 뒀다 — "기능 8이 이번 기능의 원래 목적지다. `get_onsite_user_ids()`를 그대로 호출하면 대상 명단이 나온다. **판정 쿼리를 새로 짜지 말 것**." 화면에 뜨는 "현장 3명"과 알림이 가는 사람 수가 어긋나지 않게 하려는 것이다.

### 웹인데 왜 "푸시"인가 — 이번 범위의 전제

사용자의 최종 목표는 이 프로젝트를 **Android 앱으로 만드는 것**이다. 다만 지금은 모바일 전환을 하지 않고, 웹 스택(Flutter 웹 + FastAPI)에서 만들 수 있는 범위로 하되 **나중에 Android로 옮기기 쉬운 모양**으로 설계해 달라는 요청이었다. 원문은 9절에 그대로 남겼다.

그래서 이번 결과물은 "탭이 열려 있을 때 동작하는 인앱 알림"이고, 진짜 푸시(탭을 닫아도 오는 것)는 **꽂을 자리만 파 두고 만들지 않았다.** 그 자리가 어디인지는 9절 마지막에 정리했다.

## 3. 구현한 것

### 백엔드 (FastAPI)

**새 테이블 3개**

| 테이블 | 무엇 | 상태 |
|---|---|---|
| `notifications` | 알림 이벤트 1건 = 1행. `user_id`, `type`, `spot_content_id`, `question_id`, `body`, `created_at`, `read_at` | 실제로 쓰임 |
| `user_notification_settings` | 사용자별 **전역** 알림 ON/OFF 스위치. 기본 ON | 실제로 쓰임 |
| `push_subscriptions` | 나중에 Web Push/FCM을 붙일 때 쓸 구독 정보 | **스키마만. 0행이 정상** |

**새 엔드포인트 5개** (전부 기존 `/api/notifications` 라우터에 얹음 — 새 라우터 파일을 만들지 않았다)

| METHOD | 경로 | 용도 |
|---|---|---|
| GET | `/api/notifications` | 내 알림 목록 + 미읽음 수 (앱이 폴링) |
| POST | `/api/notifications/{id}/read` | 1건 읽음 처리 (멱등) |
| POST | `/api/notifications/read-all` | 전체 읽음 처리 (멱등) |
| GET | `/api/notifications/push-settings` | 전역 스위치 조회 |
| POST | `/api/notifications/push-settings` | 전역 스위치 변경 |
| **WS** | **`/api/notifications/ws`** | **2026-09-12 3차 신설.** "새 알림이 있으니 위 GET을 다시 불러라"는 **빈 신호**만 보낸다 |

**알림 생성 지점 2곳** — `POST /questions`(질문 등록)와 `POST /questions/{id}/answers`(답변 등록)에 알림 생성을 얹었다. **두 API의 응답 스키마는 한 글자도 바뀌지 않았다** — 알림은 부수효과일 뿐이다.

**만료 판정** — "알림이 언제까지 보이는가"는 **연결된 질문이 아직 2시간 안인가**로 판정한다(조회 시점 계산, 아래 6-1절). 남아 있는 수신자 필터는 **본인 제외**와 **전역 스위치 OFF 제외** 둘뿐이다.

> 최초 구현에는 발송 제한 3종(질문당 10명 / 1인 시간당 2건 / 6시간 재발송 금지)과 알림 자체 30분 만료가 있었는데, **2026-09-10 방향 수정에서 전부 폐기**됐다 → 6-2절·변경 이력 참조.

## 4. 동작 흐름

### 흐름 A — 질문이 올라왔을 때 (`NEW_QUESTION`)

```
사용자 C가 경복궁 상세페이지에서 질문 등록
  → POST /api/questions
  → 질문 저장 (여기까지는 기존 기능 6 그대로)
  → [이번에 추가] services/notification.py
       ① get_onsite_user_ids(경복궁)  ← 기능 6이 만들어 둔 함수 그대로 호출
          = 최근 30분 안에 경복궁에서 GPS 인증한 사람들
       ② 질문자 본인(C) 제외
       ③ 전역 스위치를 OFF 한 사람 제외
          (여기서 끝. 인원 상한·시간당 상한·중복 방지는 2026-09-10에 폐기됐다)
  → notifications 테이블에 현장 인원수만큼 INSERT (질문 저장과 같은 트랜잭션)
     본문은 발췌 없이 고정 문구 "새로운 질문이 도착했습니다"

  → [2026-09-12 3차 추가] 수신자마다 ws_manager.notify(user_id)
       그 사용자의 열린 WebSocket에 {"type":"notification"} 빈 신호만 보낸다
       (연결이 없으면 = 지금 접속 안 함 → 아무 일도 안 함. 다음 접속 때 목록으로 받는다)

  ...WS가 붙어 있으면 1초 이내 / 끊겼으면 최대 7초 뒤(폴백 폴링)...

현장 사용자 A의 앱
  → WS 신호를 받았거나(즉시) 폴백 타이머가 돌아서(7초) GET /api/notifications 호출
     ※ 두 경로 모두 같은 API를 부른다 — 그래서 결과가 갈릴 수 없다
  → 서버: 알림에 연결된 "질문"을 INNER JOIN해서
          질문의 created_at + 2시간이 아직 안 지난 것만 골라서 응답
  → Dart의 fromJson이 서버 JSON을 앱 객체로 변환
  → 직전에 없던 미읽음 id가 새로 나타났으면 모달 다이얼로그
     (2026-09-12 2차: 개수 비교 → id 집합 차집합 / 3차: 자동 닫힘 배너 → 모달)
  → "확인하기"를 누름 → 읽음 처리(POST .../read) → 그 질문 상세 시트
```

### 흐름 B — 내 질문에 답변이 달렸을 때 (`NEW_ANSWER`)

```
현장 사용자 D가 C의 질문에 답변 등록
  → POST /api/questions/{id}/answers
  → GPS 재검증 → 답변 저장 → Credit +50 (기존 기능 6 그대로)
  → [이번에 추가] 수신자 = 질문자 C 1명
       (본인 제외 규칙에 자동으로 걸리지 않는다 — 질문자와 답변자가 다르므로)
  → notifications에 1행

C의 앱 → WS 신호(또는 폴백 폴링) → "내 질문에 답변이 달렸어요 — 지금은 한산합니다." 모달

⚠️ 이 답변 알림의 만료 시각도 **알림이 만들어진 시각이 아니라 원래 질문이 등록된 시각 + 2시간**이다.
   질문이 등록된 지 1시간 50분 뒤에 답변이 달리면, 그 답변 알림은 10분만 보이고 사라진다.
```

### 중요: 알림 실패가 질문·답변을 망가뜨리지 않는다

알림을 만드는 코드는 예외를 삼키고 로그만 남긴다. 알림 생성이 실패해도 **질문/답변은 정상 저장되고 응답도 그대로**다. 알림은 부수적인 기능인데 그것 때문에 본 기능이 롤백되면 안 되기 때문이다.

## 6. 핵심 코드 / 개념

### 6-1. 만료를 배치 없이 만드는 법 — 그리고 "무엇의 수명인가"

알림은 언젠가 목록에서 사라져야 한다. 이걸 만드는 방법은 두 가지인데, **하나는 거의 항상 틀렸다.**

- ❌ **틀린 방법**: `is_expired` 같은 상태 컬럼을 두고, 주기적으로 도는 프로그램(배치)이 만료된 행을 찾아 표시한다. → 배치가 1분 늦으면 그 1분 동안 **DB가 거짓말을 한다.** 그리고 이 프로젝트에는 그런 주기 프로그램이 하나도 없어서 새로 만들어야 한다.
- ✅ **쓴 방법**: 컬럼을 아예 두지 않고, **목록을 조회할 때마다** 만료됐는지 비교해서 거른다.

```
notifications 테이블 컬럼:
id, user_id, type, spot_content_id, question_id, body, created_at, read_at
  → expires_at 컬럼이 없다. 응답의 expires_at은 계산해서 만든 값이다.
```

**여기서 한 걸음 더 나간 것이 2026-09-10 방향 수정이다.** "무엇의 수명을 재느냐"가 바뀌었다.

| | 최초 구현 | 지금 |
|---|---|---|
| 기준 | **알림 자신의** `created_at + 30분` | **연결된 질문의** `created_at + 2시간` |
| 방법 | `notifications`만 조회 | `notifications` × `questions` **INNER JOIN** 후 `Question.created_at >= now - 2h` |

왜 바꿨나 — 알림은 질문을 가리키는 **손가락**일 뿐이다. 질문이 아직 살아 있는데(2시간 유효) 손가락이 30분 만에 사라지면, 사용자는 답할 수 있는 질문을 못 보게 된다. 반대로 질문이 죽었는데 알림만 남아 있으면 눌러도 아무것도 없다. **가리키는 대상의 수명에 손가락의 수명을 맞춘 것이다.**

이 판정은 `notification.active_join()` 헬퍼 하나에 모여 있고, **목록 조회 · 미읽음 개수 · 전체 읽음 처리 세 곳이 전부 그 헬퍼를 공유한다.** 그래서 "배지에는 3건인데 목록은 비어 있다" 같은 어긋남이 구조적으로 생길 수 없다.

**⚠️ 앱이 절대 하면 안 되는 것**: `expires_at`을 알림의 `created_at + 2시간`으로 **역산**하는 것. 답변 알림은 질문보다 한참 늦게 생기므로 두 값이 갈라진다. QA 3회차에서 실측한 응답이 그 증거다.

```
NEW_ANSWER 알림
  created_at 2026-09-10T14:05:10.312068   ← 알림이 만들어진 시각
  expires_at 2026-09-10T16:04:42.886875   ← 질문이 등록된 13:59… + 2시간
                                             (알림 시각 + 2h인 16:05:10이 아니다)
```

QA는 "행이 지워진 게 아니라 조회 필터"라는 것도 실측했다. 질문의 `created_at`을 2시간 5분 전으로 조작하니 목록이 4건 → 3건, `unread_count`도 같이 줄었지만 **`notifications` 행 12건은 DB에 그대로 남아 있었다.**

### 6-2. 발송 제한 3종 — 만들었다가 통째로 걷어낸 이야기

최초 구현에는 제한이 3종 있었다. ⓐ 질문 1건당 최대 10명 / ⓑ 1인당 시간당 최대 2건 / ⓒ 같은 (사람·관광지·종류)는 6시간 내 재발송 금지. **셋 다 2026-09-10 방향 수정에서 폐기됐다**(9-6절). 지금 코드에는 `_rate_limited_user_ids`도 `_deduped_user_ids`도 없다.

그래도 이 절을 지우지 않고 남긴다. **여기서 배운 것이 제한을 다시 붙일 때 그대로 필요하기 때문이다.**

당시 어려웠던 것은 제한을 만드는 것이 아니라 **거는 순서**였다.

```
현장에 15명이 있다. 앞 10명은 이미 시간당 2건을 다 받았고, 뒤 5명은 0건이다.

먼저 10명으로 자르면  → 그 10명이 전부 ⓑ에 걸림 → 최종 수신자 0명
                        (받을 수 있었던 뒤 5명이 이유 없이 누락)

나중에 자르면        → ⓑ·ⓒ를 먼저 통과시키면 5명이 남음 → 최종 수신자 5명 ✅
```

그래서 코드는 **개인별 제한(ⓑ·ⓒ)을 먼저 적용하고, 남은 사람 중에서 10명을 잘랐다.** 언젠가 스팸이 문제가 되어 상한을 되살린다면 이 순서부터 다시 세운다.

그리고 제한이 만든 **더 비싼 문제**가 QA 1회차 F1이었다 — ⓑ의 쿼터를 `NEW_QUESTION`과 `NEW_ANSWER`가 공유해서, 붐비는 곳에 있으면 **내 질문에 달린 답변 알림이 조용히 사라졌다.** 제한을 거는 순간 "무엇을 세는가"를 명세에 적어야 한다는 교훈이 여기서 나왔다(10절 7번).

### 6-3. `NotificationSender` — 나중에 갈아 끼울 자리

"알림을 실제로 사용자에게 밀어 보내는 경로"를 **인터페이스**(약속만 정해 둔 빈 껍데기)로 정의하고, 질문/답변 등록 코드는 그 인터페이스만 부른다.

```python
class NotificationSender:
    """구현체 교체가 호출부를 건드리지 않게 한다(P14)."""
    async def deliver(self, db, notifications) -> None:
        raise NotImplementedError

class InAppNotificationSender(NotificationSender):
    """이번 범위의 구현체. 실제로 아무것도 밀어 보내지 않는다.
    전달 수단이 인앱 폴링이라, 테이블에 행을 저장한 것 자체가 곧 전달이다."""
```

지금은 "아무것도 안 하는 구현체"가 들어 있다. 나중에 FCM을 붙일 때 **`deliver`를 구현한 클래스 하나를 추가하면 끝**이고, `questions.py`는 한 줄도 안 바뀐다.

### 6-4. 전역 배너를 겹쳐 그린 이유 (`Stack` vs `Column`)

이 앱에는 모든 화면을 감싸는 껍데기 위젯이 없었다(각 화면이 각자 `Scaffold`를 만든다). 그래서 배너를 어디에 두든 화면 하나에만 뜨는 문제가 있어, `MaterialApp.builder`로 전역 껍데기를 새로 만들었다.

여기서 **배너를 `Column`으로 아래 화면을 밀어내지 않고 `Stack`으로 겹쳤다.** 이유는 이렇다 — 이 프로젝트의 바텀시트들은 `MediaQuery...size.height * 0.8`처럼 **화면 전체 높이 기준**으로 자기 높이를 잡는다. 배너가 화면을 밀어낸 상태에서 시트를 열면 계산이 어긋나 오버플로가 난다. 겹쳐 그리면 **아래 화면의 레이아웃 제약이 한 픽셀도 변하지 않는다.**

### 6-5. 상태를 한 곳에서만 관리 (single source of truth)

배너·MyPage 배지·목록 화면 세 곳이 알림을 보여준다. 이 셋이 각자 서버를 조회하면, 목록 화면에서 읽음 처리를 해도 **MyPage 배지 숫자가 안 줄어드는** 종류의 어긋남이 생긴다.

그래서 셋 다 `NotificationService` 하나의 `items` / `unreadCount`만 읽는다. 목록 화면은 조회를 직접 하지 않고 `_service.refresh()`만 시킨다.

Riverpod을 쓰지 않고 `ChangeNotifier`(Flutter 기본 제공) 싱글턴을 쓴 이유는 9절에 있다.

### 6-6. 폴링 주기 7초가 곧 "지금 접속 중"의 정의다

방향 수정 정책(P23)은 이렇게 말한다 — 질문이 올라오면 **"현재 접속 중인"** 현장 사용자에게 실시간으로 보이고, 접속 중이 아니었던 사람은 **다시 들어왔을 때** 밀린 알림으로 받는다.

여기서 "접속 중"을 어떻게 아느냐가 문제인데, **별도의 online 컬럼이나 소켓 연결을 만들지 않았다.** 폴링 그 자체가 정의다.

- 탭이 열려 있다 = 7초마다 물어본다 = **다음 7초 안에 뜬다** (= 접속 중)
- 탭이 닫혀 있다 = 아무도 안 물어본다 = 다시 열 때 밀린 것을 한꺼번에 받는다

즉 **"접속 중"이라는 상태를 저장하는 대신, 물어보러 오는 행위 자체를 접속의 증거로 삼았다.** 저장하는 상태가 하나도 늘지 않는다는 것이 이 방식의 이점이다(끊긴 소켓을 정리하는 코드도, 유령 online 행도 없다).

7초라는 숫자를 그냥 줄일 수 있었던 이유(QA 3회차 확인):
- 서버에 요청 빈도를 막는 장치(rate limit)가 **없다** → 429를 맞을 일이 없다
- 관광지 이름 조회가 부르는 TourAPI는 **600초 캐시**가 흡수한다 → 주기를 줄여도 외부 호출량이 안 늘어난다
- 응답이 7ms다 → 7초 주기에 비해 세 자릿수 여유
- 요청이 겹쳐도 `_inFlight`가 진행 중인 요청을 공유해 **쌓이지 않는다**

**단, 이 근거들은 "지금 이 구조에서" 성립한다.** 캐시를 걷어내거나 주기를 더 줄이면 셋 다 다시 봐야 한다 — QA F5가 정확히 이 지점을 지적했다(8절 문제 6).

> **⚠️ 2026-09-12 3차 변경으로 이 절의 전제가 바뀌었다.** 이제 평상시에는 폴링이 **돌지 않는다** — WebSocket이 붙어 있으면 폴링 타이머를 끈다. 그래서 "접속 중"의 정의도 **"7초마다 물어보러 온다"에서 "WebSocket 연결이 살아 있다"로** 옮겨 갔다(연결이 끊기면 다시 7초 폴링이 그 역할을 대신한다). 위 7초 안전성 근거들은 **폴백이 돌 때만** 적용된다. 6-7절이 왜 그렇게 바꿨는지를 설명한다.

### 6-7. WebSocket으로 "알림 내용"이 아니라 **"신호"만 보내는 이유** (2026-09-12 3차)

WebSocket을 붙이면 보통 **알림 내용 자체를 밀어 보내고** 싶어진다. 그렇게 하지 않았다.

```
서버가 보내는 것 전부:   {"type": "notification"}
                          ↑ 누구 것인지, 무슨 알림인지, 몇 건인지 아무것도 없다

앱이 이 신호를 받으면 →  기존 GET /api/notifications 를 그냥 다시 부른다
                        (= 폴링이 7초를 기다리지 않고 지금 당장 한 번 도는 것과 같다)
```

왜 이렇게 했나 — **판정 로직을 두 곳에 두지 않기 위해서다.** "이 알림이 아직 유효한가"는 `active_join()` 하나가 답하고, 그걸 **목록 조회 · 미읽음 개수 · 전체 읽음 처리** 세 곳이 이미 공유한다(6-1절). 만약 WebSocket이 알림 내용을 직접 실어 보내면, **만료 판정과 수신자 판정이 네 번째 사본으로 늘어난다.** 그 사본은 목록 조회와 조금씩 어긋나기 시작하고, 그 어긋남은 "배너에는 떴는데 목록에는 없다" 같은 형태로만 드러나서 테스트로 잡히지 않는다.

즉 **WebSocket을 "전달 수단"이 아니라 "폴링의 방아쇠"로만 쓴 것이다.** 덕분에 ⓐ 서버의 알림 응답 스키마가 **한 글자도 안 바뀌었고** ⓑ WS가 끊겨도 폴백 폴링이 **똑같은 결과**를 만들고(두 경로가 같은 API를 부르므로) ⓒ 나중에 진짜 푸시를 붙여도 이 구조가 그대로 남는다.

**대가**: 신호 1건마다 HTTP 요청이 1번 추가로 발생한다. 알림 내용을 실어 보냈다면 0번이다. 지금 규모(사용자 수 명)에서는 이 비용이 위 이점 셋보다 훨씬 싸다.

## 7. 사용한 기술

| 기술 | 어디에 |
|---|---|
| `ChangeNotifier` + `ListenableBuilder` | Flutter 기본 제공 상태 알림 도구. 새 패키지 없이 배너·배지·목록을 한 상태에 묶었다 |
| `Timer.periodic` (**7초**) | 인앱 폴링. `dispose`에서 반드시 `cancel` — 웹에서는 안 지우면 조용히 샌다 |
| `MaterialApp.builder` + `GlobalKey<NavigatorState>` | 전역 배너 계층. 배너는 Navigator 바깥이라 `Navigator.of(context)`로 라우터를 못 찾는다 → `rootNavigatorKey` 필요 |
| `AppLifecycleState.resumed` | 앱(탭)이 다시 활성화될 때 즉시 재조회. 다음 주기를 기다리지 않게 |
| SQLAlchemy **INNER JOIN** (`notifications` × `questions`) | 유효 알림 판정. `active_join()` 헬퍼 하나를 목록·미읽음 수·전체읽음이 공유 |
| Alembic 리비전 (`1d90a3fa7298`) | 테이블 3개 생성. 로컬 SQLite 적용 완료, Railway Postgres는 배포 시 자동 적용 |
| `X-Test-User-Id` 헤더 (`TEST_MODE`) | 로그인이 없어서 다인 시나리오를 만들 수 있는 유일한 수단. QA와 스모크가 전부 이걸로 돌았다 |
| SQLAlchemy 비동기 `select` + `func.count` | 미읽음 개수 판정 쿼리 (최초 구현에서는 발송 제한 판정에도 썼다) |

**새로 추가한 외부 라이브러리는 백엔드·프론트 모두 0개다.** → **2026-09-12 3차에 프론트 1개가 늘었다.**

## 8. 문제와 해결

### 문제 1 — 팀 병렬 실행 도구가 이 세션에 없었다 (하네스 문제)

- **문제**: `livespot-feature` 스킬은 "명세 판정 → 백엔드·프론트 **병렬** 구현 → 경계면 검증"을 의도한 오케스트레이터인데, 이번 세션에는 팀을 만들고 서로 통신시키는 도구(`TeamCreate`/`TaskCreate` 계열)가 없었다.
- **원인**: 하네스가 가정한 도구와 실제 세션에 붙은 도구가 달랐다.
- **해결**: **순차 실행**으로 진행했다 — `spec-arbiter` → (사용자에게 Q1~Q4 확인) → `backend-builder` 완료 → **계약서(`02_backend_contract.md`) 확정** → `flutter-builder` 시작 → `contract-qa`.
- **배운 점**: 병렬성은 못 얻었지만 **"스키마가 확정된 뒤에 프론트가 시작한다"는 순서 자체는 지켜졌고, 이 프로젝트의 경계면 버그를 막은 건 병렬성이 아니라 그 순서였다.** 실제로 QA 1회차 경계면 결함이 0건이다. 병렬 실행은 시간을 줄이는 최적화이지 정합성의 조건이 아니다 — 도구가 없으면 순차로 내려가되 **"계약서 확정 → 프론트 착수" 관문은 절대 건너뛰지 않는다.**

### 문제 2 — 새로 만든 조회 메서드만 에러 메시지를 안 꺼냈다 (QA F2)

- **문제**: 알림 조회가 500으로 실패하면 화면에 `DioException [bad response]: This exception was thrown because...`라는 영문 기술 문자열이 빨간 글씨로 그대로 떴다.
- **원인**: 같은 파일의 형제 메서드 3개는 전부 `on DioException catch (e) { throw Exception(_extractErrorMessage(e)); }`로 감싸 서버의 `detail` 원문을 꺼내는데, **새로 추가한 `fetchNotifications` / `fetchPushSettings` 2개에만 그 `try/catch`가 없었다.** 화면은 `'Exception: '` 접두사만 벗기는데 `DioException.toString()`은 그 접두사로 시작하지 않아 벗겨지지 않았다.
- **해결**: 두 메서드를 형제와 같은 모양으로 맞췄다(리더가 직접 수정). 서버가 "정직하게 500을 던진다"는 설계 의도가 화면에서 무너지던 지점이었다.
- **배운 점**: **같은 파일에 형제 메서드가 있으면 새 메서드는 그 모양을 그대로 따라야 한다.** 규칙으로 넣은 곳 → `.claude/skills/livespot-contract/references/bug-patterns.md` **9절 신규**("새로 추가한 형제 메서드만 모양이 다름").

### 문제 3 — 새로고침하면 잠깐 다른 사용자의 알림이 뜬다 (QA F4)

- **문제**: `seed_user_04`로 시연하다 브라우저를 새로고침하면, MyPage에 들어가기 전까지 배지와 배너가 기본 `test_user` 기준이었다.
- **원인**: 테스트유저 ID를 저장소에서 복원하는 코드가 **MyPage 화면의 `initState`에만** 있었다. 그런데 알림 폴링은 그보다 훨씬 먼저 앱 루트에서 시작한다. Credit 통계도 같은 구조였다.
- **해결**: `main.dart`의 `runApp` 전에 복원하도록 3줄 추가. 알림뿐 아니라 Credit·북마크의 같은 증상까지 함께 사라졌다.
- **배운 점**: **"누구로서 요청하는가"를 정하는 전역 상태는 특정 화면이 아니라 앱 부팅 시점에 복원해야 한다.** 규칙으로 넣은 곳 → `bug-patterns.md` **5-3 신규**.

### 문제 4 — 폴링 중복 방지를 잘못 만들면 실패가 "알림 없음"으로 둔갑한다

- **문제**: 초기 구현은 "이미 폴링 중이면 건너뛴다"였다. 그러면 목록 화면이 부른 새로고침이 **아무것도 안 하고 즉시 성공으로 끝나서**, 그 사이 돌던 폴링이 실패했을 때 화면이 **빈 목록을 그린다.**
- **원인**: 이 프로젝트에서 가장 비쌌던 버그 유형(`bug-patterns.md` 1-1 "에러를 빈 상태로 뭉갬")과 정확히 같은 형태다.
- **해결**: 진행 중인 요청의 Future를 **공유해서 돌려주도록** 고쳤다. 새로고침을 부른 쪽이 그 요청의 성공/실패를 그대로 받는다.
- **배운 점**: **중복 요청 방지를 "건너뛰기"로 구현하면 실패가 성공으로 둔갑한다. 진행 중인 Future를 공유하라.** 규칙으로 넣은 곳 → `bug-patterns.md` **1-5 신규**.

### 문제 5 — 서버 `limit` 파라미터의 타입 표기가 실제와 달랐다 (QA F3)

- **문제**: `limit: int = Query(default=None, ...)` — 타입은 `int`인데 기본값이 `None`.
- **원인**: 단순 표기 실수. 앱이 `limit`을 보내지 않아 런타임 증상은 없었다.
- **해결**: `Optional[int]`로 정정. 지금은 증상이 없지만 나중에 OpenAPI로 클라이언트를 생성하거나 타입 체커를 붙이면 이 자리에서 어긋난다.
- **배운 점**: 증상이 없는 타입 표기 오류도 **문서(OpenAPI)를 통해 거짓말을 퍼뜨린다.** 기존 규칙(`bug-patterns.md` 2-2 Optional 짝맞추기)의 서버 쪽 변형이라 새 항목을 추가하지 않았다.

### 문제 6 — 7초라는 결정 옆에 **사실이 아닌 근거**가 적혀 있었다 (QA 3회차 F5)

- **문제**: 폴링 주기를 60초 → 7초로 줄이면서 `constants.dart`에 이렇게 적었다 — *"`GET /api/notifications`는 TourAPI를 부르지 않는 경량 엔드포인트라 이 정도 주기는 부담이 없다."* **그런데 그 엔드포인트는 매 호출 TourAPI를 부른다**(관광지 이름을 채우는 `resolve_spot_names`).
- **원인**: 실제로 주기를 떠받치고 있던 것은 "안 부른다"가 아니라 **`tour_api.py`의 600초 TTL 캐시**였다. 캐시 미스는 관광지당 10분에 1회라 폴링 주기와 무관하다. 서버 쪽 주석도 같은 오해를 강화하고 있었다.
- **해결(상태)**: **아직 안 고쳤다.** 런타임 증상이 없어 이번 범위에서 조치하지 않고 12절 다음 단계로 넘겼다. **7초라는 결정 자체는 옳다** — QA가 rate-limit 부재·캐시·응답 7ms·`_inFlight` 가드로 안전을 확인했다.
- **왜 그래도 결함인가**: 이 주석은 다음 사람에게 "이 엔드포인트에는 외부 API 비용이 없다"고 단언한다. 그 사람이 주기를 3초로 더 줄이거나 캐시 없는 경로로 이름 조회를 바꾸는 순간 TourAPI 429를 맞는데, **잘못된 근거가 정확히 그 방향으로 안내한다.**
- **배운 점**: **성능 상수의 근거 주석은 "무엇이 이 값을 떠받치는가"를 이름으로 적어야 한다.** 규칙으로 넣은 곳 → `bug-patterns.md` **5-4 신규**("성능 상수의 근거 주석이 실제 코드 경로와 다르다").

### 문제 7 — 두 상수가 서로 관계를 갖게 됐는데 아무 데도 안 적혀 있다 (QA 3회차 F6)

- **문제**: Dio의 `receiveTimeout`이 8초, 폴링 주기가 7초. 60초였을 때는 7배 차이라 서로 무관했는데, **7초가 되면서 타임아웃이 주기보다 길어졌다** — 응답이 느리면 다음 주기가 이전 요청이 끝나기 전에 도착한다.
- **원인**: 한쪽 값만 바꿨고, 그 변경이 다른 파일의 값과 새로운 관계를 만든다는 것을 두 파일 어디에도 남기지 않았다.
- **해결(상태)**: **아직 안 고쳤다.** 지금은 `NotificationService._inFlight`가 진행 중인 요청을 공유해서 요청이 쌓이지 않으므로 증상이 없다. 주석 1줄 보강을 12절로 넘겼다.
- **배운 점**: **상수를 바꿀 때는 그 값이 다른 상수와 대소 관계를 갖게 되는지 확인하고, 생겼으면 양쪽 모두에 적는다.** 한쪽에만 적으면 반대쪽을 고치는 사람이 못 본다. 규칙으로 넣은 곳 → `bug-patterns.md` **5-4**(위와 같은 절의 마지막 문단).

### 문제 8 — 정책이 폐기되면 "필드를 지우는 작업"이 양쪽에 동시에 생긴다

- **문제**: 방향 수정으로 응답 필드 `ttl_minutes`가 사라졌다. 이 필드 하나가 살던 곳이 **다섯 군데**였다 — 백엔드 Pydantic 스키마 / 라우터 생성자 인자 / `config.py` 설정값 / Dart 모델 필드+`fromJson` / 그 값을 쓰던 화면 푸터. 한 곳만 남겨도 앱이 깨지거나(non-null 읽기) 죽은 코드가 남는다.
- **원인**: 필드를 **추가**할 때는 빠뜨리면 컴파일이 깨져서 알아채지만, **삭제**는 남겨둬도 안 깨진다.
- **해결**: 삭제 목록을 먼저 적고 진행했고, QA 3회차가 삭제된 심볼 11개를 저장소 전수 grep해서 **실행되는 참조 0건**(히트는 전부 주석)을 확인했다. `ttl_minutes`도 다섯 곳에서 모두 사라진 것을 확인했다.
- **딸려온 것**: 값이 사라지면 그 값으로 그리던 UI도 사라져야 한다. 전역 푸터 한 줄("30분이 지나면 사라져요")은 **모든 알림의 수명이 같았기 때문에** 가능했던 문장이다. 만료 기준이 질문별로 갈리는 순간 그 한 줄은 화면이 하는 거짓말이 되므로, 남은 시간을 **항목별 캡션**(`_remainingLabel`)으로 내렸다.
- **배운 점**: **이름·타입이 그대로인데 의미만 바뀐 필드가 가장 위험하다.** `expires_at`은 이름도 타입도 nullable 여부도 안 바뀌었는데 계산 기준만 바뀌었다 — `contract_diff.py`도 curl 키 대조도 이런 변화는 **원리적으로 못 잡는다.** 그래서 QA는 ① 앱에 역산 코드가 있는지 grep하고 ② 서버 값과 역산 값이 실제로 갈라지는 응답을 만들어 실측했다. 규칙으로 넣은 곳 → `bug-patterns.md` **10 신규 절**("응답 필드를 삭제할 때 한쪽만 지움" + "의미만 바뀌는 경우가 더 위험하다").

### 문제 9 — WebSocket 핸드셰이크가 **항상 403**으로 거부됐다 (2026-09-12 3차)

- **문제**: 서버도 켜져 있고 엔드포인트도 등록됐는데, 브라우저가 `/api/notifications/ws`에 붙으려 하면 **매번 HTTP 403**이 돌아왔다. 코드에는 권한 검사가 한 줄도 없었다.
- **원인**: 권한 문제가 전혀 아니었다. **`uvicorn[standard]==0.30.0`이 딸려 받는 `websockets` 라이브러리가 15.x로 올라가 있었고, 이 버전의 서버 API가 uvicorn 0.30이 기대하는 모양과 달랐다.** 라이브러리 안쪽에서 핸드셰이크가 실패하면서 **바깥에서는 403으로만 보였다.**
- **해결**: `requirements.txt`에 **`websockets==13.1`을 명시적으로 고정**했다. uvicorn 자체는 올리지 않았다 — 그쪽을 올리면 이 기능과 무관한 기동 경로까지 한꺼번에 바뀐다.
- **배운 점**: **`pkg[standard]` 같은 "묶음 설치"는 버전을 고정한 것이 아니다.** 본체(`uvicorn==0.30.0`)만 핀을 박아 두면 딸려오는 하위 의존성은 설치 시점에 따라 제멋대로 올라가고, 그 결과가 **엉뚱한 HTTP 상태코드로 위장해서** 나타난다. 403을 보고 권한 코드를 뒤지면 하루를 날린다 — **"권한 검사를 한 적이 없는데 403이 온다"면 그 403은 내 코드가 만든 것이 아니다.**

### 문제 10 — 서버를 껐는데 **예전 코드가 계속 응답했다** (2026-09-12 3차, Windows)

- **문제**: WebSocket 엔드포인트를 고치고 백엔드를 재시작했는데도 **계속 예전 코드로 응답**했다. `--reload`를 끈 상태였고, 포트를 잡고 있던 프로세스도 분명히 죽였다.
- **원인**: **`uvicorn --reload`는 프로세스가 하나가 아니다.** 부모(리로더)가 `multiprocessing.spawn`으로 **자식 워커**를 띄우고, **실제로 요청을 처리하는 코드는 자식에 있다.** `Get-NetTCPConnection`으로 찾은 PID는 부모라서, 그것만 죽이면 자식 워커가 **고아 프로세스로 살아남아 계속 예전 코드로 답한다.** 서버가 안 죽은 게 아니라 **덜 죽은 것**이었다.
- **해결**: 자식까지 찾아서 함께 종료한다.

  ```powershell
  $parent = (Get-NetTCPConnection -LocalPort 8000 -State Listen).OwningProcess
  Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
    Where-Object { $_.CommandLine -like "*parent_pid=$parent*" }   # ← 자식 워커
  # 자식 → 부모 순으로 taskkill /F
  ```

  자식 워커는 커맨드라인에 **`parent_pid=<부모 PID>`** 가 박혀 있어서 이것으로 식별한다.
- **배운 점**: **"재시작했는데 코드가 반영 안 된다"는 캐시나 빌드 문제이기 전에 프로세스 문제일 수 있다.** 그리고 `/health`가 200을 주는 것은 서버가 **새 코드로** 떠 있다는 증거가 아니다 — 재시작 확인은 반드시 **바뀐 코드가 실제로 응답에 나타나는지**로 해야 한다. 규칙으로 넣은 곳 → **`.claude/skills/livespot-run/SKILL.md` "포트가 이미 사용 중일 때" 절에 「`--reload`로 띄운 uvicorn은 자식 워커까지 죽여야 한다」 하위 절 신설** (탐지·종료·확인 명령 3단계를 그대로 적어 뒀다).

## 9. 의사결정

### 9-1. 사용자가 준 정책 (원문)

기능 요청 시점:

> "이제 질문 push 기능 구현할건데, 내 최종적인 목표는 웹이 아니라 이거를 android 앱으로 만드는거야. 그거 감안해서 push 기능 구현해줘. 우선 지금은 모바일 전환은 하지는 않을건데, 웹에서 구현할 수 있는 기능을 추가를 해줘."

이 한 문단이 이번 작업의 범위를 전부 결정했다. **"지금은 웹" + "나중에 Android" + "이식을 감안한 설계"** 세 가지다.

### 9-2. 착수 전 확정한 4가지 (사용자 확답)

`spec-arbiter`가 `function.md` 기능 8, 과거 일지, 실제 코드를 대조해 **"구현자가 임의로 고르면 되돌리기 비싼" 미결정 4건**을 뽑았고, 리더가 사용자에게 직접 물었다. **네 건 모두 사용자가 권장안을 그대로 선택했다.**

| # | 질문 | 사용자 확정 | 무엇을 버렸나 |
|---|---|---|---|
| **Q1** | 무슨 일이 생겼을 때 누구에게 보내나 | **C — 둘 다.** `type` 컬럼(`NEW_QUESTION`/`NEW_ANSWER`)으로 구분해 같은 테이블·같은 경로·같은 화면 공유 | A만(질문→현장사용자) 고르면 요청 문구 "질문 **답변** 알림"과 어긋난다. B만(답변→질문자) 고르면 [013]이 기능 8을 위해 미리 만들어 둔 `get_onsite_user_ids()`가 **계속 호출자 0명으로 남는다.** 둘의 차이는 트리거 한 줄과 수신자 수뿐이라 구조를 공유할 수 있었다 |
| **Q2** | 어떤 방식으로 전달하나 | **C — 인앱 폴링 + 이식용 추상화.** `NotificationSender` 인터페이스와 채널 중립 `push_subscriptions` 스키마만 미리 파 두고, 실제 Web Push는 만들지 않음 | B(진짜 Web Push)는 탭을 닫아도 알림이 온다는 큰 이득이 있지만 — ① `function.md` 스스로 "웹 푸시는 도달률이 낮다, **후순위**"라고 적었고 ② Flutter Web은 `flutter run -d chrome` 개발 모드에서 Service Worker가 등록되지 않아 **개발 중에 확인할 방법이 없다.** A(인앱만)를 안 고른 것은, 이식 자리를 파 두는 비용이 0.3일뿐이라 요청의 "Android 감안"과 직결되기 때문 |
| **Q3** | 알림을 받으려면 먼저 켜야 하나 | **B — GPS 인증한 사람은 자동 대상, 끄고 싶으면 MyPage에서 전역 OFF.** 기본 ON **→ 2026-09-13 [015](015-notification-policy-reduction.md)로 무효.** 사용자 요청으로 전역 OFF 토글을 제거하고 `user_notification_settings` 테이블까지 드롭했다. 지금은 "끌 수 없다"가 맞는 동작이다 | A(기존 관광지별 스위치 재사용)는 그 스위치의 기본값이 **False**라 **만들어 놓고 아무 일도 안 일어나는 상태**가 된다. 게다가 기능 3의 근접 알림과 스위치를 공유하게 되어 하나만 끄고 싶어도 같이 꺼진다. C(스위치 없음)는 `function.md` 기능 12의 MyPage 명세와 충돌. B는 죽어 있던 메뉴 하나를 살렸다 |
| **Q4** | 목록 화면과 읽음 처리를 이번에 만드나 | **B — 목록 화면 + 서버 읽음 처리** | A(배너만, 읽음은 기기 로컬 저장)는 기기를 바꾸면 본 알림이 다시 뜬다. 무엇보다 Q1에서 "답변 도착 알림"을 만드는데 **"눌러서 그 질문으로 이동"이 없으면 알림이 반쪽**이 된다. C(헤더 벨 아이콘)는 전역 셸이 없어 **모든 화면의 AppBar를 각각 손대야 해서** 이득 대비 회귀 위험이 컸다 |

### 9-3. QA 이후 사용자가 확정한 것 — F1 "그대로 둔다" (→ 이후 무효)

> **이 절의 결론은 2026-09-10 방향 수정으로 무효가 됐다.** P26이 발송 상한 3종을 전부 폐기해서 F1의 원인 코드 자체가 사라졌다(9-6절). 당시 판단의 기록으로 남겨 둔다 — **상한을 다시 도입한다면 이 문제가 그대로 되살아난다.**

QA가 실측으로 이런 상황을 재현했다.

> 어떤 사용자가 붐비는 관광지에 있어 `NEW_QUESTION` 알림 2건을 먼저 받으면, 시간당 상한 2건을 다 쓴 상태가 된다. 그 뒤에 **본인이 올린 질문에 답변이 달려도 `NEW_ANSWER` 알림이 오지 않는다.**

이 기능의 이름값("질문 **답변** 알림")과 우선순위가 뒤집혀 있어서 리더가 사용자에게 다시 물었고, **사용자는 "그대로 둔다"로 확정했다.**

- **왜 결함이 아닌가**: 확정 정책 P5ⓑ가 "1인당 시간당 최대 2회"라고만 적었고 종류를 구분하지 않았으므로 **구현은 명세대로다.** 백엔드의 버그가 아니라 명세에 빠져 있던 설계 결정이다.
- **버린 선택지**: ① 상한을 종류별로 분리 ② `NEW_ANSWER`를 상한에서 면제. 둘 다 코드 수정이 필요하고, 면제 쪽은 "한 질문에 답변이 연달아 달리면 알림이 그만큼 쌓이는" 새 문제를 만든다.
- **남기는 이유**: 이 동작을 모르면 **"왜 답변 알림이 안 왔지"를 버그로 오인**하게 된다. 그래서 11절에도 한계로 명시했다.

### 9-5. Android 이식 시 무엇을 재사용하고 무엇을 교체하나

이번 작업의 요청 자체가 "Android 전환을 감안"이었으므로, **이식 경로의 핵심 3곳**을 명시해 둔다.

| 자산 | 이식 때 | 왜 여기가 핵심인가 |
|---|---|---|
| **`NotificationSender` 인터페이스** (`livespot_backend/app/services/notification.py`) | **교체.** `deliver()`를 구현한 클래스(FCM용/Web Push용)를 하나 추가하고 `get_sender()`가 그걸 돌려주게 한다 | `api/questions.py`가 아는 것은 이 인터페이스뿐이다. **질문/답변 등록 코드는 한 줄도 안 바뀐다** |
| **`push_subscriptions` 테이블** (채널 중립 스키마) | **그대로 재사용.** `platform`("web"/"android"/"ios"), `endpoint`(Web Push URL 또는 FCM 등록 토큰), `keys_json` | 지금 0행이지만 컬럼 모양을 미리 못 박아 뒀다. 그때 테이블을 새로 만들면 **마이그레이션이 배포와 얽힌다** |
| **`notification_service.dart`** | **교체.** 파일 상단 주석에 무엇을 바꾸는지 적어 뒀다 — `Timer.periodic` → 푸시 수신 콜백 구독, `_poll`의 전체 재조회 → 푸시 페이로드 1건을 앞에 삽입. `refresh()`는 그대로 남는다(앱 복귀 시 밀린 알림 동기화에 계속 필요) | 화면(배너·목록·배지)은 전부 이 클래스의 `items`/`unreadCount`만 보므로 **위젯 코드는 한 줄도 안 바뀐다** |

**그대로 재사용되는 것**: `notifications` 테이블, 5개 엔드포인트, 만료 판정, 읽음 처리, 전역 스위치, 알림 목록 화면 — 즉 **데이터 모델과 판정 로직 전부**다. 새로 만들 것은 "실제로 밀어 보내는 구현체" 하나뿐이다.

> 이 표의 전제(“Android 이식”)는 **2026-09-10 방향 수정으로 우선순위가 내려갔다** — 최종 출품물이 모바일 웹서비스로 확정됐다(아래 9-6절 P21). 이식 가능성 자체는 유지되므로 표는 그대로 둔다.

### 9-8. 3차 후속 변경 — WebSocket 전환 · 모달 다이얼로그 · 재접속 요약 (2026-09-12)

9-7절 직후에 이어진 변경 3건이다. **셋 다 사용자가 채팅으로 정책을 직접 준 것**이고, 원문을 아래에 그대로 남긴다.

> **주의**: 이 절의 변경 A는 **9-7절 결정 표의 첫 줄("전달 방식을 SSE/WebSocket으로 바꿀까 → 폴링 유지")을 뒤집은 것**이다. 우리가 판단을 번복한 것이 아니라 **사용자가 실시간성을 직접 요구했다.** 당시 우리가 폴링 유지를 택한 근거(P-K 설계 자산, 다중 인스턴스 위험, 재연결 과제)는 지금도 유효하며, 어떻게 그 셋을 감당했는지는 아래에 적었다.

#### 변경 A — 실시간 전달을 폴링에서 WebSocket으로

**사용자가 준 정책 (원문)**

> "그리고 지금 어쨌든 모든 알림 대상은 웹에 접속한 사람들 대상이니까, 질문/답변 그리고 gps 인증 관련 인앱 알림은 모두 폴링방식에서 웹소켓 방식으로 바꾸자. 그래야 실시간성이 살아날 것 같아"

리더가 되물어 확정한 것 2가지:

| 리더의 질문 | 사용자 답 |
|---|---|
| "웹소켓 적용 범위: 질문/답변 알림만 바꿀까요, 아니면 GPS 인증(현재 위치 확인 3분 타이머 + '답변 대기중 질문' 배너)까지 포함해야 하나요?" | **"질문/답변 알림만 (권장)"** |
| "연결 실패/끊김 시 대비: WebSocket 연결이 끊기면 폴링으로 자동 폴백할까요, 아니면 WS만 쓰고 재연결만 시도할까요?" | **"WS + 폴링 폴백 (권장)"** |

**⚠️ GPS 인증이 왜 범위에서 빠졌나 — 이게 이 절에서 가장 중요한 판정이다.**

원문은 "gps 인증 관련 인앱 알림"도 WebSocket으로 바꾸자고 했다. 그런데 리더가 실제 코드(`proximity_alert_service.dart`, `home_screen.dart`의 60초 타이머)를 조사한 결과 **바꿀 대상 자체가 없었다.**

```
질문/답변 알림:  서버가 "누구에게 보낼지" 판정하고 알림 행을 만든다
                 → 서버발 이벤트가 존재한다 → 밀어줄 것이 있다 → WS로 바꿀 수 있다

GPS 근접 확인:   서버가 아무것도 판정하지 않는다. 앱이 60초마다 자기 위치를 보고
                 "지금 내가 관광지 근처인가?"를 **스스로 자문**한다
                 → 서버발 이벤트가 없다 → 밀어줄 것이 없다 → WS로 바꿀 대상이 없다
```

즉 GPS 쪽의 60초 타이머는 "서버에게 물어보는 폴링"이 아니라 **"자기 자신에게 물어보는 루프"** 다. 이름이 같은 "폴링"이라 한 덩어리로 보였을 뿐, 성질이 전혀 다르다. 리더가 이 사실을 사용자에게 설명했고 범위에서 제외됐다.

**이 판정을 여기 남기는 이유**: 이걸 안 적어 두면 다음에 또 "GPS 알림도 웹소켓으로 바꾸자"가 나오고, 그때 다시 같은 조사를 처음부터 한다. **"서버가 판정해서 밀어주는 것"과 "클라이언트가 스스로 확인하는 것"은 겉보기 주기 동작이 같아도 다른 문제다.**

**우리가 판단해 확정한 것**

| 쟁점 | 결정 | 왜 다른 쪽을 버렸나 |
|---|---|---|
| WS로 **무엇을** 보낼까 | **내용 없는 빈 신호 `{"type":"notification"}` 만.** 앱은 이 신호를 받으면 기존 `GET /api/notifications`를 다시 부른다 | 알림 내용을 실어 보내면 만료·수신자 판정이 `active_join()` 말고 **두 번째 사본**으로 늘어난다. 그 사본은 목록 조회와 조금씩 어긋나고, "배너엔 떴는데 목록엔 없다" 형태로만 드러나 테스트로 안 잡힌다. 대가는 신호당 HTTP 1회 추가인데 이 규모에서는 훨씬 싸다 (6-7절) |
| 사용자 식별을 **헤더로 할까 쿼리로 할까** | **쿼리 파라미터 `test_user_id`** | 나머지 API는 전부 `X-Test-User-Id` **헤더**를 쓰는데 여기만 다르다. 이유는 취향이 아니라 제약이다 — **브라우저의 WebSocket API는 핸드셰이크에 커스텀 헤더를 실을 수 없다.** 헤더를 고집하면 브라우저에서 아예 연결이 안 된다 |
| 9-7절이 경고한 **다중 인스턴스 위험**은 어떻게 하나 | **단일 인스턴스 전제를 받아들이고, 그 전제를 코드에 크게 적어 뒀다** | 지금 해결하려면 Redis pub/sub이 필요하고 그건 인프라가 하나 느는 일이다. 대신 `ws_manager.py` 모듈 docstring 맨 위에 "인스턴스가 늘면 **에러 없이 조용히** 알림이 안 가는 인스턴스가 생긴다"를 명시했다 — **이 종류의 고장은 로그에 아무것도 안 남기 때문에, 적어 두지 않으면 원인 추적이 불가능해진다** |
| 기존 폴링을 **지울까** | **남긴다. WS가 붙어 있으면 타이머를 끄고, 끊기면 즉시 다시 켠다** | 사용자가 "WS + 폴링 폴백"을 직접 택했다. 그리고 두 경로가 **같은 API를 부르므로 결과가 갈릴 수 없다**(6-7절) — 폴백이 "덜 좋은 두 번째 구현"이 아니라 **같은 구현의 느린 버전**이라는 점이 이 설계의 핵심이다 |

**⚠️ 상수 하나의 의미가 바뀌었다 — 다음에 이걸 보는 사람을 위해**

`AppConstants.notificationPollIntervalSeconds = 7`은 **이름이 그대로인데 뜻이 바뀌었다.**

| | 2026-09-10 ~ 3차 이전 | 지금 |
|---|---|---|
| 뜻 | **기본** 폴링 주기. 평상시 7초마다 서버에 묻는다 | **WS가 끊겼을 때만 쓰는 폴백** 주기. 평상시에는 **아예 안 돈다** |
| 이 값이 정하는 것 | 알림이 뜨기까지 최대 지연 | WS 장애 시의 최대 지연 (평상시 지연은 1초 이내) |

8절 문제 8이 배운 것("이름·타입이 그대로인데 의미만 바뀐 필드가 가장 위험하다")이 **상수에서 두 번째로 반복됐다.** 이 값을 보고 "평상시 7초 지연"이라고 읽으면 틀린다.

**실측 검증 (이 변경은 눈으로 확인했다)**: 실제 브라우저에서 `seed_user_02`로 GPS 실측 좌표로 presence를 등록해 둔 상태에서, `seed_user_03`이 질문을 올리자 **1초 이내에 `GET /api/notifications` 재조회가 서버 로그에 찍혔다.** 폴링 주기(7초)보다 훨씬 빠르게 반응했다 — 즉 WS 신호가 실제로 도착해서 재조회를 일으킨 것이 확인됐다.

#### 변경 B — 자동 닫힘 배너를 모달 다이얼로그로

**사용자가 준 정책 (원문)**

> "오케이, 질문/답변 등록시 확실하게 현재 해당 관광지 인증된 사용자에게는 화면에 뜨는거지? 실시간으로 알림이. 다이얼로그 형태로"

리더가 되물어 확정:

| 리더의 질문 | 사용자 답 |
|---|---|
| "질문/답변 알림을 지금과 같이 자동으로 사라지는 배너로 둘까요, 아니면 근접 알림처럼 사용자가 직접 닫아야 하는 모달 다이얼로그로 바꿀까요?" | **"모달 다이얼로그로 변경"** |

**무엇이 바뀌었나** — `notification_banner.dart`를 전면 재작성했다.

| | 전 | 후 |
|---|---|---|
| `NotificationBannerHost.build` | 화면 맨 위에 배너 위젯을 그림 | **항상 `SizedBox.shrink()`** — 아무것도 안 그린다 |
| 표시 방법 | `Stack` 안의 위젯 | `showDialog(barrierDismissible: false)` |
| 닫힘 | 6초 타이머로 자동 | **사용자가 "나중에"/"확인하기"를 직접 눌러야** |
| 여러 건이 겹치면 | 배너가 교체됨 | `_dialogShowing` 플래그로 **하나씩 순서대로** (다이얼로그가 쌓이지 않는다) |

이 변경으로 `AppConstants.notificationBannerDuration`(6초)이 **아무 데서도 안 쓰이게 되어 삭제**했다. 11절 "정책적으로 그대로 두기로 한 것" 2번("배너 자동 닫힘 6초는 근거 있는 값이 아니다")은 이로써 소멸했다.

**남는 것**: `NotificationBannerHost`라는 **이름은 그대로인데 더 이상 배너가 아니다.** 이름을 안 바꾼 이유는 `app.dart`의 전역 셸 등록 지점이 그 이름을 참조하고 있어서이고, 대신 파일 상단 주석에 "이 클래스는 이제 아무것도 그리지 않는 다이얼로그 컨트롤러다"를 적어 뒀다.

#### 변경 C — 재접속 시 밀린 알림 요약 다이얼로그 (신규) + 사용자의 알림 설계 철학

**사용자가 준 정책 (원문) — 이 프로젝트의 알림 설계 철학이 여기 있다**

> "난 사용자를 귀찮게해야 참여율이 올라간다고 보기때문에 최대한 노출을 시켜줘야한다고 생각해. 이런 내 생각도 작업일지에 반영해주고! 또한 웹에 접속하지않았다가 다시 들어온 사람들도 읽지않은 질문/답변이 왔다고 알려줄 수 있도록 구현해줘.(모달 다이얼로그로) 이것도 설계시 필요한 요소있으면 물어보면서 진행하고!"

**이 철학은 이번에 처음 나온 것이 아니다.** 9-6절 P26(발송 상한 3종 전면 폐기)이 정확히 같은 방향이었다 — 당시에도 "인원 상한과 **현장 사용자 전원에게 알린다**는 취지가 충돌해서 상한을 없앴다". 그리고 변경 B(자동으로 사라지는 배너 → 직접 닫아야 하는 모달)도 같은 방향이다.

```
P26 (2026-09-10)   발송 상한 3종 폐기        → 더 많은 사람에게
변경 B (2026-09-12) 자동 닫힘 → 모달        → 더 확실하게 보이도록
변경 C (2026-09-12) 재접속 시 밀린 알림 요약 → 자리를 비웠던 사람에게도

= 이 기능 전체를 관통하는 한 방향: "덜 귀찮게"가 아니라 "더 노출"
```

**이 방향을 명시해 두는 이유**: 앞으로 "알림이 너무 자주 뜨는데 줄일까요?"라는 판단이 생기면, 그건 **사용자 정책을 거스르는 제안**이다. 일반적인 UX 상식("알림은 최소화")과 이 프로젝트의 정책이 **정반대**이므로, 상식에 기대어 조용히 줄이면 안 된다.

**리더가 되물어 확정한 것 2가지**

| 리더의 질문 | 사용자 답 | 무엇을 버렸나 |
|---|---|---|
| "재접속 시 밀린 알림이 여러 건이면 어떻게 보여줄까요?" | **"'새 알림 N건' 요약 다이얼로그 하나만"** | 개별 알림마다 다이얼로그를 띄우는 안을 버렸다. 리더가 요약 쪽을 권장한 이유는 **대량일 때 다이얼로그를 N번 닫아야 하는 번거로움** 때문이다. 즉 여기서는 **"최대 노출" 철학과 "한 번에 너무 많이 닫게 하지 않기"가 절충됐다** — 철학을 그대로 밀면 개별 표시가 맞지만, 그 경우 사용자가 다 닫지 않고 창을 떠나버려 **노출 목적 자체가 오히려 실패한다** |
| "언제 이 재접속 알림을 띄울까요?" | **"앱 최초 실행 시만 (권장)"** | 탭 전환·복귀마다 띄우는 안을 버렸다. 탭을 오갈 때마다 모달이 뜨면 그건 노출이 아니라 방해다 |

**구현**

| 무엇 | 어디에 |
|---|---|
| `backlogUnreadCount` (`int?`) 필드 신설 | `notification_service.dart`. **이 세션의 첫 관측**(`_lastObservedUnreadIds`가 직전에 `null`이었던 시점 = 콜드 스타트/새로고침 직후)에 미읽음이 하나라도 있으면 그 개수를 세운다 |
| `dismissBacklogSummary()` | 요약을 닫으면 이 값만 `null`로 되돌린다. **서버 상태는 건드리지 않는다** |
| `_BacklogSummaryDialog` 위젯 | `notification_banner.dart`. "닫기" / "확인하러 가기" 두 버튼 |
| "확인하러 가기" 이동 | `MyQnaScreen(initialTabIndex: 2)` — 내 Q&A의 **알림 탭**으로 바로 연다. 이를 위해 `MyQnaScreen`에 `initialTabIndex` 파라미터(기본값 0)를 추가했고, **기본값 0이라 기존 진입 경로는 그대로다** |

**우리가 판단해 확정한 것**

| 쟁점 | 결정 | 왜 다른 쪽을 버렸나 |
|---|---|---|
| **9-4절의 "첫 폴링에서는 배너를 안 띄운다"를 어떻게 하나** | **뒤집었다.** 첫 관측에서 미읽음이 있으면 이제 **요약 다이얼로그를 띄운다** | 원래 그 규칙의 목적은 "앱을 열자마자 묵은 알림이 튀어나오는 것을 막자"였는데, **사용자 정책이 정확히 그 반대("재접속한 사람에게도 알려라")를 요구했다.** 다만 통째로 뒤집지는 않았다 — 실시간 배너는 여전히 첫 관측에서 안 뜨고, **요약 다이얼로그 하나만** 뜬다. 원래 규칙이 막으려던 것(개별 배너가 우수수)은 그대로 막혀 있다 |
| **`resetForUserSwitch()`(테스트유저 전환)도 이 경로를 탈까** | **안 탄다. 의도적으로 분리했다** | 이 함수는 기준선을 `null`이 아니라 **빈 집합**으로 세우므로(9-7절) "첫 관측" 조건에 해당하지 않는다. 계정을 바꿀 때마다 요약 모달이 뜨는 건 과하다고 판단했다 — **계정 전환은 기존의 실시간 배너 경로만 탄다.** 9-7절이 "리셋 경로마다 이후 첫 관측이 새로운 것인지 따로 답하라"고 배운 것이 **여기서 세 번째 경로(콜드 스타트 / 계정 전환 / 요약)로 갈라진 것**이다 |
| **요약을 닫으면 서버에 읽음 처리를 할까** | **안 한다** | **"요약을 봤다"와 "안의 알림을 읽었다"는 다른 사건이다.** 읽음 처리를 하면 N건이 전부 읽음이 되어 목록에서 강조가 사라지고, 사용자는 **무엇이 새 것이었는지 영영 알 수 없게 된다** — 최대 노출 정책과 정면으로 충돌한다 |

## 10. 배운 것

1. **만료를 구현하는 방법은 두 가지고, 하나는 거의 항상 틀렸다.** 상태 컬럼 + 배치는 배치가 늦는 순간 DB가 거짓말을 한다. 조회 시점 계산은 항상 맞고, 덤으로 원본 행이 남는다. ([006]·[013]에서 이미 배운 것이 이번에 세 번째로 적용됐다)
2. **필터를 거는 순서가 결과를 바꾼다.** "10명으로 자른다"를 먼저 하면 받을 수 있었던 사람이 이유 없이 누락된다. 개인별 조건을 먼저, 전체 상한을 마지막에. (상한 자체는 이후 폐기됐지만 순서 규칙은 남는다)
3. **인터페이스는 "지금 필요해서" 만드는 게 아니라 "나중에 갈아 끼울 지점을 한 곳으로 모으려고" 만든다.** 이번 `NotificationSender`의 구현체는 아무것도 안 하는 빈 껍데기지만, 그 덕에 나중에 FCM을 붙일 때 바뀌는 파일이 백엔드 1개·프론트 1개로 고정됐다.
4. **스키마 이름 하나가 미래의 선택지를 잠근다.** `device_tokens`라고 지었으면 Web Push를 붙일 때 컬럼명이 거짓말이 됐을 것이다.
5. **UI를 겹치느냐 밀어내느냐는 취향이 아니라 레이아웃 계약 문제다.** 화면 전체 높이를 기준으로 크기를 잡는 위젯이 하나라도 있으면 `Column`으로 밀어내는 순간 그 계산이 깨진다.
6. **"이미 하고 있으면 건너뛴다"는 중복 방지가 아니라 실패 은폐다.** 진행 중인 작업의 결과(Future)를 공유해야 부른 쪽이 성공/실패를 제대로 받는다.
7. **명세에 "1인당 시간당 2회"라고만 적으면, 종류가 둘 이상일 때 어느 종류가 쿼터를 먹는지가 비어 있다.** 1회차 F1이 정확히 그 빈칸이었다. 상한을 적을 때는 **무엇을 세는지**까지 적어야 한다.
8. **"무엇의 수명을 재는가"가 만료 구현의 진짜 결정이다.** 방법(조회 시점 계산)은 처음부터 맞았는데, 기준을 알림 자신에게 두느냐 알림이 가리키는 질문에 두느냐가 남아 있었다. 알림은 손가락이고 질문이 대상이다 — **손가락의 수명은 대상의 수명을 따라가야 한다.**
9. **이름·타입이 그대로인데 의미만 바뀐 필드는 어떤 자동 대조로도 못 잡는다.** `expires_at`은 스키마 대조에서 계속 `[OK]`가 나온다. 이런 변경은 **두 해석이 실제로 갈라지는 응답을 하나 만들어 눈으로 보는 것**만이 검증이다(답변 알림: `created 14:05:10` / `expires 16:04:42`).
10. **"상태를 저장하지 않고 행위 자체를 증거로 삼는" 방법이 있다.** "지금 접속 중"을 online 컬럼이나 소켓으로 만들지 않고 **폴링해 오는 행위**로 정의했다. 저장하는 상태가 늘지 않으니 유령 데이터도, 정리 코드도 안 생긴다.
11. **정책이 폐기되면 코드보다 문서가 먼저 썩는다.** 상한 3종을 지우는 것은 함수 두 개 삭제였지만, 그 상한을 전제로 쓰인 주석·일지·화면 문구는 곳곳에 흩어져 있었다. 삭제 작업은 **심볼 전수 grep으로 끝을 확인**해야 한다.
12. **성능 상수 옆의 근거는 "왜 안전한가"가 아니라 "무엇이 이걸 떠받치는가"로 적어야 한다.** "TourAPI를 안 부른다"는 틀린 안심이었고, 진짜 안전장치는 600초 캐시였다. 안전장치 이름이 적혀 있어야 그것을 걷어낼 때 이 값도 같이 재검토된다.
13. **"만들어 달라"는 요청이 항상 "없다"는 뜻은 아니다.** (2026-09-12) 요청받은 두 기능은 이미 코드에 있었고 실체는 버그 하나였다. 요청대로 새로 만들었다면 배너가 두 개 뜨고 멀쩡한 백엔드가 바뀌었을 것이다. **코드를 고치기 전에 "지금 무엇이 안 되는가"와 "어떻게 재현했는가"를 물은 것**이 성패를 갈랐다.
14. **사용자의 증상 문장은 대부분 원인을 가리킨다.** (2026-09-12) *"목록은 업데이트되는데 팝업만 안 뜬다"* 는 **통신이 아니라 표시 판정 로직**의 문제라고 이미 말하고 있었다. 데이터가 도착한 증거와 도착 안 한 증거가 한 문장에 같이 있으면, **둘을 가르는 코드**가 범인이다.
15. **변화를 "개수"로 감지하면 원소가 빠질 수 있는 목록에서 눈이 먼다.** (2026-09-12) 개수는 "무엇이 새로 왔는가"의 대용물일 뿐이다. 묻고 싶은 것이 신규 도착이면 **id 집합의 차집합**으로 직접 물어라.
16. **상태를 리셋하는 함수는 "이 리셋 후 첫 관측이 사용자에게 새로운 것인가"를 상황마다 따로 답해야 한다.** (2026-09-12) 앱 최초 시작은 "새롭지 않다", 사용자 전환은 "새롭다"이다. 둘을 같은 값으로 묶어 둔 것이 배너가 억제되던 버그였다. → **3차에서 경로가 셋으로 늘었다**(콜드 스타트는 "요약 모달만", 계정 전환은 "실시간 배너만"). 이 질문은 한 번 답하고 끝나는 게 아니라 **경로가 늘 때마다 다시 답해야 하는 질문**이다.
17. **실시간 전송 경로를 추가할 때, 거기에 "내용"을 실으면 판정 로직이 한 벌 더 생긴다.** (2026-09-12) WebSocket으로 알림 내용을 밀어 보내는 대신 **"다시 읽어라"는 빈 신호**만 보냈더니, 응답 스키마가 안 바뀌고 폴백 경로와 결과가 갈릴 수 없게 됐다. **새 전송 경로는 "전달 수단"이 아니라 "기존 경로의 방아쇠"로 만들면 사본이 안 생긴다.**
18. **겉보기에 같은 "폴링"이라도 서버에게 묻는 것과 자기 자신에게 묻는 것은 다른 문제다.** (2026-09-12) GPS 근접 확인의 60초 타이머는 서버발 이벤트가 아예 없어서 **WebSocket으로 바꿀 대상 자체가 없었다.** "이거 실시간으로 바꾸자"는 요청이 오면 먼저 물을 것 — **누가 판정하는가? 서버인가 클라이언트인가?** 서버가 아니면 밀어줄 것이 없다.
19. **`pkg[standard]` 같은 묶음 설치는 버전을 고정한 것이 아니다.** (2026-09-12) 본체만 핀을 박으면 하위 의존성은 설치 시점에 따라 올라가고, 그 불일치는 **엉뚱한 HTTP 상태코드로 위장**한다. websockets 버전 불일치가 **403**으로 나타났다 — **권한 검사를 한 적이 없는데 403이 온다면 그 403은 내 코드가 만든 것이 아니다.**
20. **"재시작했는데 코드가 반영 안 된다"는 캐시 문제이기 전에 프로세스 문제일 수 있다.** (2026-09-12) `uvicorn --reload`는 부모(포트를 잡음)와 자식(실제 코드 실행)이 따로 있어서, 포트로 찾은 PID만 죽이면 **자식이 고아로 살아남아 예전 코드로 답한다.** 그리고 `/health` 200은 **새 코드로 떠 있다는 증거가 아니다** — 재시작 확인은 바뀐 코드가 응답에 나타나는지로 해야 한다.
21. **이름·타입이 그대로인데 의미만 바뀌는 일은 필드에만 생기지 않는다. 상수에도 생긴다.** (2026-09-12) `notificationPollIntervalSeconds = 7`은 값도 이름도 그대로인데 **"기본 주기" → "WS 끊겼을 때의 폴백 주기"** 로 뜻이 바뀌었다. 9번 교훈(`expires_at`)의 두 번째 반복이다 — **이런 변화는 어떤 자동 대조로도 안 잡히므로 사람이 문서에 적는 수밖에 없다.**
22. **사용자의 설계 철학이 UX 상식과 반대일 수 있고, 그때는 철학이 이긴다.** (2026-09-12) *"난 사용자를 귀찮게해야 참여율이 올라간다고 보기때문에 최대한 노출을 시켜줘야한다"* — 일반적인 조언("알림은 최소화")을 그대로 적용하면 이 프로젝트에서는 **정책 위반**이다. 다만 철학을 기계적으로 밀면 역효과가 나는 지점도 있었다(밀린 알림 N건을 개별 모달로 띄우면 사용자가 다 안 닫고 떠나 **노출 목적 자체가 실패**한다) — **철학은 목적이지 수단이 아니다.**

#### 이번에 배운 것 (10절에 13~16번으로 추가했다)

13. **"만들어 달라"는 요청이 항상 "없다"는 뜻은 아니다.** 이번 요청의 두 기능은 이미 있었고, 실체는 버그 하나였다. 요청대로 새로 만들었다면 배너가 두 개 뜨고 멀쩡한 백엔드가 바뀌었을 것이다. **코드를 고치기 전에 "지금 무엇이 안 되는가"와 "어떻게 재현했는가"를 물은 것**이 이번 작업의 성패를 갈랐다 — 사용자의 재현 절차 한 문장("A로 질문 올린 뒤 B로 전환")이 원인을 정확히 가리켰다.
14. **사용자가 원인까지 말해 줄 것이라 기대하면 안 되지만, 증상 문장은 대부분 원인을 가리킨다.** "목록은 업데이트되는데 팝업만 안 뜬다"는 **통신이 아니라 표시 판정 로직**의 문제라고 이미 말하고 있었다. 데이터가 도착한 증거(목록 갱신)와 도착 안 한 증거(팝업 없음)가 한 문장에 같이 있으면, 둘을 가르는 코드가 범인이다.

### 2026-09-12 — WebSocket 전환 + 모달 다이얼로그 + 재접속 요약 (3차)

위 2차 작업 직후에 이어진 변경 **3건**이다. **셋 다 사용자가 채팅으로 정책을 직접 준 것**이고, **원문 3건은 9-8절에 그대로 인용해 뒀다.** 2차가 "이미 있는 것의 버그를 고친 것"이었다면, 이번은 **전달 방식과 표시 방식 자체가 바뀐 것**이다.

> ⚠️ **변경 A는 9-7절의 우리 결정("폴링 유지, SSE/WebSocket 안 씀")을 뒤집는다.** 우리가 번복한 것이 아니라 **사용자가 실시간성을 직접 요구했다.** 당시 근거(다중 인스턴스 위험 등)가 사라진 것은 아니고, 어떻게 감당했는지는 9-8절 변경 A의 결정 표에 있다.

#### 변경 A — 실시간 전달을 폴링 → WebSocket (+ 폴링 폴백)

사용자 원문과 리더의 확인 질문 2건(적용 범위 / 폴백 여부)은 **9-8절 변경 A**. 요지는 "질문/답변 알림만, WS + 폴링 폴백".

**GPS 인증은 조사 끝에 범위에서 빠졌다** — GPS 근접 확인(`proximity_alert_service.dart`, `home_screen.dart`의 60초 타이머)은 서버가 대상을 판정해 밀어주는 구조가 아니라 **클라이언트가 스스로 "지금 여기 근처인가"를 자문하는 완전 클라이언트 로직**이라, WebSocket으로 바꿀 **서버발 이벤트 자체가 없다.** 리더가 이를 조사해 사용자에게 설명했다. 이 판정은 9-8절에 자세히 남겼다 — **안 적어 두면 다음에 같은 요청이 또 나오고 같은 조사를 처음부터 반복한다.**

**백엔드**

| 파일 | 무엇 |
|---|---|
| `app/services/ws_manager.py` | **신규.** `NotificationConnectionManager` — `user_id` → WebSocket 집합(한 사람의 여러 탭), 인메모리, `connect`/`disconnect`/`notify` |
| `app/services/notification.py` | `InAppNotificationSender.deliver()`에서 알림 저장 후 **수신자별로 `ws_manager.notify(user_id)` 호출.** 알림 데이터는 싣지 않고 **`{"type":"notification"}` 빈 신호만** 보낸다 |
| `app/api/notifications.py` | **`GET /api/notifications/ws` 신설.** 사용자 구분은 **쿼리 파라미터 `test_user_id`** — 브라우저 WebSocket 핸드셰이크는 커스텀 헤더를 못 실으므로 `X-Test-User-Id` 헤더를 쓸 수 없다 |

#### 변경 B — 자동 닫힘 배너 → 모달 다이얼로그

사용자 원문과 리더의 확인 질문은 **9-8절 변경 B**. 사용자 답은 **"모달 다이얼로그로 변경"**.

`livespot_app/lib/widgets/notification_banner.dart`를 **전면 재작성**했다.

- `NotificationBannerHost`는 더 이상 화면에 아무것도 그리지 않는다 — `build`가 항상 `SizedBox.shrink()`이고, `bannerEntry`가 생기면 `showDialog(barrierDismissible: false)`로 모달을 띄운다.

#### 변경 C — 재접속 시 밀린 알림 요약 다이얼로그 (신규 기능)

**사용자 정책 원문은 9-8절 변경 C에 그대로 있다.** 여기에는 그 정책이 무엇을 뜻하는지만 적는다.

> 핵심 문장은 *"난 사용자를 귀찮게해야 참여율이 올라간다고 보기때문에 최대한 노출을 시켜줘야한다고 생각해"* 이고, **사용자가 이 생각을 작업일지에 반영해 달라고 직접 요청했다.**

이 정책은 **9-6절 P26(발송 상한 3종 폐기 — "인원 상한과 현장 사용자 전원 알림 취지가 충돌해 상한을 없앴다")과 같은 방향**이다. 변경 B(자동 닫힘 → 모달)도 마찬가지다. **"덜 귀찮게"가 아니라 "더 노출"이 이 기능 전체를 관통하는 사용자의 일관된 설계 철학**이라는 점을 9-8절에 명시적으로 연결해 적었다 — 앞으로 "알림을 줄일까요?"라는 제안은 **일반 UX 상식에는 맞아도 이 프로젝트의 정책에는 어긋난다.**
