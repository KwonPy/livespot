# "내 주위 관광지" 위치 기반 조회의 데이터 누락 문제

## 1. 한 줄 요약

"내 주위 관광지"가 거리순으로 정렬되는 방식 자체는 정상인데, 정작 반경 안에 있는 관광지 하나가 원본 데이터(TourAPI)에서부터 통째로 빠져 있어서 목록에 안 뜨는 문제를 발견했다. 아직 고치지는 않았고, 하루 안에 끝낼 수 있는 해결 방안만 정리해뒀다.

## 2. 왜 만들었는가

사용자가 경희대 국제캠퍼스 안(경희천문대 근처)에서 앱을 써보다가 "노천극장도 분명 근처에 있고 카테고리도 맞는데 왜 목록에 안 뜨냐"고 물어봤다. "내 주위 관광지"의 정렬 기준을 설명하려고 코드를 확인하다가, 정렬 로직이 아니라 애초에 서버가 받아오는 원본 데이터 자체에 이 관광지가 없다는 걸 알게 됐다.

## 3. 구현한 것

이번엔 코드를 바꾸지 않았다. 원인을 조사해서 확정했고, 해결 방안을 설계까지만 해뒀다(5절 참고). 실제 코드 변경은 다음 단계다.

## 4. 동작 흐름

지금 "내 주위 관광지"(`POST /api/spots/nearby`)가 실제로 하는 일:

```
사용자 GPS 좌표
→ TourAPI locationBasedList2 호출 (반경 내, arrange=S → 거리순, 최대 100건)
→ 카테고리 화이트리스트 (12 관광지 / 14 문화시설 / 15 축제 / 28 레포츠 / 38 쇼핑)
→ 좌표 없는 항목 제외
→ 상위 20개를 그대로 반환 (순서는 TourAPI가 준 거리순 그대로, 백엔드가 다시 정렬하지 않음)
```

문제는 이 첫 단계 `locationBasedList2` 호출 자체가 "경희대학교 국제캠퍼스 노천극장"을 반환하지 않는다는 것이다. 뒤에 있는 화이트리스트·좌표 필터는 통과 여부를 검사할 기회조차 없었다 — 애초에 원본 목록에 없으니까.

## 5. 주요 파일

- `livespot_backend/app/api/spots.py` — `nearby_spots()`(POST `/nearby`), `_filter_allowed_items()`: 정렬·필터 로직이 있는 곳. 이번에 조사한 코드
- `livespot_backend/app/services/tour_api.py` — `get_nearby_spots()`(`locationBasedList2` 호출), `get_area_based_list()`(`areaBasedList2` 호출, 해결 방안에서 쓸 예정), `AREA_CODE_SEOUL`/`AREA_CODE_GYEONGGI` 상수(이미 있지만 현재 미사용)
- `livespot_backend/app/services/geo.py` — `calculate_distance_m()`: GPS 제보 인증에 쓰던 거리 계산 함수. 해결 방안에서 재사용 예정

## 6. 핵심 코드 / 개념

**공공데이터는 "이 API로 검색되면 존재하고, 안 되면 없다"가 아니다.** TourAPI는 관광지 하나에 대해 여러 조회 방식(이름 검색, 지역 목록, 위치 기반)을 제공하는데, 이 방식들이 내부적으로 서로 다른 색인(index)을 쓴다. 그래서 어떤 관광지는 이름 검색(`searchKeyword2`)이나 지역 목록(`areaBasedList2`)으로는 잡히는데, 위치 기반 검색(`locationBasedList2`)의 "이 좌표 반경 안에 뭐가 있나" 색인에는 등록이 안 돼 있을 수 있다. 실제로 확인한 결과:

| 조회 방식 | "노천극장" 검색 결과 |
|---|---|
| `searchKeyword2` (이름 검색) | ✅ 정상 조회됨 (content_id `2946243`, 문화시설, 좌표 정상) |
| `locationBasedList2` (반경 2000m, 실측 거리 약 666m) | ❌ 응답 29건 안에 없음 |

거리도 충분히 가깝고(666m < 2000m 반경), 카테고리(문화시설=14)도 우리 화이트리스트에 들어있고, 좌표도 정상인데 반경 검색 결과에만 빠져 있다 — 즉 우리 필터링 로직이 걸러낸 게 아니라, TourAPI가 애초에 후보로 주지도 않았다는 뜻이다.

## 7. 사용한 기술

새로운 기술 없음. TourAPI의 서로 다른 오퍼레이션(`locationBasedList2` vs `searchKeyword2`)을 직접 호출해서 결과를 대조하는 방식으로 원인을 확인했다.

## 8. 문제와 해결

- **문제:** 경희천문대 근처(반경 2000m 이내, 실측 666m)에 있는 "경희대학교 국제캠퍼스 노천극장"이 "내 주위 관광지" 목록에 나타나지 않음
- **원인:** 우리 백엔드의 정렬·필터 로직 문제가 아니라, TourAPI의 위치 기반 조회(`locationBasedList2`)가 참조하는 공간 색인 자체에 이 관광지가 누락돼 있음. `searchKeyword2`(이름 검색)로는 정상 조회되므로 데이터 자체가 없는 건 아니고, 위치 기반 색인에만 빠진 것으로 보임
- **해결:** 아직 하지 않음 — 9절/12절에 다음 단계로 정리
- **배운 점:** 외부 공공 API를 쓸 때 "한 오퍼레이션에서 안 나오면 데이터가 없는 것"이라고 단정하면 안 된다. 같은 데이터를 다른 오퍼레이션(이름 검색, 지역 목록)으로도 교차 확인해봐야 진짜 원인(필터링 버그 vs 원본 데이터 누락)을 구분할 수 있다. 이 교훈은 별도 규칙 파일에는 넣지 않았다 — TourAPI 오퍼레이션 간 색인 불일치는 이번이 처음 확인된 사례라 아직 일반 패턴인지 판단하기 이르고, 비슷한 증상이 한 번 더 나오면 그때 `livespot-contract`의 참고 자료로 일반화할 것

| 지금 바로 고칠지, 조사만 하고 남길지 | **이번엔 조사·제안까지만, 구현은 다음 단계로 미룸** | 사용자가 "제안해줄래"라고 물었을 뿐 구현을 지시하지 않았음. 아래 제안안은 하루 안에 끝낼 수 있는 범위로 설계해뒀으니, 실행은 사용자 승인 후 진행 |

### 검토한 해결 방안 (구현 전 제안)

**방안: `areaBasedList2`를 보완 조회로 병행 사용**

`areaBasedList2`(지역 전체 목록, 시도 단위 등록부 방식)는 `locationBasedList2`(반경 검색, 공간 색인 방식)와 색인 체계가 다르다. 위치 기반 색인에서 빠진 항목도 지역 목록 등록부에는 있을 가능성이 높다 — 실제로 `areaBasedList2`가 참조하는 등록부 자체를 이름 검색(`searchKeyword2`)이 정상적으로 찾아낸 것으로 보아, 위치 기반 색인만 별도로 관리되고 있다고 추정할 수 있다.

절차:
1. `nearby_spots()`에서 `locationBasedList2` 원시 결과의 `addr1` 값을 다수결로 봐서 사용자가 서울/경기 중 어디 있는지 판별 (별도 지오코딩 API 호출 불필요 — 이미 받아온 응답으로 판별)
2. 해당 시도의 `area_code`(기존 `AREA_CODE_SEOUL="1"` / `AREA_CODE_GYEONGGI="31"` 상수 — 이미 코드에 있지만 지금은 안 쓰이고 있음)로 `get_area_based_list()` 보완 조회
3. 보완 목록의 각 항목에 대해 GPS 인증에 쓰던 `calculate_distance_m()`으로 사용자 좌표와의 거리를 직접 계산, 요청 반경(`req.radius`) 이내만 남김
4. `content_id` 기준으로 원래 `locationBasedList2` 결과와 병합·중복 제거 (겹치면 원래 결과의 `dist` 값을 우선 사용)
5. 기존과 동일하게 카테고리·좌표 필터를 적용하고 거리순 정렬해서 상위 20개 반환

**왜 이 방안인가:**
- 새 API 키나 외부 서비스가 필요 없다 — `get_area_based_list()`(이미 있음)와 `calculate_distance_m()`(이미 있음, GPS 제보 인증에서 재사용)만 조합하면 됨
- 시도 판별에 별도 지오코딩 호출이 필요 없다 — 이미 받아온 `locationBasedList2` 응답의 `addr1`로 판별
- `get_area_based_list()`가 이미 300초 TTL 캐시를 갖고 있어([004-congestion-prediction.md](004-congestion-prediction.md), [018-congestion-quota-fix.md](018-congestion-quota-fix.md)에서 겪은 쿼터 소진 문제와 같은 실수를 반복하지 않도록) 같은 지역 반복 조회는 API 호출로 이어지지 않음
- 위 이유로 하루 안에 구현 가능하다고 판단

**한계로 남는 부분:**
- **응답 크기·지연** — 시군구 단위가 아니라 시/도 전체 목록을 받아오는 방식이라, 사용자 위치와 무관하게 대량 데이터(수백~수천 건)를 매번 내려받아야 한다. 콘텐츠타입 파라미터로 응답을 줄이는 절충이 필요하다.
- **거리 계산 비용이 백엔드로 전가됨** — `locationBasedList2`는 TourAPI가 이미 반경 필터링을 해서 주지만, `areaBasedList2` 보완 조회분은 그런 필터링이 없어서 시/도 전체 목록의 항목 하나하나에 대해 `calculate_distance_m()`을 백엔드가 직접 계산해야 한다. 항목 수가 많을수록(특히 경기도) 요청당 연산량이 늘어난다.
- **300초 TTL 캐시가 지역 단위라 최신성이 떨어짐** — 시/도 전체 목록을 통째로 캐시하는 방식이라, 반경 검색이었다면 덜 느꼈을 최대 5분의 지연이 생길 수 있다.
- **경계 지역(서울/경기 접경) 누락 가능성** — `addr1` 다수결로 사용자가 어느 시/도에 있는지 판별하기 때문에, 서울-경기 경계 근처 사용자는 반대편 시/도의 더 가까운 관광지를 여전히 놓칠 수 있다.
- **서울/경기 외 지역 미검증** — 사용자 실사용 범위가 지금까지 서울/경기뿐이라, 전국으로 확장했을 때 시/도별 목록 크기 편차(경기도가 서울보다 훨씬 큼)가 성능 문제로 커지는지는 확인되지 않았다.
- `locationBasedList2` 자체의 색인 누락 원인(왜 이 항목만 빠졌는지)은 TourAPI 쪽 문제라 우리가 고칠 수 없고, 위 보완 조회는 증상을 우회하는 방법일 뿐임

### 후속 합의 (2026-09-17)

> 이거를 그대로 worklog의 한계부분에 재반영해주고, 우리는 그냥 데이터셋의 한계를 감수하고 가는걸로 가자. 페이로드를 줄이는 방향으로 가기로 합의했다고 말미에 간략하게 언급해줘.

TourAPI 위치 기반 색인 누락이라는 데이터셋 자체의 한계는 고칠 수 없으므로 감수하고 가기로 했다. `areaBasedList2` 보완 조회 방안은 그대로 채택하되, 위 한계 중 응답 크기 문제는 구현 단계에서 콘텐츠타입 파라미터 등으로 페이로드를 줄이는 방향으로 처리하기로 합의했다.

## 10. 배운 것

- 공공데이터 API는 오퍼레이션마다(이름 검색 / 지역 목록 / 위치 기반) 내부 색인이 분리돼 있을 수 있고, 한쪽에서 안 나온다고 해서 데이터가 없는 게 아니다. 다른 오퍼레이션으로 교차 확인해야 "필터 버그"와 "원본 데이터 누락"을 구분할 수 있다.
- 이 프로젝트는 이미 GPS 거리 계산(`geo.py`)과 지역별 목록 조회(`get_area_based_list()`)를 다른 목적으로 구현해둔 게 있어서, 새 기능처럼 보이는 문제도 기존 조각을 조합해서 하루 안에 풀 수 있는 경우가 많다.

## 11. 현재 한계

- 원인만 확정했고 실제 코드 수정은 하지 않았다. "내 주위 관광지" 반경 검색은 지금도 TourAPI 위치 기반 색인에서 누락된 항목을 놓칠 수 있는 상태 그대로다.
- 위 보완 조회 방안이 서울/경기 외 지역에서도 같은 문제를 겪는지는 확인하지 않았다 (사용자 실사용 범위가 지금까지 서울/경기였음).
