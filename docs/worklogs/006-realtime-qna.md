# 실시간 현장 Q&A (기능 7)

> 소급 기록 — 2026-09-01 작성. DB 마이그레이션 생성일 기준 실제 구현은 2026-08-31.

## 1. 한 줄 요약

멀리 있는 사람이 "지금 대기 있나요?"라고 물으면, **그 관광지 현장에 GPS로 인증된 사람만** 답할 수 있다.

## 2. 왜 만들었는가

제보([002](002-report-gps-verification.md))는 현장에 있는 사람이 **자발적으로** 올리는 정보다. 하지만 여행자가 진짜 궁금한 건 정해져 있지 않다 — "지금 주차 자리 있어요?", "우산 필요한가요?" 같은 건 제보 폼의 3개 항목으로 답할 수 없다.

질문을 열어두면 현장 사람이 **그 질문에 맞춰** 답한다. 제보가 못 채우는 공백을 메우는 기능이다.

이 기능 이전까지 질문 작성 창(`AskQuestionModal`)은 파일로만 존재했고 **앱 어디에서도 열리지 않았다.** 상세화면의 "질문하기 >" 버튼은 눌러도 아무 일도 일어나지 않았다.

## 3. 구현한 것

- `questions`, `answers` 테이블과 마이그레이션
- 질문 등록·목록 조회 API (필터 3종)
- 답변 등록 API — GPS 현장 인증 필수
- 앱: 질문 작성 모달 연결, 답변 모달, Q&A 목록 위젯, 질문 상세 시트

## 4. 동작 흐름

```
[질문]  상세페이지 "질문하기"
→ POST /api/questions {spot_content_id, content}
→ 위치 검증 없음 (질문자는 원래 멀리 있는 사람)
→ 즉시 ACTIVE 상태

[조회]  GET /api/questions?spot_content_id=...&active_only=true
→ 오늘(KST) 등록된 것만 필터
→ 질문마다 status를 그 자리에서 계산 (created_at + 2시간 지났으면 EXPIRED)
→ 답변 목록까지 함께 내려줌

[답변]  현장에서 "답변하기"
→ POST /api/questions/{id}/answers {content, lat, lng}
→ ① 본인 질문인가? → 403
→ ② 만료됐나?     → 400
→ ③ 서버가 거리 재계산 (150m) → 초과면 403
→ 저장 + questions.answer_count += 1
```

## 6. 핵심 코드 / 개념

**상태(ACTIVE/EXPIRED)를 컬럼으로 저장하지 않는다**

```python
def _status(question):
    return "EXPIRED" if 지금 >= question.created_at + 2시간 else "ACTIVE"
```

상태 컬럼을 두면 그걸 바꿔줄 배치 작업(스케줄러)이 필요하고, 배치가 늦으면 **DB의 상태가 거짓말을 하게 된다.** `created_at` 하나면 언제든 정확히 계산할 수 있으니 저장하지 않는다.

**"하루 단위 리셋"을 배치 없이 구현하기**

정책은 "질문 목록은 하루 단위로 현재 목록을 리셋"이었다. 이것도 마찬가지로 **조회할 때 오늘(KST) 것만 거르는 방식**으로 구현했다. 과거 질문은 DB에 그대로 남는다. KST 자정 계산은 [005](005-live-status-hotspots.md)에서 만든 로직을 그대로 재사용했다.

**답변 개수를 미리 세어 저장한다** (`answer_count`)

"답변 대기 중인 질문"을 찾으려면 답변이 0개인 질문을 골라야 하는데, 매번 전체를 세면 질문이 쌓일수록 느려진다. 답변을 저장할 때 `answer_count += 1`을 함께 해두면 `WHERE answer_count = 0`으로 바로 찾을 수 있다.

**필터 3종의 용도가 각각 다르다**

| 파라미터 | 쓰는 곳 | 동작 |
|---|---|---|
| (기본) | 상세페이지 | 오늘 것 전부. 만료된 질문도 "만료" 배지와 함께 보여줌 |
| `active_only` | Live "내 현장 Q&A" | 만료 제외 — 답변 가능한 것만 |
| `pending_only` | 답변 유도 | 만료 제외 + 답변 0개 |

## 7. 사용한 기술

| 기술 | 용도 |
|---|---|
| SQLAlchemy `@property` | `is_expired`를 모델에서 계산 |
| Pydantic `Literal` | `status` 값을 두 개로 고정 |
| SQLAlchemy JOIN | 답변에 작성자 닉네임을 붙여 응답 |

## 8. 문제와 해결

- **문제:** 만료된 질문을 어떻게 다뤄야 하나? 숨길까, 보여줄까?
- **원인:** 정책은 "만료된 질문은 조회 가능하지만 새 답변 작성 불가"였는데, 화면마다 필요한 게 달랐다. Live 페이지의 "내 현장 Q&A"는 지금 답할 수 있는 것만 보여줘야 하고, 상세페이지는 과거 답변도 읽을 수 있어야 한다.
- **해결:** 하나로 정하지 않고 `active_only` 쿼리 파라미터로 화면이 고르게 했다. 기본값은 "만료도 보여줌"(정책 그대로).
- **배운 점:** 정책이 "조회는 되고 쓰기는 안 됨"처럼 **읽기/쓰기를 나눠 말할 때**는, 화면마다 읽기 범위가 다를 수 있다. 서버가 하나로 못 박지 말고 선택지를 열어두는 게 맞다.

| 쟁점 | 결정 | 근거 |

| "상세페이지에서만 작성 가능"을 서버가 강제할까 | **앱(UI)이 지킨다.** 서버는 질문에 위치·경로 제한을 걸지 않는다 | 질문은 원래 위치 제한이 없는 기능이라, 서버가 강제할 수 있는 기술적 근거가 없다 |

## 10. 배운 것

- **상태를 저장하지 말고 계산하라** — 시간이 지나면 자동으로 바뀌는 상태(만료, 리셋)는 컬럼에 저장하는 순간 그것을 갱신할 배치가 필요해지고, 배치가 늦으면 데이터가 거짓말을 한다. `created_at` 하나로 계산할 수 있으면 그게 항상 정확하다.
- 반대로 **집계는 저장해도 된다**(`answer_count`) — 이건 시간이 지나서 바뀌는 값이 아니라 이벤트가 있을 때만 바뀌는 값이라, 갱신 시점이 명확하다.
- 같은 검증 로직(GPS 거리 판정)이 세 곳(제보 저장, 현장 인증, 답변 저장)에서 필요해졌다. 상수를 `settings`에 두고 공유한 덕에 기준이 갈리지 않았다.

## 11. 현재 한계

- **Credit 지급(+50) 없음.** 기능 4에서 연결해야 한다.
- 답변 작성자가 전부 `test_user`라, "질문자 본인은 답변 불가" 규칙 때문에 **한 계정으로는 질문과 답변을 둘 다 테스트할 수 없다.** `TEST_MODE`로 사용자를 바꿔가며 확인해야 한다.

- 답변 알림(푸시, 기능 8) 없음 — 질문자는 앱을 다시 열어봐야 답변을 안다.
