# 방문 집중률 예측 분리 (기능 9)

> 소급 기록 — 2026-09-01 작성.

## 1. 한 줄 요약

한국관광공사의 "방문 집중률 예측"을 우리 사용자의 "현장 제보"와 **절대 합치지 않고** 나란히 보여준다.

## 2. 왜 만들었는가

"이 관광지 지금 붐비나요?"에 답하는 방법이 두 가지 있는데, 성격이 완전히 다르다.

| | 방문 집중률 예측 | 현재 현장 상황 |
|---|---|---|
| 출처 | 한국관광공사 (과거 방문 패턴) | 우리 사용자의 GPS 인증 제보 |
| 성격 | **미래 예측** | **지금 이 순간의 실측** |
| 커버리지 | 대상 관광지 전부 항상 있음 | 제보가 있는 곳만 |

이전 코드는 이 둘을 "제보 3건 이상이면 제보 우선 → 아니면 혼합 → 아니면 공공데이터 → 아니면 시간대로 추측" 식으로 **하나의 값으로 합치고** 있었다. 합치는 순간 두 정보가 모두 왜곡된다. 이 작업은 그 병합 로직을 폐기하고 둘을 분리하는 것이 목적이었다.

## 3. 구현한 것

- 집중률 API(TatsCnctrRateService) 연동 서비스
- 전국 시도·시군구 행정표준코드 테이블 (API 호출에 필수인데 조회 오퍼레이션이 없어서 직접 들고 있어야 함)
- 관광지명 매칭 로직 (집중률 API에는 `content_id`가 없다)
- 단건 조회 + 지도용 배치 조회 API
- 앱: 지도 마커 색상은 **집중률 예측만** 사용, 현장 제보는 상세페이지 배지로만

## 4. 동작 흐름

```
지도에 관광지 30개가 보임
→ POST /api/spots/congestion-batch  [{content_id, title, address} × 30]
→ 주소에서 시군구를 추려냄 (예: "서울 종로구 ..." → areaCd 11, signguCd 11110)
→ 중복 제거 → 시군구 3~4개
→ 시군구별로 집중률 API 1회씩 호출 (관광지 30번이 아니라 시군구 4번!)
→ 응답에는 오늘부터 30일치가 옴 → 오늘 날짜 행만 사용
→ 관광지명으로 매칭 ("덕수궁 대한문" ↔ "덕수궁")
→ {content_id: 집중률} 맵으로 응답
→ 지도 마커 색상 (🟢 0~39 / 🟡 40~69 / 🔴 70~100)
```

## 5. 주요 파일

- `livespot_backend/app/services/congestion.py` — 집중률 API 연동, 이름 매칭, 캐싱
- `livespot_backend/app/services/region_codes.py` — 전국 행정표준코드 표 + 주소 파서
- `livespot_backend/app/api/spots.py` — `/congestion`, `/congestion-batch` 엔드포인트
- `livespot_app/lib/models/congestion_info.dart`
- `livespot_app/lib/widgets/crowdedness_badge.dart` — 집중률 배지 (제보 라벨과 다른 함수를 쓴다)
- `livespot_backend/app/services/crowdedness.py` — ⚠️ 이 작업 이전의 레거시. 새로 쓰지 말 것

## 6. 핵심 코드 / 개념

**지역코드 체계가 두 가지다** — 이게 이 기능에서 가장 오래 막힌 부분이다.

```
TourAPI 본체:        서울 = "1",  종로구 = "1"~"25"
집중률 API:          서울 = "11", 종로구 = "11110"   ← 행정표준코드
```

TourAPI 코드를 넣으면 **에러 없이 조용히 0건**이 온다. 그래서 한참 동안 "데이터가 없나 보다"라고 오해했다.

**시군구 단위 호출로 뒤집기**

집중률 API의 `tAtsNm`(관광지명)은 문서상 필수라고 적혀 있지만 실제로는 선택 필터다. 생략하면 그 시군구의 관광지 전체가 온다. 그래서 관광지 30개를 30번 호출하는 대신 **시군구 3~4번 호출로 전부 덮는다.**

**이름 매칭** — 집중률 API에는 `content_id`가 없고 관광지명이 사실상 유일한 키인데 표기가 조금씩 다르다. 단계적으로 느슨하게 맞춘다.

```
1) 그대로 비교           "덕수궁" = "덕수궁"
2) 공백 제거 후 비교      "경복궁 " → "경복궁"
3) 괄호 안 제거 후 비교   "남산서울타워(N서울타워)" → "남산서울타워"
```

매칭된 이름은 `spot_name`으로 함께 내려보내서, 앱이 **"덕수궁 기준"**이라고 밝힐 수 있게 했다. 다른 관광지 값을 슬쩍 보여주지 않기 위해서다.

**캐시는 자정까지** — 집중률은 하루 단위(`baseYmd`) 데이터라 자정 전에는 값이 바뀌지 않는다. 그래서 TTL을 "오늘 자정까지 남은 초"로 계산해 넣는다. 개발계정 일일 쿼터(1000회)를 아끼는 효과가 크다.

## 7. 사용한 기술

| 기술 | 용도 |
|---|---|
| TatsCnctrRateService (한국관광공사) | 관광지별 집중률 추이 예측 |
| 행정표준코드 | 집중률 API의 지역 파라미터 |
| `asyncio.gather` | 여러 시군구 동시 호출 |
| 정규표현식 | 관광지명 정규화(괄호·공백 제거) |

## 8. 문제와 해결

- **문제:** 집중률 API가 계속 빈 응답만 돌려줬다. 에러도 안 났다.
- **원인:** TourAPI의 `areaCode`(서울=1)를 그대로 넣었는데, 이 API는 **행정표준코드**(서울=11)를 쓴다. 잘못된 코드에도 200 OK에 0건으로 응답한다.
- **해결:** 한국관광공사가 배포한 시군구 코드 엑셀을 `region_codes.py`로 옮기고, 주소 문자열에서 시도·시군구를 뽑는 파서를 붙였다.
- **배운 점:** **"에러가 안 난다 ≠ 잘 되고 있다."** 공공데이터 API는 잘못된 파라미터에 빈 결과로 답하는 경우가 흔하다. 0건이 나오면 "데이터가 없다"고 결론 내기 전에 파라미터 체계부터 의심해야 한다.
  → 이 교훈은 하네스의 `bug-patterns.md`에 넣어야 할 유형이다("외부 API 0건 = 파라미터 체계 의심").

- **문제:** 강원·전북 지역이 계속 0건이었다.
- **원인:** 구코드(42/45)를 쓰고 있었다. 특별자치도 전환으로 신코드(51/52)만 유효하다.
- **해결:** 코드표를 신코드로 갱신.

## 9. 의사결정

| 쟁점 | 결정 | 근거 |
|---|---|---|
| 집중률과 현장 제보를 합칠까 | **절대 합치지 않는다.** 응답 필드부터 분리 | 예측과 실측은 성격이 다르다. 섞으면 두 정보가 모두 왜곡된다. 두 값이 다를 수 있다는 것 자체가 LiveSpot의 차별점이다 |
| 지도 마커 색상의 근거 | **집중률 예측만** | 모든 관광지에 값이 있어 마커가 비지 않는다. 제보를 섞으면 다시 "합쳐진 하나의 값"이 된다 |
| 등급 표현 | 집중률은 "여유/보통/**높음**", 제보는 "여유/보통/**혼잡**" | 말끝만 봐도 어느 쪽 데이터인지 구분되게 한다 |
| 0~100 → 3단계 구간 | 0-39 / 40-69 / 70-100 | 한국관광공사 공식 기준이 아니라 우리 서비스의 UX 기준이라, 코드 상수로 두고 언제든 바꿀 수 있게 함 |
| 응답을 DB에 저장할까 | **저장 안 함.** 메모리 캐시만 (자정까지) | [001](001-tourapi-spots.md)의 공공데이터 원칙 |
| 기존 병합 로직(`crowdedness.py`) | **폐기.** 파일은 남기되 "새로 쓰지 말 것" 주석 | 병합 자체가 지양 대상. 남은 시간대 휴리스틱은 근거가 약한 추측값 |

## 10. 배운 것

- 공공데이터는 같은 기관이라도 **API마다 코드 체계가 다를 수 있다.** 문서의 "필수/선택" 표기도 실제와 다를 수 있다(`tAtsNm`은 필수라고 적혀 있지만 실제로는 선택 필터였고, 그 덕에 시군구 단위 조회가 가능해졌다).
- 외부 API에 조회 키(`content_id`)가 없고 **이름이 유일한 키**일 때는, 매칭에 성공한 이름을 응답에 함께 실어 보내야 한다. 그래야 화면에서 "무엇 기준인지"를 정직하게 밝힐 수 있다.
- 호출 단위를 뒤집으면(관광지 30번 → 시군구 4번) 쿼터 문제가 통째로 사라진다.

## 11. 현재 한계

- 집중률 데이터가 없는 관광지는 `level: "unknown"`으로 온다. 서울 주요 관광지 중에도 예측 대상이 아닌 곳이 있다.
- 이름 매칭이 3단계 규칙이라, 표기가 크게 다르면 놓친다.
- `crowdedness.py`의 시간대 휴리스틱이 `/spots/{id}/crowdedness`, `/spots/{id}/briefing` 경로에 아직 남아 있다(앱은 쓰지 않는다).
- 상세페이지의 "출처가 다른 3블록 구분 표시"는 부분적으로만 반영됐다.
