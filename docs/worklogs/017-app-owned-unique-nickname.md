## 1. 한 줄 요약

카카오가 주는 닉네임을 쓰지 않고, **로그인한 사용자가 앱에서 직접 자기 닉네임을 정하게 하고 서버가 "이미 있는 이름"을 막는다.**

---

## 2. 왜 만들었는가

### 이 작업의 위치

016(카카오 로그인)을 끝냈을 때, 앱의 닉네임은 **카카오에서 받아온 값**이었다. 카카오에 "권영진"으로 돼 있으면 우리 앱에서도 "권영진"이고, 카카오에서 이름을 바꾸면 우리 앱 이름도 따라 바뀌었다. 중복도 허용했다 — 같은 이름을 쓰는 사람이 둘 있어도 그냥 뒀다(016의 P22).

그런데 사용자가 방향을 바꿨다. **"카카오 이름을 그대로 쓰는 게 아니라, 앱에서 쓸 이름을 따로 정하게 하고 싶다. 중복도 막아야 한다."** 그리고 한 발 더 나아가 **"카카오에서 닉네임도 프로필 사진도 아예 안 받겠다"** 고 했다. 카카오는 이제 "이 사람이 진짜 그 사람인지 확인해 주는 역할"만 한다.

그래서 이번 작업은 새 기능이라기보다 **016에서 확정했던 정책 하나(P22)를 뒤집는 후속 작업**이다. `function.md`의 기능 번호로는 여전히 3장 **기능 1(회원가입·로그인)** 안에 있다.

### 왜 굳이 뒤집었나

| 카카오 닉네임을 그대로 쓸 때의 문제 | 이번 변경으로 달라지는 것 |
|---|---|
| 제보·질문 목록에 같은 이름 두 사람이 나란히 뜨면 누가 누군지 모른다 | unique 제약으로 같은 이름이 둘 존재할 수 없다 |
| 카카오에서 이름을 바꾸면 우리 앱의 제보 작성자 이름이 소급해서 바뀐다 | 앱 닉네임은 사용자가 정한 뒤 우리가 보관한다. 카카오가 건드리지 않는다 |
| 실명이나 본명이 그대로 노출된다 | 여행 앱에서 쓸 별명을 따로 고를 수 있다 |
| 카카오 동의 화면에서 "닉네임·프로필 사진 제공" 동의를 받아야 한다 | 동의 항목이 **0개**가 된다. 로그인 화면이 훨씬 가벼워진다 |

### ⚠️ 이 작업의 진행 방식 (기록해 둘 것)

**이 세션에서 사용자가 직접 준 메시지는 없다.** 이전 세션에서 이미 명세 판정 → 백엔드·프론트 구현 → QA 1·2회차까지 다 진행된 작업을, 이번 세션에서 작업일지만 이어서 작성한 것이다.

그래서 아래 9절에 인용한 정책 원문은 **이번 대화에서 새로 받은 것이 아니라 `_workspace/01_spec.md` 2-0절에 기록돼 있던 것**이다. spec-arbiter가 이전 세션에서 받아 적어 둔 것이고, 그 파일이 사라지면 원문도 사라진다. 그래서 이 일지에 그대로 옮겨 놓는다.

## 3. 구현한 것

### 백엔드 (`livespot_backend/`)

- **`users.nickname`을 "비어 있을 수 있는 값"으로 바꾸고, 동시에 "같은 값이 둘일 수 없는 값"으로 만들었다** (nullable + unique). 이 두 가지가 동시에 성립하는 것이 이 작업의 핵심이다 — 아직 안 정한 사람은 비어 있고, 정한 사람끼리는 겹칠 수 없다.
- **닉네임 제출 API** `PUT /api/auth/me/nickname` 신설. 최초 설정과 나중의 변경을 **같은 엔드포인트**가 처리한다.
- **실시간 중복 확인 API** `GET /api/auth/nickname-available?nickname=...` 신설. 로그인 없이도 부를 수 있다.
- **닉네임을 안 정한 사람은 아무것도 쓸 수 없게 막았다.** 판정은 `deps.py` 함수 **한 곳**에서만 하고, 27개 라우터는 **한 줄도 안 바꿨다.**
- **닉네임 규칙을 `app/services/nickname.py` 한 파일로 모았다** — 정규화(앞뒤 공백 제거 + 유니코드 NFC) → 길이(2~12자) → 문자 집합(한글·영문·숫자·밑줄).
- **카카오 모듈을 "신원 확인 전용"으로 축소했다.** 닉네임·프로필 이미지를 가져오던 코드를 전부 지우고, 함수 이름을 `fetch_profile()` → `verify_and_get_kakao_id()`로 바꿨다.
- **재로그인 시 사용자 정보를 덮어쓰던 코드를 제거했다.** 이제 로그인이 `users` 행의 표시 값을 건드리는 경로가 하나도 없다.
- 마이그레이션 1건 (`2a65ad89e75b_app_owned_unique_nickname.py`).

### 프론트 (`livespot_app/`)

- **`web/index.html`에서 카카오 동의 항목 요청(`scope`)을 통째로 삭제했다.** 이 작업에서 **가장 먼저** 넣은 변경이다(이유는 9-3).
- **닉네임 설정 강제 모달** `lib/widgets/nickname_setup_gate.dart` 신설 — 실시간 중복 확인, 입력 검증, 제출, **로그아웃 버튼**.
- **닉네임 규칙 파일** `lib/utils/nickname_rules.dart` 신설 — 서버 `nickname.py`의 거울.
- **`NicknameRequiredException`** 추가 — "닉네임을 안 정해서 거부됨"을 예외 타입으로 표현.
- `AuthUser` 모델에 `nickname → String?` / `nicknameRequired` 추가.
- 프로필 카드 아바타를 **닉네임 첫 글자 이니셜**로 바꿨다(카카오 사진이 이제 항상 없으므로).

### 이번에 만들지 않은 것

| 제외 | 이유 |
|---|---|
| 욕설·비속어 필터 | 걸린 닉네임을 **고칠 도구가 프로젝트에 없다**(신고 기능도 관리자 화면도 없음). 한국어 욕설 필터는 오탐이 많아 정상 닉네임을 막는 피해가 더 크다. 나중에 붙일 자리는 `validate_nickname()` **한 곳**으로 고정해 뒀다 |
| 닉네임 변경 UI | 백엔드는 이미 변경까지 지원한다. 나중에 붙일 일은 **프론트 화면 하나뿐**이다 → 12절 |
| `users.profile_image_url` 컬럼 삭제 | 값은 항상 null이 되지만 컬럼은 남겼다. 이유는 9-6 |
| 앱 자체 프로필 이미지 업로드 | 사용자가 요청하지 않았다. `images.py` 라우터가 이미 있어 나중에 붙이기 쉽다 |
| 회원 탈퇴 / 닉네임 반납 | 016 그대로. 탈퇴가 없으므로 닉네임은 **영구 점유**된다 |

## 4. 동작 흐름

### 4-1. 처음 로그인 → 닉네임을 정하기까지

```
[카카오 로그인 버튼]
  → 카카오 팝업 (동의 화면이 없거나 아주 짧다 — 요청하는 동의 항목이 0개)
  → 카카오 access token
  → POST /api/auth/kakao
      → 서버가 카카오에 토큰 검증 (회원번호 하나만 받아온다)
      → 우리 DB에 없는 회원번호면 새 사용자 생성: nickname = None
      → JWT 발급
  → 응답: { access_token, is_new_user, user: { nickname: null, nickname_required: true, ... } }
  → AuthService가 _user를 세우고 notifyListeners()
  → app.dart의 ListenableBuilder가 needsNickname == true를 보고
  → 화면 전체를 덮는 NicknameSetupGate가 트리에 나타난다   ← 띄우는 코드가 없다. 그냥 존재한다
```

닉네임을 입력하는 동안:

```
사용자가 한 글자 입력
  → 400ms 기다림 (디바운스 — 타이핑 중에는 안 부른다)
  → GET /api/auth/nickname-available?nickname=...
  → { nickname: "정규화된 값", available: true/false, reason: "..." }
  → 입력창 아래에 초록(사용 가능) / 빨강(사용 불가) / 회색(확인 실패, 그래도 제출 가능)
```

제출:

```
[확인] 버튼
  → 앱이 먼저 로컬 검증 (nickname_rules.dart)  ← 뻔히 틀린 입력을 왕복시키지 않기 위한 편의일 뿐
  → PUT /api/auth/me/nickname { "nickname": "밤톨이_99" }
      → 서버: strip + NFC 정규화 → 길이 검사 → 문자 검사 → 중복 SELECT → INSERT
      → DB의 uq_users_nickname 제약이 최종 방어 (동시 제출 경합)
  → 200 { nickname: "밤톨이_99", nickname_required: false, ... }
  → AuthService가 _user를 통째로 교체 + notifyListeners()
  → needsNickname이 false가 됨
  → app.dart가 NicknameSetupGate를 트리에서 걷어낸다   ← 닫는 코드도 없다
```

**포인트:** 이 모달은 "띄우고 닫는" 것이 아니라 **`needsNickname`이 true인 동안 존재할 뿐**이다. 이게 왜 중요한지는 9-2.

### 4-2. 닉네임을 안 정한 사람이 뭔가 쓰려고 할 때

```
POST /api/reports (제보 작성)
  → Depends(get_current_user_id)      ← 27개 라우터가 전부 이것만 본다
      → 토큰에서 user_id 꺼냄 (여기까진 OK)
      → DB에서 User 로드 (같은 요청에서 이미 로드돼 있어 추가 쿼리 없음)
      → user.nickname is None ?
          → HTTP 403 { "detail": { "code": "NICKNAME_REQUIRED",
                                    "message": "닉네임을 먼저 설정해 주세요" } }
  → 앱 api_service.dart의 _apiError()
      → detail이 Map이고 detail['code'] == 'NICKNAME_REQUIRED' 이면
      → NicknameRequiredException을 던진다
  → 기존 화면의 catch (e) { ... e.toString() } 이 그대로 서버 문구를 보여준다
```

**403 상태코드만 보고 판정하면 안 된다.** 이 프로젝트는 403을 이미 다른 뜻으로 세 군데에서 쓴다 — 남의 질문 수정(`questions.py:242,260`), GPS 반경 밖 제보(`reports.py:77`). 그래서 `detail`을 **객체(dict)로 만든 것 자체가 계약의 일부**다. 기존 403들은 `detail`이 문자열이라 절대 헷갈리지 않는다.

### 4-3. 예외 세 곳

닉네임이 없어도 통과해야 하는 곳이 있다. 아니면 **"닉네임이 필요하다"는 사실 자체를 앱이 알 방법이 없어진다.**

| 엔드포인트 | 의존성 | 이유 |
|---|---|---|
| `GET /api/auth/me` | `get_current_user_id_any` | 여기서 403을 내면 앱이 `nickname_required`를 못 읽는다 |
| `PUT /api/auth/me/nickname` | `get_current_user_id_any` | 이 상태를 **푸는** 경로다. 막으면 영원히 못 푼다 |
| `GET /api/auth/nickname-available` | `get_current_user_id_optional` | 로그인 자체가 불필요 |

## 6. 핵심 코드 / 개념

### 6-1. "미설정"을 표현하는 방법을 하나로 못 박았다

닉네임을 아직 안 정한 상태를 어떻게 표현할까? 두 가지 방법이 있었다.

| 방법 | 문제 |
|---|---|
| `nickname_set` 불리언 컬럼을 따로 둔다 | **같은 사실의 출처가 둘**이 된다. 닉네임은 채웠는데 불리언을 안 바꾸면 두 값이 어긋난다 |
| **`nickname IS NULL` 하나로만 표현한다** ← 채택 | 출처가 하나뿐이라 어긋날 수가 없다 |

016에서 실제로 터진 버그 3건(F2·F3)이 전부 **"같은 사실의 출처가 둘이 되어 한쪽만 갱신된"** 계열이었다. 그래서 이번엔 처음부터 하나로 못 박았다.

앱 쪽도 마찬가지다. 화면이 `nickname == null`을 직접 해석하지 않는다 — 서버가 계산해 준 **`nickname_required` 불리언 하나만** 본다. 클라이언트가 정책을 추론하기 시작하면 서버와 앱의 판정이 언젠가 갈린다.

### 6-2. 유니코드 NFC — 눈에는 똑같은데 컴퓨터에는 다른 글자

이번 작업에서 가장 배울 게 많았던 부분이다.

한글 "밤"은 컴퓨터에 **두 가지 방식**으로 저장될 수 있다.

| 방식 | 저장 형태 | 코드포인트 개수 |
|---|---|---|
| **NFC** (조합형/완성형) | `밤` 한 글자 | **1개** (U+BC24) |
| **NFD** (분해형) | `ᄇ` + `ᅡ` + `ᆷ` 세 조각 | **3개** (U+1107, U+1161, U+11B7) |

**화면에는 완전히 똑같이 보인다.** 그런데 컴퓨터는 다른 문자열로 본다. Windows 한글 입력은 보통 NFC를, macOS/iOS 계열은 NFD를 만든다.

이게 왜 문제인가:

```
사용자 A(Windows)가 "밤톨이"로 가입    → DB에 NFC 3코드포인트로 저장
사용자 B(macOS)가 "밤톨이"로 가입      → NFD 8코드포인트 → DB는 "다른 값"이라고 판단
                                       → unique 제약을 그대로 통과한다!
결과: 화면에 "밤톨이"가 두 명 뜬다. 중복 방지 기능이 아무 일도 안 한 것이다.
```

그래서 **서버가 저장 직전에 반드시 NFC로 합친다**(P30). 이게 이번 unique 제약이 실제로 동작하기 위한 전제다.

### 6-3. 판정 지점을 하나로 유지하기 — 이 작업의 숨은 주제

016이 남긴 자산 덕분에 이번 변경이 놀랄 만큼 작았다.

### 6-4. 한글 정준 결합을 직접 구현한 것 (`composeHangul`)

Dart 표준에는 `String.normalize()`가 없다. 새 패키지를 넣을 수도 있었지만, **허용 문자 집합 안에서 NFC가 실제로 바꾸는 것은 한글뿐**이라 한글 결합만 직접 구현했다.

유니코드 표준(UAX #15 Hangul Syllable Composition)의 규칙은 딱 두 개다.

```dart
// ① 초성 + 중성 → 받침 없는 음절
//    ᄇ(U+1107) + ᅡ(U+1161) → 바(U+BC14)
out[last] = 0xAC00 + (초성번호 * 21 + 중성번호) * 28;

// ② 받침 없는 음절 + 종성 → 받침 있는 음절
//    바(U+BC14) + ᆷ(U+11B7) → 밤(U+BC24)
//    `sIndex % 28 == 0`이 "아직 받침이 없다"는 뜻 — 이미 받침 있는 글자에 또 붙이지 않는다
out[last] = last + 종성번호;
```

데이터 테이블이 전혀 필요 없는 **순수 산술**이다. 한글 음절 11,172자가 `0xAC00`부터 규칙적으로 배열돼 있기 때문에 가능하다.

**합쳐지지 않는 자모는 일부러 그대로 남긴다** — 그러면 뒤의 문자 집합 검사가 거부한다. 서버 동작과 정확히 같다.

### 6-5. `scope` 키 하나를 지우는 것이 왜 "선택이 아니라 필수"였나

사용자는 "카카오 콘솔에서 동의 해제할게"라고만 했다. 코드 얘기는 없었다. 그런데:

> 콘솔에서 동의 항목을 껐는데 코드가 계속 그 항목을 요청하면, **카카오는 `KOE205` 에러로 인가 요청 자체를 거부한다.** 로그인이 전면 실패한다.

즉 "닉네임 기능을 만들었더니 **로그인 자체가 안 되는**" 상황이 될 수 있었다. 그래서:

- **순서가 중요하다:** ① 코드에서 `scope` 제거 → ② 콘솔에서 동의 해제.
- 반대로 하면 그 사이의 모든 로그인이 실패한다. **코드를 먼저 넣으면 콘솔 변경 시점이 언제든 안전하다.**
- 그래서 이 한 줄 삭제가 **이번 작업에서 가장 먼저 들어간 변경**이다.

`''`로 비우지 않고 키를 통째로 지웠다. 카카오 SDK 소스(`kakao.js`)를 실제로 받아 확인한 결과 `if (settings.scope) { params['scope'] = settings.scope; }` — 값이 falsy면 파라미터를 아예 안 보낸다. 빈 문자열도 같은 결과지만 **"여기 뭔가 들어갈 예정"으로 읽혀 다음 사람을 헷갈리게 하므로** 키를 남기지 않았다.

### 6-6. 동의 항목을 전부 꺼도 인증은 약해지지 않는다

이걸 오해하기 쉽다. "동의를 하나도 안 받으면 검증도 약해지는 거 아닌가?"

**아니다.** 카카오에서 받아오는 두 값은 동의 항목이 아니라 **토큰 자체의 속성**이다.

| 값 | 출처 | 동의 필요? |
|---|---|---|
| 회원번호(`id`) | `/v2/user/me` | ✗ 항상 내려온다 |
| 앱 ID(`app_id`) | `/v1/user/access_token_info` | ✗ 항상 내려온다 |

016 6-5의 "다른 카카오 앱에서 발급된 토큰 차단"(`_verify_app_id()`)은 **그대로 살아 있다.** 이건 지우면 안 된다.

## 8. 문제와 해결

### 8-1. QA 1회차 F1 — nullable로 바꾼 값을 `as String`으로 캐스팅해 프로필 화면이 통째로 죽었다

- **문제**: 닉네임이 NULL인 테스트유저가 한 명이라도 있으면 **프로필 화면이 build 도중 TypeError로 죽는다**(회색/빨간 에러 화면). 게다가 테스트유저 전환 스낵바에는 `"테스트 유저 전환: null"`이 그대로 찍혔다.

- **원인**: `/api/dev/test-users`는 `response_model` 없이 dict를 그대로 내려준다(`{"id": u.id, "nickname": u.nickname}`). 앱은 이걸 `Map<String, dynamic>`으로 받는데 — **`Map<String, dynamic>`의 `[]`는 `dynamic`을 돌려주므로 `as String` 캐스트도, 문자열 보간도 컴파일러와 `dart analyze`가 전부 침묵한다.**

  더 아픈 것은, flutter-builder가 이미 "앱 전체를 `nickname`으로 재grep해서 남은 자리가 없음을 확인했다"고 적어 뒀다는 점이다. 실제로는 **모델 필드만 봤고 `dynamic` 슬롯을 빠뜨렸다.** 그리고 그 두 곳(드롭다운·스낵바)이 **각자 따로 캐스팅**하고 있어서 둘 다 틀렸다.

  이건 가설이 아니었다. `02_backend_contract.md` R4와 `03_flutter_wiring.md` R2가 **QA 재현 절차로 `UPDATE users SET nickname=NULL WHERE id='seed_user_30'`을 직접 지시한다.** 문서대로 따라 하는 순간 화면이 깨진다.

- **해결**: `profile_screen.dart:172`에 **`_testUserLabel(Map<String, dynamic>)` 헬퍼 하나를 만들고 두 호출부가 공유하게 했다.** 캐스팅 지점을 한 곳으로 모으는 것이 핵심이다.

  ```dart
  String _testUserLabel(Map<String, dynamic> user) {
    final nickname = user['nickname'] as String?;
    if (nickname != null && nickname.isNotEmpty) return nickname;
    final id = user['id'] as String?;
    return id == null ? '(닉네임 미설정)' : '$id (닉네임 미설정)';
  }
  ```

  폴백에 **id를 같이 넣은 이유**: 미설정 행이 둘 이상이면 라벨이 똑같아져 드롭다운에서 구분되지 않는다.

  **null 행을 걸러내는 방법은 일부러 택하지 않았다.** 그 행이 바로 "닉네임 미설정 사용자로 전환해 403과 강제 모달을 재현하는" QA 진입점이기 때문이다 — 걸러내면 검증 수단을 스스로 없애는 셈이다.

  QA 2회차에서 추가로 확인된 것: `orElse: () => {'id': userId}`로 만드는 **기본값 Map에는 `nickname` 키가 아예 없는데**, Dart에서 없는 키를 읽으면 `null`이므로 같은 헬퍼가 그 경우도 함께 막았다. **이게 F1의 두 번째 지뢰였다.**

- **배운 점**: 이 교훈은 `.claude/skills/livespot-contract/references/bug-patterns.md`의 **2-5절("NOT NULL 컬럼을 nullable로 바꿨는데 `Map<String, dynamic>`의 슬롯만 안 고쳐짐")**로 넣었다. 핵심 규칙은 *"nullable 전환 시 필드 이름을 전수 grep한 뒤, 히트를 **타입이 붙은 자리**와 **`dynamic` 자리**로 나눠 적는다 — `dynamic` 자리는 손으로 세는 것 말고 방법이 없다"*와 *"같은 필드를 두 곳 이상에서 캐스팅하면 헬퍼 하나로 모은다"*이다.

### 8-2. QA 1회차 F2 — 앱이 서버보다 규칙을 조여서, 정상적인 한글 닉네임이 거부됐다

- **문제**: macOS/iOS 계열에서 입력·붙여넣기한 한글(NFD 분해형)을 **앱이 서버보다 먼저 거부했다.** `밤톨이`를 넣으면 "닉네임에는 한글, 영문, 숫자, 밑줄(_)만 쓸 수 있어요"가 뜬다. **서버에는 요청이 아예 나가지 않는다.**

  그리고 이 화면은 **닫을 수 없는 전면 모달**이다. 사용자는 멀쩡한 한글 닉네임을 넣고도 로그아웃 말고는 앱에서 빠져나갈 길이 없었다. **불편이 아니라 앱이 잠기는 사고다.**

- **원인**: 서버는 `normalize_nickname()`으로 **정규화한 뒤에** 검사한다. 앱은 그 정규화 단계 없이 **같은 정규식과 같은 길이 제한만 복제했다.**

  ```
  NFC "밤톨이"    runes.length=3    정규식 통과=true    → 통과
  NFD "밤톨이"    runes.length=8    정규식 통과=false   → CHARSET 에러   ← 화면상 완전히 같은 글자다
  ```

  두 가지가 겹쳐 있었다. ① 정규식의 `ㄱ-ㅎ`/`ㅏ-ㅣ`는 **호환 자모**(U+3131~)인데 NFD가 만드는 것은 **결합 자모**(U+1100~)라 범위 밖이다. ② `runes.length`가 NFD에서는 자모 개수를 센다.

  03 배선 문서가 "서버보다 조이지 않았다"고 적은 문장이 **바로 이 자리에서 성립하지 않았다.**

- **해결**: 신규 `lib/utils/nickname_rules.dart`에 **한글 정준 결합을 직접 구현하고**, 서버와 **같은 순서**(정규화 → 길이 → 문자 집합)로 맞췄다.

  **QA가 제안한 수정(정규식에 결합 자모 범위 `ᄀ-ᇿ` 추가 + `characters.length` 사용)은 일부러 택하지 않았다.** 그 방법은 NFD 한글을 통과시키지만, **합쳐지지 않는 낱자 하나**(`ᄀ` U+1100 단독)까지 앱이 통과시킨다 — 그 값은 서버 정규식에 없으므로 결국 400으로 튕긴다. **판정이 여전히 갈린다.** 조건을 넓혀 맞추면 반대 방향의 불일치가 새로 생긴다.

  새 의존성도 안 썼다(`String.normalize`는 Dart 표준에 없다). 규칙을 **위젯 밖 별도 파일로 뺀 것**도 의도적이다 — 규칙을 위젯 안에 뒀던 것이 이 버그의 원인이었으므로, 화면이 하나 더 늘어도 같은 복제가 일어나지 않게 했다.

- **검증 (2회차에서 확인)**:
  - 지정 케이스 **38종 전부 일치** — 판정·정규화 결과 코드포인트·에러 문구까지 코드포인트 단위로 동일.
  - **한글 음절 전수 스윕 11,172자** (`U+AC00`~`U+D7A3`) — 각각을 NFD로 분해해 양쪽에 먹인 결과 **불일치 0건**.
  - 가장 중요한 숫자: **"서버 OK & 앱 거부" = 0건.** 앱이 잠기는 경로가 없다.
  - 앱 쪽 검증은 **실제 소스 파일을 `import`해서** 돌렸다 — 규칙을 복제한 검증 스크립트로 확인하면 "복제본은 맞는데 앱은 틀린" 1회차의 실패 모드를 그대로 반복한다.
  - 회귀 테스트 `test/nickname_rules_test.dart` **10/10 통과**. NFD 문자열은 소스에 직접 적지 않고 **코드포인트로 조립**한다 — 에디터·git·포매터 중 무엇이든 저장 시 NFC로 합쳐 버리면 **테스트가 조용히 아무것도 검증하지 않게 되고, 그래도 통과하므로 아무도 모른다.**

- **배운 점**: `bug-patterns.md`에 **13절("같은 검증 규칙을 서버와 앱 양쪽에 둘 때")**을 신설해 넣었다. 핵심 규칙 네 가지:
  1. 클라이언트 검증의 불변식은 **"서버가 허용하는 값을 앱이 먼저 거부하지 않는다"** 하나뿐이다. 앱 검증은 서버보다 **항상 느슨하거나 같아야** 한다.
  2. 규칙 복제는 조건이 아니라 **판정 파이프라인 전체를 순서까지** 복제한다.
  3. 규칙을 **위젯 안에 두지 않는다.** 별도 파일로 빼고 위젯은 함수만 부른다.
  4. 판정이 갈리면 **조건을 넓히지 말고 정규화를 맞춘다.**
  검증 방법도 함께 넣었다 — 양쪽을 같은 코퍼스로 **실제 실행**해 대조하고, `서버 OK & 앱 거부 = 0`을 숫자로 확인하며, 에디터가 바꿔 버리는 입력은 코드포인트로 조립한다.

### 8-3. 마이그레이션 단계 순서를 틀려서 실제로 실패했다

- **문제**: `NOT NULL constraint failed: users.nickname`
- **원인**: 기존 카카오 사용자의 닉네임을 NULL로 미는 `UPDATE`를, **nullable 전환보다 먼저** 실행했다.
- **해결**: 순서를 고정했다.
  1. **중복 사전 검사** — 중복이 있으면 **중복 닉네임 목록을 담은 한국어 `RuntimeError`로 중단**(이 시점엔 아무것도 안 바뀐다)
  2. `nickname` **nullable 전환**
  3. `UPDATE users SET nickname = NULL WHERE auth_provider = 'kakao'`
  4. `uq_users_nickname` **이름 있는** unique 제약 추가

  ②가 ③보다 먼저여야 하고, ③이 ④보다 먼저여야 한다(겹치는 닉네임이 남은 채 unique를 걸면 터진다).

  ①을 넣은 이유: **원시 `IntegrityError`는 "UNIQUE constraint failed"만 알려줘서 배포 도중에 원인을 찾을 수 없다.** 어느 닉네임이 겹치는지 말해 주는 쪽이 훨씬 낫다.
- **배운 점**: 마이그레이션은 각 단계가 **직전 단계의 결과 위에서만 성립**한다. 스키마 변경과 데이터 변경이 섞이면 순서를 표로 적고 시작한다. (이건 016 9-8이 세운 "이름 있는 제약을 준다" 규칙의 연장선이라 별도 규칙으로 추가하진 않았다.)

### 8-4. `test_user`·`seed_user_*` 31행을 NULL로 밀지 않은 것

- **문제가 될 뻔한 것**: "카카오 닉네임을 초기화한다"를 넓게 해석해 테스트유저까지 NULL로 밀었다면, `dev.py:46`의 `order_by(User.nickname)` 테스트유저 드롭다운이 통째로 무의미해진다. **다인원 QA의 유일한 진입점이 깨진다.**

### 9-1. 016의 P22를 폐기했다 — 단, 절반만

**갈림길**: 016 일지 9절이 확정한 P22와 이번 대화의 사용자 정책이 정면으로 충돌했다.

| | 016 P22 | 이번 정책 |
|---|---|---|
| 닉네임 출처 | 카카오 | **사용자 직접 입력** |
| 중복 | 허용, unique 없음 | **금지, unique 제약** |
| 식별 키로 쓰나 | 안 쓴다 (UUID만) | — (언급 없음) |

**판정**: 앞의 두 줄만 폐기한다. **"닉네임을 식별/매칭 키로 쓰지 않는다"는 그대로 살아 있다.**

**왜 세 번째 줄을 지키나**: unique를 걸었다고 닉네임으로 사용자를 조회하기 시작하면, 나중에 닉네임 변경 기능이 붙는 순간 **활동 이력이 끊긴다.** unique는 "같은 표시명이 둘 있으면 사람이 혼동한다"를 막는 **표시 계층의 제약**이지 식별 체계의 변경이 아니다. 모든 FK는 여전히 `users.id`(UUID)를 본다.

**버린 쪽**: "unique를 걸었으니 닉네임을 키로 써도 되지 않나"라는 유혹. 016의 P8(UUID 식별)·P4(카카오 ID 비노출)는 전부 불변으로 남겼다.

### 9-2. 닉네임 입력창을 "닫을 수 없는 모달"로 만들고, 그것을 `if`가 아니라 **구조로** 강제했다

**갈림길 ①** (Q1): 입력창을 닫을 수 있게 할 것인가.

- **A. 강제(닫기 불가)** ← 사용자 선택
- B. 취소 허용 + 기존 게이트 재사용 ← 판정관 권장

판정관은 B를 권했다. 이유는 ⓐ "보는 것은 자유, 참여는 로그인"이라는 P2의 정신, ⓑ 게이트를 한 곳에 유지한다는 016의 자산, ⓒ A는 서버 장애 시 **사용자가 모달에 갇힌다**. 사용자는 A를 택했다.

**A를 택한 대가를 어떻게 막았나**: 모달 안에 **로그아웃 버튼을 반드시 넣었다.** 이 화면의 유일한 탈출구이고, 코드에 "지우지 말 것"을 주석으로 명시했다.

**갈림길 ②** (구현 방식): "닫기 불가"를 어떻게 구현할 것인가. 여기가 실제 설계 판단이었다.

| 방식 | 문제 |
|---|---|
| `showModalBottomSheet` / `showDialog` + `PopScope` | 닫히는 경로가 **여럿** 생긴다 — 브라우저 뒤로가기, `Navigator.pop`, 바깥 탭, `PopScope` 우회. 전부 `if`로 막아야 하고, 하나라도 빠지면 새어나간다 |
| 라우트로 만들기 | 위와 같다 |
| **`MaterialApp.builder`의 Stack에서 Navigator 위에 겹치는 전면 레이어** ← 채택 | **닫는 경로가 구조적으로 존재하지 않는다.** 띄우고 닫는 코드 자체가 없다 |

**왜 다른 쪽을 버렸나**: 016 9-6이 이미 세운 규칙 — *"제약을 `if`로 숨기면 조건이 하나 바뀔 때 새어나간다"*(`bug-patterns.md` 6-1). 이번 것은 그 규칙의 두 번째 적용 사례다. `needsNickname`이 true인 동안 **존재할 뿐**이고, false가 되면 트리에서 사라진다. "언제 띄우고 언제 닫나"를 화면마다 관리할 일이 없다.

**부수 결정**: 파일 이름을 명세서의 `nickname_setup_sheet.dart` 대신 **`nickname_setup_gate.dart`**로 바꿨다. 시트가 아니게 됐는데 시트라고 이름 붙이면 다음 사람이 `showModalBottomSheet` 호출부를 찾게 된다. (016 9-8의 `firebase_uid` rename과 같은 이유.)

**부수 결정 2**: 알림 배너(`NotificationBannerHost`)보다도 **위**에 뒀다 — 닉네임을 정하기 전에는 알림도 조작할 수 없어야 한다.

### 9-3. 카카오 `scope` 한 줄 삭제를 이번 작업의 **가장 먼저** 넣었다

**갈림길**: 사용자는 "콘솔에서 동의 해제할게"라고만 했다. 코드 변경은 말하지 않았다. 그럼 코드는 안 건드려도 되나?

**판정**: **코드 변경이 필수다.** 콘솔만 끄면 `KOE205`로 **로그인이 전면 실패한다.**

**왜 순서가 이 방향인가**:

| 순서 | 결과 |
|---|---|
| ① 코드 제거 → ② 콘솔 해제 ← 채택 | 코드를 넣는 순간부터 안전. 콘솔 변경은 **언제 해도 된다** |
| ① 콘솔 해제 → ② 코드 제거 | 그 사이의 **모든 로그인이 실패한다** |

**버린 쪽**: "사용자가 콘솔을 바꿀 때까지 기다렸다가 같이 넣자"는 조율. 기다릴 이유가 없다 — 코드가 먼저면 순서 위험이 **통째로 사라진다.** 그래서 backend-builder가 자기 작업 범위가 아님에도 이 항목을 `02_backend_contract.md` 0절에 **F1(최우선)**으로 올려 flutter-builder에게 넘겼고, flutter-builder가 가장 먼저 처리했다.

**되돌림 방지**: `index.html` 주석에 **"scope 키를 다시 넣지 말 것 + 넣으면 KOE205로 로그인 전면 실패"**를 남겼다. 이 변경의 실제 위험은 다음 사람이 "동의항목을 왜 안 받지?" 하고 되돌리는 것이다.

### 9-4. 403의 `detail`을 문자열이 아니라 **객체**로 만들었다

**갈림길**: "닉네임 미설정"을 앱이 어떻게 알아채게 할 것인가.

| 방식 | 문제 |
|---|---|
| 403 상태코드로 판정 | **이미 못 쓴다.** 이 프로젝트는 403을 세 군데에서 다른 뜻으로 쓴다 — 남의 글 수정(`questions.py:242,260`), GPS 반경 밖(`reports.py:77`). 403만 보고 닉네임 시트를 띄우면 **"반경 밖입니다"가 닉네임 설정 화면으로 바뀐다** |
| 문자열 메시지를 파싱 | 문구가 바뀌면 깨진다 |
| **`detail`을 dict로 만들고 `detail['code']`로만 판정** ← 채택 | 기존 403 3곳은 `detail`이 **문자열**이라 구조적으로 헷갈릴 수 없다 |

**대가**: 앱의 `_extractErrorMessage`가 `detail`이 String/List인 두 경우만 처리하고 있었다. **Map 분기를 추가하지 않으면 403 본문이 "알 수 없는 오류"로 뭉개진다.** 그래서 backend-builder가 이것도 F2로 명시해 넘겼다.

**부수 결정**: `_apiError()`라는 **예외 변환 단일 지점**을 새로 만들었다. `on DioException` 블록 9곳이 전부 `throw Exception(_extractErrorMessage(e))`였는데, 각 메서드가 직접 `detail['code']`를 파헤치게 하면 **"어떤 실패를 호출부가 분기해야 하는가"의 판정이 40여 곳으로 흩어진다.**

단, **401은 여기서 변환하지 않았다.** 지금 그 구분이 필요한 것은 `fetchMe`뿐이고, 모든 호출부를 한꺼번에 `UnauthorizedException`에 노출시키면 **기존 화면들의 에러 문구 처리가 조용히 바뀐다.**

### 9-5. `PUT /auth/me/nickname` 하나가 최초 설정과 변경을 **둘 다** 처리한다

**갈림길** (Q4): 닉네임 변경 기능을 이번에 포함할 것인가. → **이번 범위 제외.**

**그런데 백엔드는 변경까지 지원하도록 설계했다.** 이유:

- 사용자가 요청한 문장은 최초 설정에 대한 것이고, 변경 기능을 지금 넣으면 **"변경 빈도 정책"(무제한? N일 1회?)이라는 새 결정이 하나 더 열린다.** 무제한 변경을 허용하면 "어제 그 제보자"를 추적할 수 없게 된다.
- 반대로 백엔드 엔드포인트를 미리 변경까지 커버하게 만드는 비용은 **거의 0**이다(같은 함수가 UPDATE를 하면 된다).
- 결과: 나중에 붙일 때 **백엔드 작업이 0**이고 프론트 화면 하나만 추가하면 된다. 붙일 자리도 확보돼 있다(`profile_screen.dart`의 메뉴 목록).

**부수 결정**: **같은 값을 다시 제출하면 409가 아니라 200**(멱등). `bookmarks.py`의 기존 규약("이미 된 것을 다시 POST해도 409가 아니라 200")을 그대로 따랐다. 자기 자신과의 충돌을 중복으로 내면 안 된다.

### 9-6. `users.profile_image_url` 컬럼을 지우지 않았다

**갈림길**: 카카오 프로필 사진을 이제 안 받으므로 이 컬럼은 영원히 `NULL`이다. 지울 것인가.

**판정: 남긴다.**

| | 지울 때 | 남길 때 |
|---|---|---|
| 파급 | 마이그레이션 1건 추가 + 응답 스키마 + Dart 모델 + `_buildAvatar` 시그니처가 **함께** 바뀐다 (이번 변경의 파급이 두 배) | 빈 컬럼 하나 |
| 얻는 것 | 빈 컬럼 하나가 사라짐 | — |

**왜 다른 쪽을 버렸나**: **사용자가 요청한 것은 "닉네임 커스텀 입력 + 로그인 식별"이지 스키마 정리가 아니다.** 명세에 없는 것을 구현자가 확대 해석하면 검증 범위가 늘고 위험만 커진다. 그리고 **앱 자체 프로필 이미지 업로드가 나중에 붙을 때 이 자리가 그대로 쓰인다**(`images.py` 라우터가 이미 있다).

**딸려온 결정 (P41)**: 프로필 사진이 항상 null이 되면 **로그인 사용자 전원이 똑같은 회색 사람 아이콘**이 된다. 오늘 카카오 사진이 뜨던 자리가 눈에 띄게 비어 보인다. 그래서 아바타에 **닉네임 첫 글자 이니셜**을 넣었다 — 닉네임이 이제 **고유**하므로(P24) 이니셜은 실제 구분 정보를 담는다. 비용은 위젯 하나 안의 10줄 남짓이고 API·스키마 변경이 없다. **`imageUrl != null` 분기는 지우지 않았다** — P40대로 그 자리는 보존한다. 폴백 순서는 `이미지 → 이니셜 → person 아이콘` 3단이다.

### 9-7. `fetch_profile()`을 `verify_and_get_kakao_id()`로 이름을 바꿨다

**갈림길**: 함수 내부만 고치고 이름은 둘 것인가.

**판정: 바꾼다.** 이 함수는 이제 **프로필을 가져오지 않는다.** `fetch_profile`이라는 이름이 **거짓말이 된다.**

016 9-8이 `users.firebase_uid` 컬럼을 정확히 같은 이유로 rename하면서 세운 규칙 — *"이름이 틀리면 다음 사람이 매번 코드를 읽어야 의미를 알 수 있다"* — 의 **두 번째 적용 사례**다. `KakaoProfile` 데이터클래스와 `_FALLBACK_NICKNAME` 상수도 함께 삭제했다.

**지우지 않은 것**: `_verify_app_id()` 전체, `id` 누락 시 `KakaoAuthError`, 401(토큰 무효)/502(카카오 서버 장애) 구분. **동의 항목을 전부 꺼도 인증 강도는 전혀 안 낮아진다**(6-6). 이걸 오해해서 `_verify_app_id()`를 지우면 다른 카카오 앱의 토큰으로 우리 앱에 로그인할 수 있게 된다.

### 9-8. unique를 대소문자 구분으로, 이름 있는 제약으로 걸었다

**갈림길**: `Abc`와 `abc`를 같은 닉네임으로 볼 것인가.

| 방식 | 문제 |
|---|---|
| `lower(nickname)` 함수 기반 유니크 인덱스 | **SQLite와 PostgreSQL에서 함수 인덱스 표현이 갈린다.** 016 9-8이 이미 "이름 없는/방언 의존 제약을 뗐다 붙이는 마이그레이션의 위험"을 기록해 뒀다 |
| **정규화된 원문 그대로, 대소문자 구분** ← 채택 | 방언 의존이 없다 |

**알려진 대가로 남긴다**: 나중에 대소문자 무시로 바꾸려면 **마이그레이션 1건이 필요하다.** 숨기지 않고 정책 문서에 적어 뒀다.

**제약에 `uq_users_nickname`이라는 이름을 준 이유**: 이름이 없으면 **SQLite batch 모드에서 떼어낼 수 없다.** 016 9-8의 교훈 그대로다.

### 9-9. 닉네임 글자 규칙을 처음부터 엄격하게 조였다

**갈림길** (Q3): 2~12자 한글·영문·숫자·밑줄만(엄격) vs 2~16자 + 내부 공백(표준) vs 2~20자 이모지 포함(느슨).

**판정: 엄격.**

**왜**: **나중에 조이는 것이 비싸고 나중에 푸는 것이 싸다.**

- 허용 문자를 나중에 조이면 **이미 만들어진 닉네임이 규칙 위반 상태로 남는다** — 그걸 고칠 도구가 이 프로젝트에 없다(신고 기능도 관리자 화면도 없음). 유일한 구제 수단이 DB 직접 수정이 된다.
- 반대로 나중에 푸는 것은 아무 문제가 없다.
- 그리고 이 앱의 닉네임은 **제보 신뢰도를 판단하는 라벨**이지 자기표현 수단이 아니다. 조인다고 잃는 것이 거의 없다.
- 표준안(내부 공백 허용)을 버린 이유: **"권 영진"과 "권영진"이 다른 닉네임으로 공존해** 육안 구분이 어려워진다. 중복 방지를 하겠다면서 육안으로 같은 이름을 허용하는 것은 모순이다.

**구현 판단 하나**: 호환 자모(`ㄱ-ㅎ`, `ㅏ-ㅣ`)를 허용했다. `"ㅋㅋ"`는 사용자에게 명백히 한글이고, 막으면 납득하기 어려운 거절이 된다. 더 조이려면 `nickname.py`의 `_ALLOWED_RE` **한 줄**이다.

**저장 컬럼은 `String(50)` 그대로 뒀다.** 검증에서만 12자로 자른다 — 컬럼 축소 마이그레이션은 위험 대비 이득이 없다.

### 9-10. 욕설 필터를 넣지 않았다

**갈림길**: 닉네임을 사용자가 정하게 하면 욕설 필터가 필요해 보인다.

**판정: 넣지 않는다.**

**왜**:
1. 필터를 붙이면 **"걸린 닉네임을 누가 어떻게 고치는가"**가 곧바로 필요해진다. 그런데 이 프로젝트에는 **신고 기능도 관리자 도구도 없다.** 유일한 구제 수단이 DB 직접 수정이 된다.
2. 한국어 비속어 필터는 **오탐률이 높다.** 정상 닉네임을 막는 쪽의 피해가 더 크다.

**대신 한 것**: 나중에 붙일 자리를 **`validate_nickname()` 안 한 곳**으로 고정해 뒀다. 차단 목록을 추가하는 작업이 파일 하나로 끝나게.

### 9-11. 실시간 중복 확인을 추가했다 — 단, 그것은 **조언일 뿐**이다

**갈림길** (Q2): 제출 시점에만 중복을 볼 것인가, 실시간으로도 볼 것인가.

**판정: 실시간 확인 API 추가.** 이 기능의 본질이 "사용자가 이름을 고르게 하는 것"인데 고르는 과정이 시행착오면 기능 자체의 체감 품질이 떨어진다. "여행자" 같은 흔한 이름을 고른 사용자는 3~4번 제출-실패를 반복하게 된다. 게다가 디바운스 선례(`spot_search_delegate.dart`)가 이미 있어 프론트 비용이 낮았다.

**그런데 DB unique 제약 + 409는 어느 쪽을 고르든 필수다.** 확인과 제출 사이에 남이 선점할 수 있으므로 **동시 제출 경합은 서버만 막을 수 있다.** 그래서 서버는 409를 **두 번** 판정한다 — 사전 `SELECT`(친절한 문구용) + DB `IntegrityError` 포착(실제 방어). 앱도 실시간 확인이 초록불이었어도 제출 시 409를 별도로 처리한다.

**부수 결정 3개**:

| 결정 | 이유 |
|---|---|
| 이 API는 **로그인 불필요** | 닉네임은 제보·질문 목록에서 **이미 공개로 표시되는 값**이라 새로 새는 정보가 아니다 |
| **형식 위반도 200**(400이 아니다) | 타이핑 도중의 1자 상태는 에러가 아니라 **아직 판정할 수 없는 상태**다. 매 키 입력마다 4xx가 쌓이는 것도 좋지 않다 |
| 확인 API 실패는 **회색 + 제출 허용**(빨강 아님) | **네트워크 실패를 "쓸 수 없는 닉네임"으로 보여주면 멀쩡한 닉네임을 사용자가 스스로 포기한다.** 에러 상태와 불가 상태의 화면을 다르게 한다(`bug-patterns.md` 1-1의 연장) |

### 9-12. 기존 카카오 사용자 1명의 닉네임을 NULL로 밀었다

**갈림길** (Q5): 이미 카카오 닉네임을 가진 사용자 1명(실측: 로컬 DB 32행 중 카카오 1명, 테스트유저 31명)을 어떻게 할 것인가.

**판정: NULL로 초기화.**

| | NULL로 민다 ← 채택 | 그대로 둔다 |
|---|---|---|
| 얻는 것 | **"앱 닉네임은 반드시 사용자가 고른 값"이라는 불변식에 예외가 없다.** 덤으로 새 흐름을 실제 계정으로 한 번 밟게 되어 QA가 된다 | 사용자가 재입력할 필요 없음 |
| 잃는 것 | 재입력 한 번(본인 계정 1개뿐) | 그 1행만 **닉네임 출처가 카카오**인 채로 남아, 나중에 "이 값은 어디서 왔나"를 설명할 수 없는 예외가 된다 |

**대상이 1행이고 복구가 재입력 한 번이다.** 데이터 예외를 하나 남기는 비용이 그보다 크다.

**함께 판정한 것**: `test_user`·`seed_user_*` 31행은 **건드리지 않는다.** 카카오에서 온 값이 아니고, `dev.py:46`이 `order_by(User.nickname)`으로 테스트유저 드롭다운을 그린다 — NULL로 밀면 **다인원 QA 진입점이 깨진다.** (8-4 참조)

### 9-13. QA 1회차 F2 수정에서 **QA의 제안을 따르지 않았다**

**갈림길**: QA는 구체적 수정 방법을 제시했다 — 정규식에 결합 자모 `ᄀ-ᇿ`를 더하고 `runes.length`를 `characters.length`로 바꾼다.

**판정: 따르지 않고 정규화를 구현했다.**

**왜 다른 쪽을 버렸나**: QA 제안은 NFD 한글을 통과시키지만, **합쳐지지 않는 낱자 하나**(`ᄀ` U+1100 단독)까지 앱이 통과시킨다. 그 값은 서버 정규식에 없으므로 결국 400으로 튕긴다 — **판정이 여전히 갈린다.** 방향만 반대가 될 뿐이다.

**QA 2회차가 이 판단을 실측으로 확인했다**: 38종 케이스 중 13·14·15번(LV+종성, LVT+잉여 종성, NFD LVT+잉여 종성)이 **QA 제안을 택했으면 갈렸을 자리**다. 검증관이 자기 1회차 제안보다 구현자의 판단이 맞았다고 리포트에 적었다.

**배울 점**: QA 리포트의 "수정 방법"은 **증상을 없애는 최소 변경**이지 반드시 최선의 설계는 아니다. 제안을 그대로 적용하기 전에 **"이 수정으로 불일치가 정말 0이 되는가"를 반대 방향으로도 물어야** 한다.

## 10. 배운 것

### 10-1. 유니코드는 "보이는 것"과 "저장된 것"이 다를 수 있다

가장 크게 배운 것이다. 화면에 똑같이 보이는 "밤"이 **1개 코드포인트일 수도, 3개일 수도** 있다. 입력 환경(Windows vs macOS/iOS)에 따라 다르다.

**그래서 문자열로 "같은가"를 판정하는 모든 자리에는 정규화가 필요하다** — unique 제약, 로그인 아이디, 검색, 중복 체크. 정규화 없이 unique를 걸면 **제약이 있는데도 중복이 들어온다.**

### 10-2. 한글 음절 11,172자는 규칙적인 산술로 배열돼 있다

`U+AC00`("가")부터 `U+D7A3`("힣")까지, `초성 19 × 중성 21 × 종성 28 = 11,172`개가 정확히 그 순서로 놓여 있다. 그래서 자모를 합치는 것이 **데이터 테이블 없이 곱셈과 덧셈만으로** 된다.

```
음절 = 0xAC00 + (초성번호 × 21 + 중성번호) × 28 + 종성번호
```

이 구조 덕분에 NFC 전체를 구현하지 않고 **한글 부분만** 40줄 남짓으로 만들 수 있었다.

### 10-3. "판정 지점 하나"는 만드는 것보다 **지키는 것**이 어렵다

016이 `deps.py` 한 곳과 `ensureLoggedIn` 한 곳을 만들어 놨기 때문에, 이번 변경이 27개 라우터와 12개 게이트 호출부를 **한 줄도 안 건드리고** 끝났다.

그런데 지키는 쪽은 매 순간 판단이 필요했다:
- 게이트 위젯에서 성공 후 `Navigator.pop`을 부르고 싶어진다 → **그게 곧 두 번째 판정 지점이다.** 안 부른다.
- `ensureLoggedIn()`에 닉네임 검사를 넣고 싶어진다 → **강제 모달이 이미 처리한다.** 넣으면 판정이 둘이 된다.
- 화면에서 `nickname == null`을 직접 보고 싶어진다 → **`nickname_required`만 본다.**

QA가 `grep -rn "needsNickname"`으로 **정의 1곳 + 사용 1곳**임을 실측으로 확인한 것이 이 원칙이 지켜졌다는 증거다. **"판정 지점이 하나인가"는 주장이 아니라 grep으로 세는 숫자여야 한다.**

### 10-4. 컴파일러가 안 잡는 자리가 어디인지 알아야 한다

Dart에서 타입 검사를 조용히 빠져나가는 세 자리:

| 자리 | 예 | 왜 안 잡히나 |
|---|---|---|
| `Map<String, dynamic>`의 `[]` | `u['nickname'] as String` | `[]`가 `dynamic`을 돌려준다 |
| 문자열 보간 | `'전환: ${u['nickname']}'` | `dynamic`은 아무거나 `toString()`된다 |
| `dynamic` 슬롯의 Map 리터럴 | `{'subtitle': user!.nickname}` | 값 타입이 `dynamic`이다 |

**이번에 세 자리가 전부 나왔다.** 명세서가 미리 세 번째 자리를 경고했고(`profile_screen.dart:687`), flutter-builder가 그걸 고치면서 두 번째 자리도 함께 찾았는데, **QA가 첫 번째와 두 번째의 또 다른 인스턴스를 잡아냈다.**

`dart analyze`가 조용한 것은 **안전하다는 근거가 아니다.**

### 10-5. "안 조였다"는 주장은 실행해서 대조해야 한다

03 배선 문서가 "서버보다 조이지 않았다"고 적었을 때, 그건 **코드를 읽고 내린 판단**이었다. 실제로는 한 단계가 빠져 있었다.

2회차에서 한 것은 **양쪽을 실제로 실행해 같은 입력을 먹이는 것**이었다 — python `validate_nickname()` vs `dart run` `validateNickname()`, 11,177 케이스. 그리고 앱 쪽은 **실제 소스 파일을 import**했다(복제본으로 검증하면 원래의 실패 모드를 반복한다).

집계할 숫자는 두 개다: **서버 OK & 앱 거부 = 0**(앱이 잠기는 사고), 앱 OK & 서버 거부(헛왕복일 뿐).

### 10-6. 테스트 입력이 "저장될 때 바뀌는" 경우가 있다

NFD 문자열을 테스트 소스에 그대로 적으면, 에디터·git·포매터 중 무엇이든 저장하면서 NFC로 합쳐 버릴 수 있다. 그러면 **테스트가 아무것도 검증하지 않게 되는데, 통과하므로 아무도 모른다.**

그래서 `_nfd([0x1107, 0x1161, 0x11B7, ...])`처럼 **코드포인트로 조립**했다.
