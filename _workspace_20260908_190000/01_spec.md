### (2) 크레딧을 적립할 "트리거" 후보 — 코드상 **딱 2개뿐이다**

사용자 활동을 DB에 쓰면서 `user_id`를 남기는 경로를 전수 조사한 결과:

| 경로 | 코드 | `user_id` 남는가 | 적립 트리거 적격 |
|---|---|---|---|
| 현장 제보 | `api/reports.py:42` `create_report` | ✅ `Report.user_id` | ✅ **후보 1** |
| Q&A 답변 | `api/questions.py:150` `create_answer` | ✅ `Answer.user_id` | ✅ **후보 2** |
| Q&A 질문 | `api/questions.py:75` `create_question` | ✅ `Question.user_id` | ⬜ 정책상 0점 (기록만) |
| 리뷰 | `api/reviews.py:15` `create_review` | ❌ **작성자 개념 자체가 없다.** `_reviews_db = []` 메모리 리스트에 쌓고 `ReviewResponse`에 `user_id` 필드가 없다 | ❌ **기술적으로 불가.** 적립 대상에서 제외 |
| 알림 설정 on/off | `api/notifications.py` | ✅ | ❌ 정보 생산이 아님 |
| LIVE 체크인 / 현장 인증 | `POST /reports/verify-location` (`reports.py:107`) | ❌ **아무것도 저장하지 않는다.** 거리 계산 후 응답만 반환하는 순수 함수. `presence` 테이블(기능 6)은 미구현 | ❌ 이번 범위 밖 (기능 6 선행 필요) |

→ **"LIVE 체크인 적립"은 이번에 만들 수 없다.** 체크인을 기록하는 테이블(`presence`, 기능 6, 구현 순서 6단계)이 아직 없기 때문이다. 이 사실이 Q2(뱃지 종류)의 선택지를 제약한다 — "N곳 방문" 류의 뱃지는 지금 계산할 근거 데이터가 없다.

**두 트리거의 코드 형태 (구현자가 반드시 알아야 할 것):**

- `create_report`는 **early-return이 2개** 있다: `client_request_id` 중복 조회(`reports.py:53`)와 `IntegrityError` 롤백 후 재조회(`reports.py:91`). **이 두 경로에서 크레딧을 다시 주면 중복 지급이 된다.** 실제 저장은 `db.add(new_report)`(`:84`) → `await db.commit()`(`:86`) 한 곳뿐이다.
- `create_answer`는 `db.add(answer)`(`:196`) → `question.answer_count += 1`(`:197`) → `await db.commit()`(`:198`)로 **이미 한 트랜잭션**이다. 여기에 원장 행을 add하면 `function.md:112`가 요구한 트랜잭션 경계가 자동으로 지켜진다.
- ⚠️ **`create_answer`에는 `client_request_id` 같은 멱등 장치가 없다.** 006 일지 11절이 이미 이 구멍을 명시해 뒀다: *"한 사람이 한 질문에 여러 번 답해서 Credit 반복 수령을 막는 DB 제약이 없다(Credit이 없으니 아직 문제가 안 됨)."* — **크레딧이 붙는 순간 이게 실제 문제가 된다.** 정책상 복수 답변은 허용이므로, 막을 곳은 답변이 아니라 적립이다. → Q4.

### (3) 사용자 인증/식별 체계 — **스키마는 완비, 실제 로그인은 없음. 그리고 이게 최우선 선결 과제는 아니다.**

| 항목 | 상태 |
|---|---|
| `users` 테이블 | ✅ 존재 (`db/models/user.py`). `id`(UUID) · `firebase_uid` · `nickname` · **`credit_balance: int = 0`** · **`trust_level: str = "NEWCOMER"`** · `created_at` |
| `reports.user_id` / `questions.user_id` / `answers.user_id` | ✅ 전부 `ForeignKey("users.id")`로 연결돼 있다 |
| 현재 작성자 판정 | `api/deps.py` `get_current_user_id()` — **평상시 무조건 `TEST_USER_ID`(`00000000-…-0001`) 고정 반환.** `settings.TEST_MODE=True`일 때만 `X-Test-User-Id` 헤더로 전환 |
| 앱 쪽 로그인 | `services/auth_service.dart` — 전부 주석 처리된 **더미**. `signInAnonymously()`가 1초 `Future.delayed`만 한다. `providers/auth_provider.dart`의 `authStateProvider`는 항상 `false` 상수 |
| 프로필 화면 로그인 버튼 | `screens/profile/profile_screen.dart:156-158` — 카카오·Google 버튼 2개, **둘 다 `onTap: () {}` 빈 콜백** |

**판정: 크레딧 귀속에 필요한 것(사용자 행·FK·닉네임 조인)은 이미 전부 있다.** `credit_ledger.user_id → users.id` FK를 거는 데 로그인은 필요 없다. `function.md:246-248`이 로그인을 맨 뒤(9단계)로 미룬 이유가 정확히 이것이다 — *"`users` 테이블 스키마는 이미 있어서 마지막에 `deps.py` 하나만 교체하면 된다."*

**단, 실사용 체감은 다르다.** 프로덕션 설정(`TEST_MODE=False`)에서는 **모든 방문자가 한 명(`test_user`)으로 합쳐진다.** 즉 크레딧을 붙여도 "내 크레딧"이 "전 세계 공용 크레딧"이 된다. 데모에서 두 기기로 접속하면 같은 숫자가 보인다. → 이 체감 문제를 이번에 어떻게 다룰지가 **Q5**다.

### (4) 재사용 가능한 기존 DB 모델/스키마

- **`users.credit_balance` 컬럼이 이미 있다** (마이그레이션 `038a46869fc7`에 포함). `function.md:106`이 말한 "빠른 조회용 캐시"가 **이미 만들어져 있는 셈**이라, 잔액 캐시에는 마이그레이션이 필요 없다.
- `users.trust_level` (기본값 `"NEWCOMER"`)도 있다. 다만 이 어휘("NEWCOMER")는 기능 11의 뱃지 어휘(새싹/탐방객/…)와 **다른 체계**다 → 3절 C3 판정 참조.
- Alembic 체인 head = **`9285c2232240`** (`add_questions_and_answers_tables`). 새 마이그레이션의 `down_revision`은 이 값이다.
- `app.main`에는 `Base.metadata.create_all`이 **없다.** 테이블 생성 경로는 Alembic 단독 → 마이그레이션을 빼먹으면 런타임에 `no such table`로 터진다.
- `services/report_window.py` — "오늘(KST)" cutoff 계산이 이미 공유 모듈로 추출돼 있다. **일일 적립 상한의 "하루"를 여기서 가져다 쓰면 Q&A·LIVE·브리핑과 하루 경계가 갈리지 않는다.**

### (5) 보너스 — 009 일지가 남긴 검증 차단 요인은 해소됐다

009 일지 8절 문제 4는 *"`apis.data.go.kr`로의 TCP 연결이 타임아웃 → TourAPI 경유 엔드포인트가 실서버에서 전부 404"*를 기록했다. 이번에 확인한 결과 **아웃바운드가 복구됐다** (`apis.data.go.kr` HTTP 401 = 키 없이 호출해 거부된 정상 응답, 0.19초).

이게 이번 기능에 중요한 이유: `create_report`와 `create_answer`는 **둘 다 내부에서 `tour_service.get_spot_detail()`을 호출**한다(GPS 거리 판정용). TourAPI가 죽어 있으면 두 트리거 엔드포인트가 404를 내서 **크레딧 적립을 실물로 스모크할 수 없다.** 지금은 가능하다.

### Q1. 크레딧 적립 기준 — 어떤 행동에 몇 점?

- **맥락**: 트리거는 제보·답변 2개로 확정됐지만(0-(2)), **금액이 문서마다 다르다.** `function.md` 기능 4는 제보 +10 / 답변 +5, 지난 일지 002·006은 제보 +30 / 답변 +50을 인용한다. **두 안은 제보와 답변의 우열이 정반대**라 임의로 못 고른다. 금액은 원장에 그대로 기록되므로, 나중에 바꾸면 이미 쌓인 행과 새 행의 기준이 섞여 "왜 저번엔 30이었죠?"를 설명할 수 없게 된다. 그리고 이 값이 Q2(뱃지 컷)의 눈금을 결정한다.

- **선택지 A — 제보 +10 / 답변 +5 / 질문 0** (`function.md` 확정안, **권장**)
  → 원칙: *"제보가 이 서비스의 본체"*. 답변은 제보보다 가볍고(텍스트 1줄) 하루에 여러 건 쓸 수 있어 낮게 둔다. 뱃지 500점 = 제보 50건 ≈ 진짜 헤비유저. 등급이 천천히 오르므로 5단계가 의미를 가진다.
  → 구현 난이도: 동일. 상수 2개.

- **선택지 B — 제보 +30 / 답변 +50 / 질문 0** (지난 일지가 인용하던 값)
  → 원칙이 뒤집힌다: *"남을 직접 돕는 답변이 가장 가치 있다"*. Q&A 활성화에 유리.
  → 부작용: **답변이 가장 비싼 행동이 되는데, 답변에는 `client_request_id` 같은 멱등 장치가 없다**(C7). 어뷰징 유인이 가장 큰 행동이 가장 방어가 약한 상태가 된다 → Q4의 답이 반드시 "질문당 1회"여야 안전하다.
  → 뱃지 500점 = 제보 17건 또는 답변 10건. **현재 5단계 컷을 그대로 쓰면 몇 번의 활동으로 마스터가 되어 등급이 무의미해진다** → Q2에서 컷 재조정 필수.
  → 구현 난이도: 동일. 단 Q2·Q4가 B에 종속된다.

- **선택지 C — 제보 +10 / 답변 +10 / 질문 0 (동일 가중)**
  → 정책 논쟁을 피하고 "정보를 생산하면 같은 값" 한 문장으로 설명된다. 뱃지 컷 재조정 불필요(A와 눈금이 비슷).
  → 잃는 것: `function.md:103`이 세워둔 *"질문은 요청, 답변은 기여"* 서사에서 제보/답변의 층위 구분이 사라진다.

- **권장: A.** 이유 세 가지 — ① `function.md` 기능 4에 근거 문단까지 딸린 유일한 안이고, ② 뱃지 5단계 컷(Q2 권장안)과 이미 눈금이 맞춰져 있어 Q2를 함께 확정할 수 있고, ③ 답변이 가장 싼 행동이 되므로 멱등 장치가 없는 `create_answer`(C7)의 어뷰징 유인이 구조적으로 가장 작다.

### Q2. 뱃지 — 무엇을 기준으로, 몇 단계로?

- **맥락**: 사용자가 "뱃지 종류/조건 미정"이라고 했다. `function.md` 기능 11은 **누적 크레딧 단일 축 5단계**를 제시한다. 대안은 **행동별 업적 뱃지**(첫 제보, 제보 10건, 답변 10건, …)다. 이 선택이 데이터 모델을 바꾼다 — 단일 축은 원장 합계 하나로 끝나지만, 업적형은 행동별 카운트를 각각 세야 하고 "획득 시점"을 남길지도 정해야 한다. 되돌리기 비싸다.
  ⚠️ **제약**: "N곳 방문", "연속 출석" 류는 **지금 만들 수 없다.** 방문 기록(`presence`, 기능 6)이 아직 없다(0-(2)).

- **선택지 A — 누적 크레딧 5단계** (`function.md` 확정안, **권장**)
  `0~49 🌱새싹 / 50~99 📍Spot 탐방객 / 100~199 🧭Spot 탐험가 / 200~499 🏆베테랑 / 500+ 👑마스터`
  → 구현: **테이블 0개, 새 쿼리 1개**(원장 합계). 뱃지 로직 전체가 함수 하나(등급표 상수 + 이분 탐색). 1.5일 일정에 여유가 남는다.
  → 화면: 마이 화면에 뱃지 1개 + "다음 등급까지 N점" 진행바. 단순하고 즉시 이해된다.
  → 잃는 것: 답변만 열심히 한 사람과 제보만 한 사람이 구분되지 않는다.
  → ⚠️ **Q1에서 B를 고르면 이 컷은 그대로 쓸 수 없다** (제보 17건에 마스터).

- **선택지 B — 누적 크레딧 5단계 + 행동별 업적 뱃지 3~5종 (병행)**
  예: `🥇 첫 제보` / `📢 제보 10건` / `🙌 답변 10건` / `🌍 관광지 5곳 제보`
  → 구현: 등급 뱃지 + 업적 판정 로직. `reports`/`answers`에 `COUNT`·`COUNT(DISTINCT spot_content_id)` 쿼리 추가(인덱스는 이미 있음). **획득 시점을 남기려면 `user_badges` 테이블 + 마이그레이션 1개 추가**, 안 남기면 매 조회 계산(P4 원칙과 일치, 권장).
  → 화면: 뱃지 그리드 + 미획득 회색 처리. 게이미피케이션 효과는 A보다 확실히 크다.
  → 비용: **백엔드·프론트 양쪽 대략 +0.5~1일.** 1.5일 일정이 2~2.5일이 된다.

- **선택지 C — 업적 뱃지만, 등급 없음**
  → 크레딧과 뱃지가 분리돼 "크레딧은 왜 쌓나?"에 답할 게 없어진다. 소비처를 안 만들기로 확정한 상태(C8)라 **크레딧이 목적을 잃는다.** 비권장.

- **권장: A.** 이유 — ① 소비처가 없는 확정 구조에서 "크레딧 → 뱃지"라는 단일 서사가 크레딧의 유일한 존재 이유이고, ② 테이블·마이그레이션이 추가로 안 생겨서 1.5일 일정 안에 들어가며, ③ 나중에 B로 확장할 때 A를 버릴 필요가 없다(업적을 옆에 덧붙이면 된다). **다만 Q1에서 B(+30/+50)를 고르면 컷을 `0/150/300/600/1500` 수준으로 함께 재조정해야 한다.**

### Q3. 어뷰징 상한과 GPS 미인증 처리 + 이번에 붙일 화면 범위

> 세 가지가 한 덩어리인 이유: 전부 "이번에 어디까지 만드나"의 경계이고, 답에 따라 백엔드·프론트 작업량이 함께 움직인다.

#### Q3-a. 일일 적립 상한 (설계서가 "구현 단계에서 확정"으로 미뤄둔 숫자)

- **맥락**: `function.md:109`는 *"같은 장소 하루 3건까지만 적립"*만 정하고 **행동별 일일 총 상한은 비워뒀다.** 상한 없이 배포하면 한 사람이 하루에 같은 곳에서 제보를 반복해 무한 적립할 수 있다(제보 자체는 `client_request_id`가 매번 새로 발급되므로 막히지 않는다). "하루"의 기준은 어느 쪽을 고르든 `report_window.today_cutoff_utc()`(KST 자정)를 재사용한다(P16).
  - **선택지 A**: 같은 장소 하루 3건 **만** (설계서 문장 그대로, **권장**) → 판정 쿼리 1개. 여러 관광지를 도는 정상 사용자는 제한을 못 느낀다.
  - **선택지 B**: A + 행동별 일일 총 상한(예: 제보 10건 / 답변 10건) → 쿼리 2개. 방어는 확실하나 숫자 근거가 없어 임의값이 하나 더 는다.
  - **선택지 C**: 이번엔 상한 없음, 운영 정비(8단계)로 미룸 → 가장 빠르지만 **데모 중 아무나 크레딧을 무한 적립할 수 있다.**
  → 어느 쪽이든 **상한 초과 시에도 제보·답변은 정상 저장**되고 적립만 건너뛴다(P15).

#### Q3-b. `gps_verified=False` 제보/답변에 적립할까?

- **맥락**: `DEMO_BYPASS_GPS=True`(노트북 시연용 스위치)면 반경 밖에서도 제보가 **저장되고 `gps_verified=False`가 찍힌다**(`reports.py:79-83`). 크레딧의 명분은 *"실제 현장에서 정보를 제공했다"*이므로 여기서 갈린다.
  - **선택지 A**: `gps_verified=True`일 때만 적립 (**권장**) → 크레딧 = 현장성의 증거라는 정의가 유지된다. 대신 **데모 모드로 시연하면 크레딧이 0으로 남아 이번 기능이 화면에 안 보인다** — 시연 시 실기기 또는 시드 데이터 필요.
  - **선택지 B**: 저장되면 무조건 적립 → 데모가 쉽다. 대신 `DEMO_BYPASS_GPS`를 끄는 걸 잊고 배포하면 원격 제보에도 크레딧이 나간다.

#### Q3-c. 마이 화면을 어디까지 만들까? (기능 12 MyPage와의 경계)

- **맥락**: `profile_screen.dart`는 **전부 하드코딩 mock**이다 — 스탯 4개가 `'0'`·`'0p'`(`:188-195`), 메뉴 8개 전부 `onTap: () {}`(`:245`), 로그인 버튼 2개도 빈 콜백(`:156-158`). 크레딧·뱃지를 만들어도 **보여줄 곳이 없으면 기능이 없는 것과 같다.**
  - **선택지 A — 최소**: 스탯 행(제보 수 / 답변 수 / 크레딧)을 실제 값으로 교체 + 뱃지 배지 1개 표시. 죽은 메뉴는 그대로 둔다.
    → 프론트 반나절. 크레딧이 실제로 오르는 걸 즉시 확인 가능.
  - **선택지 B — 권장**: A + **"Credit 내역" 메뉴를 실제로 연결**(원장 목록 화면) + 동작 안 하는 '북마크' 스탯을 **뱃지 자리로 교체** + `function.md:76`에 어긋나는 **Google 로그인 버튼 제거**(C5).
    → 프론트 1일. `function.md:105`가 원장을 만든 이유(*"왜 줄었죠?에 답할 수 있게"*)가 화면에서 실제로 성립한다. 죽은 UI 2개가 줄어든다.
  - **선택지 C — MyPage 전체(기능 12)**: 내 제보 목록 / 내 Q&A 목록 화면까지. **백엔드 엔드포인트 2개 추가 필요**(`GET /reports`가 현재 `spot_content_id` 필수라 "내 제보"를 못 뽑는다).
    → +1일 이상. 로그인 없이는 전부 `test_user` 한 명 것이라 가치가 반감된다.

- **권장: Q3-a=A, Q3-b=A, Q3-c=B.**

### Q4. 답변 크레딧을 "답변당" 줄까, "질문당" 줄까?

- **맥락**: 006 일지 11절이 **미해결로 명시해 둔 구멍**이다. 정책상 한 질문에 **복수 답변이 허용**되고(006 9절 사용자 정책 원문), `create_answer`에는 제보의 `client_request_id` 같은 멱등 장치가 **없다**. 크레딧이 붙는 순간, 한 사람이 같은 질문에 "네", "맞아요", "저도요"를 연달아 달아 반복 수령할 수 있다. `credit_ledger`의 `UNIQUE(user_id, source_type, source_id)` 제약에서 **`source_id`에 무엇을 넣느냐**로 결정되며, 나중에 바꾸면 마이그레이션 + 기존 원장 정리가 따라온다.

- **선택지 A — `source_id = question_id` (질문당 1회, **권장**)**
  → 같은 질문에 두 번째 답변부터는 저장은 되지만 적립 없음. DB 유니크 제약 하나가 그대로 방어벽이 된다(추가 조회 불필요).
  → 잃는 것: 성실하게 서로 다른 내용을 두 번 답한 사람도 1회만 받는다. (답변 수정·삭제 기능이 없어 이어 쓰는 경우가 실제로 생긴다.)

- **선택지 B — `source_id = answer_id` (답변당 1회)**
  → 쓴 만큼 받는다. 단 **유니크 제약이 어뷰징을 전혀 막지 못한다**(답변 id가 매번 새로우므로). 방어하려면 Q3-a의 일일 상한에 전적으로 의존하게 된다 → Q3-a에서 C(상한 없음)를 고르면 **무방비**가 된다.

- **선택지 C — `source_id = answer_id` + "같은 질문 하루 1회" 별도 카운트 쿼리**
  → A의 방어력 + B의 기록 정밀도. 대신 적립 경로에 조회가 하나 늘고 정책 설명이 길어진다.

- **권장: A.** 이유 — ① 006 일지가 남긴 미해결 항목을 **DB 제약 한 줄로** 닫는다(런타임 검사 추가 없음), ② `function.md:107`의 *"이 건에 대한 적립은 1회만"*을 가장 단순하게 해석한 것이고, ③ Q1에서 B(답변 +50)를 고를 경우 A가 **사실상 유일하게 안전한 선택**이다.

### Q5. 로그인을 이번 범위에 넣을까? (크레딧이 전부 한 사람에게 쌓이는 문제)

- **맥락**: 크레딧 귀속에 필요한 스키마는 이미 다 있다(0-(3)). 그러나 프로덕션 설정에서 `get_current_user_id()`가 **항상 `test_user` 하나**를 반환하므로, 두 사람이 접속해도 **같은 크레딧·같은 뱃지**를 본다. `function.md:246`은 로그인을 맨 마지막(9단계)에 두고 Credit을 5단계로 앞세웠지만, 그 순서는 "크레딧이 개인화되어 보이는가"를 따로 고려하지 않았다.

- **선택지 A — 로그인 제외, `TEST_MODE` 사용자 스위처로 시연 (**권장**)**
  → 추가 작업 0. 이미 `profile_screen.dart:86-124`에 **seed_user 30명을 골라 전환하는 드롭다운이 구현돼 있다**(`GET /dev/test-users`). 사용자를 바꿔가며 크레딧이 각자 따로 쌓이는 걸 **오늘 바로 보여줄 수 있다.**
  → 잃는 것: 실사용자 관점에서는 여전히 전원 공용 크레딧. 배포용이 아니라 데모용.

- **선택지 B — 익명 기기 식별을 먼저 넣는다** (브라우저가 UUID를 발급해 `localStorage`에 저장, 매 요청 헤더로 전송 → 서버가 없으면 `users` 행 생성)
  → 로그인 없이도 크레딧이 **기기별로 갈린다.** 데모에서 두 기기의 숫자가 실제로 달라진다.
  → 비용: 백엔드 `deps.py` 교체 + 익명 사용자 자동 생성 + 프론트 UUID 관리 = **약 +0.5~1일.**
  → ⚠️ 위험 셋: ① 서버가 클라이언트가 준 id를 그대로 믿는 구조 = `TEST_MODE`와 같은 위조 가능성(`function.md:68`이 "배포 시 반드시 False"라고 경계한 그 성질), ② 브라우저 저장소를 지우면 크레딧이 사라진다 — 소비처가 없어 손실이 크진 않으나 사용자에게는 "없어졌다"로 보인다, ③ **나중에 카카오 로그인이 붙을 때 익명 계정과 실계정을 합치는 계정 병합 문제**가 새로 생긴다.
  → **`function.md`가 정한 구현 순서(로그인 9단계)를 실질적으로 앞당기는 결정**이므로 사용자 승인이 필요하다.

- **선택지 C — 카카오 로그인을 먼저 구현하고 크레딧을 그 위에 올린다**
  → 가장 정직한 결과. 대신 `function.md:242-248`의 순서를 뒤집는다(+1.5일, Firebase 토큰 교환 다리 포함). 이번 요청("크레딧이랑 뱃지 추가하자")보다 훨씬 큰 작업이 앞에 끼어든다.

- **권장: A.** 이유 — ① `function.md:248`이 로그인을 뒤로 미룬 근거(*"`deps.py` 하나만 교체하면 된다"*)가 코드로 확인되고, ② 사용자별 크레딧 분리를 **오늘 바로 시연할 수단이 이미 화면에 구현돼 있으며**, ③ B는 계정 병합이라는 새 문제를 만들어 나중에 로그인을 붙일 때 비용을 오히려 늘린다.

## 7. 착수 전 체크리스트 (구현자용)

1. Q1~Q5 답변이 나오기 전에는 **`config.py` 상수와 화면의 "+N" 표기를 쓰지 말 것.** 나머지(모델·마이그레이션·라우터 뼈대·응답 키)는 값과 무관하므로 병렬 착수 가능하다.
2. `app/db/models/__init__.py`에 새 모델 import를 빼먹으면 Alembic autogenerate가 조용히 빈 마이그레이션을 만든다.
3. 적립 코드는 반드시 기존 `await db.commit()` **앞**에 들어간다. 별도 `commit()`을 추가하면 002 일지 10절이 경고한 *"제보는 됐는데 포인트는 안 들어옴"*이 그대로 재현된다.
4. `create_report`의 early-return 2곳(`reports.py:53`, `:91`)을 지나가는 요청에는 적립이 없어야 한다 — QA 시 **같은 `client_request_id`로 두 번 POST해서 크레딧이 1회만 오르는지** 확인할 것.
5. 스모크 순서: `POST /api/reports` → `GET /api/credits/me`에서 `balance`·`total_earned`·`badge.code`가 함께 움직이는지. TourAPI 아웃바운드는 복구됐으므로(C9) 실서버로 끝까지 확인 가능하다.
